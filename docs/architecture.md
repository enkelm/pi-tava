# Architecture

How Pi Coop's parts depend on each other, and the orderings the code relies on. [map.md](map.md) says where things are; this says what to keep when changing them.

## Durable truth and what memory keeps

Pi Durable owns the lasting state of conversations: conversations, entries, tasks, and Pi Pocket's documents (`docs.ts`), in `pocket.sqlite`. People and settings, push subscriptions, uploads, and worktrees are files beside it ([map.md](map.md#data-pi-durable-app-or-pi_pocket_dir)). What `PocketApp` keeps in memory about conversations is read back from storage:

- At startup, `#recover` reads each conversation's run, agent, chat, subagents, and who Pi works for in it.
- After that, every commit goes through `#committed`, which keeps the memory up to date.

Some state lives in this process alone, and a restart forgets it. For example:

- who is connected, typing, or away;
- which tool calls wait for approval;
- the browser's pages;
- when each run ended, which peek tiles and session-list squares use, and whether its last run failed;
- provider sign-ins in progress.

## Project organization

Projects and their goals live in the new session-scoped `pocket.projects` document. Typed-thread membership remains additive catalogue metadata in `pocket.sessions`; it does not change the conversation/task ownership tree. `app.projects` owns validation, filtered projections, independent placement and atomic goal archive/restore. Startup durably marks ordinary legacy threads without a type as Worker and untyped linked roots as independent Chats; explicit types remain unchanged. New linked roots are Chats and inherit their source’s owner-only restriction, never its Work Item membership or Durable parentage. Project cwd is a creation-time default, not live inheritance.

The commit coordinator adopts project changes into the module's cache synchronously, then the same coalesced session-list pass sends a filtered `projects` event to each tab. Session changes also refresh that projection, keeping scoped catalogue membership and hidden-only goal visibility current. Initial connection and access refresh send it too. Project documents and creation receipts are not room documents. New UI is gated by `hello.server.projects >= 1` until the server restarts.

`web/session-moves.js` routes native sidebar drags, touch drags admitted by the row hold chooser, and the touch/keyboard picker through the existing session metadata action. Only a drag originating in that list is accepted; nested goals consume their drop events instead of falling through to a project. Hover timers and edge scrolling live only while the drag does. The original native source retains its own `dragend` listener, so cancellation still cleans up after hovering between tabs detaches the Preact row. Initial feedback waits one animation frame for the browser to capture its drag preview. Multi-row placement uses one transaction per independent thread or whole Work Item, with explicit partial failure reporting across those targets, not a bulk atomic edit; no client-side optimistic membership is published. Thread type, archive state, directory and access remain untouched.

`web/session-hold.js` owns a thread’s initial hold and fresh slide-to-choose gate, expansion/fill dwell, early release and contact cancellation. Activated touch drags transfer to the list-level drag owner so switching sidebar tabs can detach the source without losing release/cancel handling. `web/sidebar-context.js` owns scoped right-click/Context Menu/Shift+F10 access and project/goal touch holds; native thread callouts cannot bypass the chooser. `web/sheets/sidebar-options.js` invokes existing actions against the selected catalogue ID, independent of the open conversation, in a bounded desktop menu or touch bottom sheet. Thread Options retains its source drawer so Select still targets that list. A held contact remains consumed through release and compatibility click even after catalogue-driven row removal. It uses the existing sheets Back stack, restores keyboard focus, and adds no server/storage path. Replies, files, diffs, text fields and terminal gestures remain unchanged.

`web/sheets/project-goal.js` sends manual goal names through the existing goal update action, with a busy guard and inline retry errors. It adds no storage or naming path; the server’s manual-rename guard still takes precedence over AI naming. Sidebar type indicators share `web/thread-type.js` with the labeled conversation-header tags.

New goal creation commits with its first Worker or Pull conversation and its creation retry receipt. The first message reserves a background `pocket.project-goal-name` task. Its response memo prevents a completed naming response from being applied or billed twice; usage, the guarded goal name and task settlement commit together through the invocation runtime. A manual rename or moved naming thread wins. Startup repairs an admitted first message cut off before reservation, before resuming work. `src/server/goal-names.ts` owns this task; the existing `/until` goals remain separate and unchanged. See [projects.md](projects.md).

## Cross-thread handoffs

`app.handoffs` owns transition validation, typed successor creation, milestones, filtered relationships and Work Item membership. UI routes and the native `/handoff` command use that module. The core runtime tool prepares handoffs and records outcomes using invocation-bound commits; it does not grant agents autonomous activation. Agents author briefs, summaries and recommendations; the UI always offers an all-role chooser with advisory recommendations/reasons and disabled-choice explanations. Eligibility loads belong to each chooser opening, including a close/reopen while its closing animation retains the component. Prepared briefs survive a human's choice of a different role. Preparation/completion exempt only their own invocation/run and wait for descendant/background work; activation and option projection require the complete writer task graph to be idle. Review requires an actual completed assistant report, preventing empty-thread reviews. Code-bound completion remains an internal prerequisite, never inferred from a click. Work Item context icons live inside the composer.

`src/server/thread-prompts.ts` defines a dedicated working playbook for each thread type. The non-toggleable core renders `thread_role` before every request from the owning root thread's committed type, including initial threads and inherited descendant helpers. Owner-edited `config.agentPrompts` override only that type's role instructions; missing entries use bundled defaults. `/api/agents` lists these instructions for the owner, and per-type saves validate length/content and the expected previous prompt before atomically persisting the merged configuration. Failed persistence restores the live configuration. Saving the bundled default removes the override. Shared scope guidance and hard execution/readiness gates are not editable settings. This per-agent system-prompt amendment is separate from `workflow` state and the user-message handoff brief; shared prompt sections and repository instructions remain loaded. Each successor has its own conversation/agent configuration: cwd/model/thinking choices may carry forward, but source-local `agent.instructions` do not. Custom instructions added to a destination belong only to that agent and persist across restart. Retired conversations keep their historical role while read-only workflow state overrides its working loop. Prompts guide iteration and validation scope; they do not replace the generation loop, plan/explicit goal hooks, or hard readiness/approval gates.

A handoff successor is an independent user-facing conversation, not a task-owned subagent and not Durable's same-conversation reset/handoff. The creating commit also stores the relationship, retry receipt, group membership and the predecessor's permanent read-only state. A durable background task delivers the initial brief with an attributed request ID. Restarted delivery finds the same submission.

Work Items keep same-work successors together. Creation derives membership and placement from the source; movement and archive/restore update all members together. Grouping never grants access. Project/goal archive continues to use the existing transaction and markers. New document kinds are additive; existing kind/scope/history/fork contracts stay unchanged.

Milestones bind to a code fingerprint. Follow-up is normally the final bounded review-repair stage before Land. It reuses a recorded Reviewer outcome (passed or unresolved) or grounded human-supplied external review through an uninterrupted same-work Follow-up repair chain for the same checkout. `handoffs.ts` receives the app-owned Storage at recovery to resolve durable human submissions for external intake, rather than racing deferred `AuthorsDoc` writes. It rechecks submission/request/entry identity through the public transaction API, excludes handoff couriers and stores source, findings, scope and the matching inspected checkpoint in additive `Workflow.externalReview` fields. Public projections omit raw findings, private submission/request IDs and inspected Git status. Both the model tool and native HTTP intake keep active-writer/idle/fingerprint gates; intake does not establish readiness or perform network reads. Completion checks provenance before fingerprint inspection and again in the final transaction; Land admission rechecks it, refusing historical or manufactured self-attestations. Changed repair fingerprints are allowed, but renewed implementation/integration or new work requires fresh evidence. Declared material rewrites (`reviewApplicability: invalidated`) block reuse and default to fresh independent review; ordinary blockers do not invalidate evidence. Successful review completion defaults to a human-activated Land recommendation. Pull is an independently startable role for external reads and local upstream integration, with no inherited readiness. Land starts from a completed review, performs local integration and checks the impact of changes it introduces. Publish starts from local landing with sufficient verification. Later content changes invalidate the recorded prerequisites. Landed and published are separate facts.

Execution restrictions are part of `pocket-core` and the conversation's environment. They cover direct filesystem methods, shell execution and inherited descendant capabilities, rather than relying on a model's instructions or the optional Lancet extension. Managed filesystem operations and writable shell children hold reservations through settlement; Pull/publication's workflow lock rejects existing reservations and excludes later writers. Fetch also checks `app.handoffs`' full ownership/task graph while holding that lock, exempting its own main invocation/run and the exact incoming brief courier already placed into that run, before any Git inspection or external execution. Queued/unrelated deliveries and helper reporters remain blocking work. GitHub helper reads do not use that idle gate. The offline ref import rejects symbolic destinations for the staged branch names, including dangling/chained symbols and remote branches named `HEAD`. It also refuses checkout URL rewrites of the staging import path so an unchecked file remote cannot replace the inspected source. Publication uses a separate exact-command approval path. Its intent and approver are stored before external execution; an interrupted external effect remains uncertain, never automatically replayed.

See [handoffs.md](handoffs.md) for the contract and platform limitations.

## Private Herdr mirror

The owner-only Herdr tab, beside Collab, is a separate view of existing local Herdr processes. This is an explicit change from the earlier Durable-only plan: private work remains ordinary Pi until imported. `PrivateSessions` discovers instance/workspace/tab/pane snapshots and reads the selected pane's terminal and last persisted Pi branch. It never writes the source journal, creates a Durable conversation, or sends private content through shared room events.

Workspace discovery preserves Herdr’s repository membership, active tabs and status. List reads also resolve checkout branches using the existing read-only Git helpers. The sidebar groups only matching daemon-provided repository keys within one instance. Terminal snapshots supply fresher workspace metadata; folding is browser-local and sends no native request.

Private HTTP routes require the app owner before any socket/process/file access and return `no-store` responses. Browsers only poll while the private tree or pane is visible; leaving or losing owner access clears its in-memory data. The private route and draft are separate from numeric Durable conversation IDs and the shared view. Private Chat uses `TranscriptEntry` from `web/transcript.js` in read-only mode: the same user bubbles, assistant blocks, thinking and paired tool cards, without room actions, file/image resolution or executable rich blocks. Both composers use `web/message-box.js` for the message box, auto-sizing field and send control; only presentation is shared. Private drafts and guarded delivery remain in `web/private.js`, with no shared draft/history storage. `web/private-input.js` manages memory-only upload previews and native command suggestions. The shared model-picker presentation accepts a private callback, so selections cannot configure a Durable room. Private model commands are acknowledged as transport delivery only; the chip follows selected-branch journal metadata, and an unobserved switch holds Chat for an explicit terminal-editor check. The terminal snapshot is collapsed beneath saved messages. Pane-detail polling requests only `pane.read` source `visible`; recent-history reads are forbidden for automatic UI snapshots because Herdr can drive alternate-screen agent scrolling to harvest them. Saved history remains journal-backed.

Prompting uses Herdr's agent-aware `agent.prompt`, not raw pane input. The server rechecks the session reference and OS foreground identity against a revision that changes on process/session replacement and app restart. Only verified idle Pi panes accept text. Requests have bounded, in-memory deduplication; uncertain sends are never automatically retried. A shared pane-operation lock prevents bridge input from overlapping an app-initiated takeover. Neither that lock nor PID checks are an atomic OS process lease, and external terminal activity remains outside the app's control. Idle status also does not prove editor focus after a custom command opens a selector. Known terminal-dialog commands are refused in Chat.

Private uploads are separate from Durable conversation files. The owner and Pi revision are checked before and after a bounded stream. Opaque upload tokens bind the owner, pane and revision; clients cannot nominate file paths. A send resolves tokens and promotes their files to retained storage before durable admission and `agent.prompt`. Both acknowledged and uncertain sends leave retained files available for delayed reads. Uploads themselves do not reserve the pane-input lock, so multi-file staging cannot block native input for the length of a file transfer. The registry and previews are ephemeral; a restart invalidates old revisions/tokens, not admitted external input.

The selected conversation can become shared only after **Import & share** confirmation. This publishes under Pocket's existing authenticated/scoped access rules, not anonymously. Its full source archive remains owner-only. Chat remains Pi-specific. The separate structured Terminal mode controls shells and other agents through Herdr's native client protocol. See [private-sessions.md](private-sessions.md) and [terminal-mode.md](terminal-mode.md).

### Structured terminal connections

`PrivateTerminals` issues short-lived, one-use WebSocket tickets after owner, origin and an acknowledged Terminal-open request. The upgrade repeats authentication, verifies the selected terminal identity, and launches an owned native helper against a server-resolved `herdr-client.sock`. The helper uses pinned, unmodified Herdr GPUI client/protocol crates to decode and reconstruct native frames. The browser renders cells and sends semantic input; it does not run a VT parser or a second shell.

Terminal attachment reserves the shared operation lock through handshake and initial focus. Chat admissions, runtime resize/layout/focus changes, native writes and takeover take short reservations before asynchronous checks and dispatch. An already attached terminal and recorded terminal use do not block import; native writes cannot overlap an app-initiated move. This coordinates Pocket operations, not Herdr's queues or other terminal clients. Durable opaque receipts precede external input. Unknown Chat delivery remains blocked across app restart; known terminal-use receipts do not imply uncertain Chat delivery or queue cancellation. No terminal transcript or prompt text is stored in these receipts. The helper may be terminated during cleanup; Herdr and its pane processes are never signalled by connection cleanup.

The gateway bounds frames, queues, command batches and connections and checks live owner access. The browser keeps instance connections across Private navigation and may reconnect to fresh state after a transport failure. It never replays input or pending requests. Explicit disconnect and owner-access loss suppress reconnection. Native layout operations travel over the connection-associated endpoint, not a global focus-stealing JSON request. Private WS traffic remains separate from shared room events.

The grid embeds `terminal-keyboard.js` on narrow or coarse-pointer screens. The touch keyboard emits semantic strokes through the grid’s current target and the same Herdr shortcut handler as hardware input, without DOM key-event dispatch or browser-reserved shortcut interception. Its one-shot/locked modifiers and repeat timers are memory-only and cancelled when the target, popup, input epoch, visibility or interactivity changes. Local `setTarget()` and cancellation reset keyboard intent synchronously, before any render. Pointer taps commit on release and scrolling cancels them; keyboard/assistive activation preserves button focus. Short terminal hosts scroll the key rows under a sticky toolbar instead of clipping essential keys. The hidden textarea is read-only with `inputMode="none"` in touch mode; native input is an explicit fallback. The keyboard’s Paste control opens a separate editable, memory-only text field for native paste menus without reading the clipboard API. Explicit submission uses the grid’s existing semantic Paste event and UTF-8 size bound; target/connection/access changes and local navigation resets discard the draft. Keyboard height participates in the terminal’s flex layout and resize reporting. `terminal-viewport.js` owns physical size reporting: its last geometry/connection key survives observer recreation and metadata/surface input fences, rather than being reset whenever interactivity changes. Actual dimension/cell-metric changes still report once and new input epochs start fresh; disposed observers cannot restore old geometry. The grid owns expanded/type state and supplies the keyboard-type group plus chevron and a Touch-only Paste icon through an optional chrome render slot. Private Terminal puts the Paste icon last in its retained mobile tab/split/zoom bar, and the type controls beside connection/help controls in the footer. The keyboard exposes a local reset/open-paste controller so the relocated action opens the same draft editor and returns Cancel focus to that icon; there is no second paste-delivery path. Its grid host reserves separate action/footer rows so read-only preview overlays cannot cover those controls. The persistent modifier hint is removed; Herdr shortcuts and Help remain. Temporary diagnostics project whitelisted transport/state/DOM geometry metadata through `terminal-diagnostics.js` without subscribing to a new native stream or changing delivery/scroll policy. Recording does not trigger renders. Browser-queued controls and received surfaces have relative timestamps; payloads, key values, titles and paths are not retained, and exports use identifier aliases. Per-connection bounded memory is cleared on disposal/owner-access loss; only an explicit owner Help action exports a stable JSON snapshot, with a readonly selectable fallback when clipboard copying is blocked. `terminal-touch.js` separates touch intent from mouse input: it waits for a tap, swipe or deliberate hold before sending anything, with timer and continuation fences on pane/popup/boot/input epoch, interactivity and geometry changes. Swipes use the same bounded semantic scroll accumulator as wheel input; fractional deltas are connection/target-scoped and reset at touch start. Holds select locally even in mouse-reporting TUIs, with a reduced-motion-aware activation cue instead of a viewport bounce. Multi-finger contact cancels terminal intent and leaves pinch zoom to the browser; release does not synthesize momentum.

## Importing ordinary Pi history

New Session → Import uses a compact bordered Live/History tab group in its source header. `app.imports.history` discovers ordinary saved files under Pi's agent sessions root (including `PI_CODING_AGENT_DIR` overrides), without opening a mutating session manager. The owner-only, no-store list returns bounded title/path/cwd/recency metadata, not journals or tool output. Discovery walks only the root and immediate project directories, refuses links, limits scanned entries, retains the 100 most recently modified candidates and reads at most 64 MiB sequentially, passing each charged candidate size as a trusted cap on the actual file-descriptor read. Known local Herdr source files are omitted from History; discovery cannot prove that every external writer has exited. Saved-file import retains its explicit stopped-process acknowledgment and strict hash/branch validation.

The browser loads History on first use and filters metadata locally. Expanding one row calls the existing preview route, which now also returns up to six bounded user/assistant text excerpts from the selected branch. It does not expose images, thinking, tools or other branches. A second action opens the existing model/consent confirmation; list selection and preview never create a conversation or tasks. Manual file/branch entry stays under Advanced import. Search and the expanded row survive outer New Session tab changes in memory only.

`app.imports.active` discovers local Herdr Pi sessions through its socket API and matches foreground PIDs to the local OS process table. Idle sessions remain selectable after terminal use. Selection only previews. Busy sessions require explicit abort consent: after source/destination preflight and a persisted `pocket.takeovers` reservation, the server sends a targeted Escape, waits for Pi to become idle and its tools to exit, then stops that verified Pi PID alone with SIGTERM. The abort path validates and imports the newly saved journal rather than the provisional preview. Ambiguous identities, protected ancestors, unresolved tool results and surviving children remain refused. It never closes a pane or escalates to SIGKILL.

A browser disconnect does not cancel the move. The import transaction also commits its takeover result, so completed retries reuse that conversation. Pending retries revalidate process identity before any stop. A failed or interrupted move stays available for explicit preview/retry after reopening the app. No automatic stop is issued during daemon startup. Imported history comes from the last persisted branch, not unsaved terminal state. A live preview may contain an unfinished tail, but only a stopped journal with complete tool results can be published. A cancelled user/tool-result tail is accepted only for the confirmed handoff, without starting tasks. Discovery outside local Herdr is not implemented.

`app.imports` validates a stable, bounded read of a stopped source file without opening it through Pi's mutating file loader. It converts one selected branch using the pinned Pi projection helpers. Historical entries are appended directly, never submitted as new user inputs, so they create no tasks or new usage totals. Failed and cancelled assistant attempts stay in history but are excluded from model context. Their partial tool calls were not dispatched by Pi and are shown as an explanatory note rather than pending tool cards. Missing results from actual tool rounds still block import.

One harness commit creates the conversation and agent configuration, appends history, stores the complete UTF-8 source in `pocket.imported-session`, writes the session catalogue and adds a source-hash/leaf key to `pocket.imports`. A failed commit publishes none of them. A retry finds the same conversation, even after restart.

These new document kinds do not alter existing stored kinds. The archive document is not in `ROOM_DOCS`; clients retrieve it through an owner-only download route. Imported user entries carry a display label rather than an invented author mapping, so the first new submission establishes whose work Pi does through the usual attribution path.

Imports default to `SessionMeta.ownerOnly` for compatibility. Explicit `visibility: "shared"` publishes the selected conversation using existing Pocket access rules. `canSee` checks the owner-only flag on the root session, session lists use the same check, and app-created forks propagate it. Scoped users retain their session restrictions. The source archive remains owner-only after sharing. General membership editing remains separate work.

## Comment-first code reviews

`app.reviews` stores discussion alongside the session's current Changes. A first comment makes its author a reviewer; there is no create, assignment, snapshot, verdict or close step. Every person who can see the conversation, including a viewer and the owner, can comment on all changes, a file or an old/new line, and reply. Pi activity never blocks discussion. The composer warns while agents work, and comments retain their original line context rather than claiming a stable checkout.

Review metadata is a separate conversation-scoped, latest-history, initial-fork document. `Room.reviews` projects `{threads, rev}`, not retry receipts. Forks start with no comments. The former round and snapshot document kinds stay registered with their original settings but are no longer read or projected; their data is not migrated.

`GET /api/c/:id/reviews/changes` and `/reviews/diff?path=…` expose read-only changes inside the session's working folder to visible participants. `/reviews/context?path=…` supplies bounded, complete text for unchanged lines in a currently changed file, so viewers can expand context and see comments on those lines inline too. These routes do not grant viewers access to the generic workspace/file/editor routes, unchanged files, or files elsewhere in an enclosing repository. Context reads reject binary, oversized and unsafe files and recheck membership, folder and file identity. Comments keep Git paths exactly, including spaces, and a working-folder identity. A changed or missing anchor remains accessible as outdated discussion instead of being silently attached to a different line.

`POST /reviews/comment` creates a thread or reply. `POST /reviews/resolve` resolves or reopens an explicit set of thread IDs atomically: the owner can handle anyone's threads, and other people can handle only their own. Mutations recheck current membership, record server-authored identity, enforce bounds and use durable request receipts. Resolving never deletes discussion or rewrites its authorship. These discussion routes never edit files, commit Git or submit model work.

`web/reviews.js` groups threads by their original author and derives each person's open/resolved status. Its sticky, collapsible reviewer index shows avatars and the owner's badge, navigates to inline comments, and offers reply/resolve icons. Selecting comments reveals a single bulk-resolution check button. People status links open Changes, expand the selected reviewer and highlight the item. Line discussions render beside their line in unified and split diffs; file discussions render below the filename. Comment composers keep post/cancel icons inside the input. Explicit bot buttons send attributed feedback for one reviewer or all reviewers through the ordinary submission route, without changing the main composer draft. These sends use captured conversation IDs and durable retry IDs, require steering and driving rights, and queue a follow-up while Pi is busy. Posting or resolving comments alone never starts Pi. New review controls require `server.localReviews >= 2`; old servers keep ordinary steering-only Changes until restarted.

## Pi provider compatibility

The owner-selected, restart-only compatibility module is a virtual Extensions row (`pi-providers.ts`), not a watched built-in. `ProviderPackages` resolves installed package metadata through Pi's public package SDK without executing it, stages exact npm releases with scripts disabled in separate Coop-owned trees, and stores requested versus applied selections. No automatic install, update check or restart runs at startup.

Before Harness opening, `ProviderExtensions` opens public-loader/runner hosts in child processes with isolated Pi configuration and registers their native proxy providers into the existing `ModelRuntime`. Conversation lanes have independent extension state and serialize through final-message transformation; auxiliary requests get independent lanes. Required headers/payload/response/message events fail closed, and terminal event and result share the transformed message before Durable persists usage. This is a supported API-key chat profile, not general Pi-extension parity or an OS sandbox. While the module is enabled, parent and worker runtimes use `modelsPath: null`; `models.json` overlays could otherwise select the SDK's unhosted global-API fallback. The file remains untouched and ordinary model configuration returns after disabling the module and restarting.

A failed candidate is disposed before last-applied releases activate in fresh workers. Requested pins remain untouched. Without a usable fallback, the harness stays paused and non-recovery mutations are blocked, because Durable progress calls can enable scheduling independently of `resume()`. Owner provider/auth/restart controls and read-only views remain available. Shutdown joins Harness work before closing hosts/unregistering providers and deleting temporary settings homes; immutable releases remain for rollback. See [provider-extensions.md](provider-extensions.md).

## Who owns what

`PocketApp` (`app.ts`) creates the app's parts and hands each one the app.

**Its parts:**

- `commands`, `extensionCommands`, `collab`, `alerts`, `providers`, `schedules`, `goals`, `shell`, `spend`
- `workspace`, `transcripts`, `attribution`, `piSessions`, `pip`, `watches`, `hooks`, `memory`, `gallery`, `reviews`, `projects`, `goalNames`, `handoffs`
- `browsers`, `linkedSessions`, `languages`, `providerPackages`, `providerExtensions`

**What stays on `PocketApp`** (the parts call these rather than keeping copies):

- **Access:** `canSee`, `requireSee`, `requireSteer`, `requireDriver`.
- **The conversation tree:** `rootOf`, `parentOf`, `conversationsOf`.
- **Where a conversation works:** `cwdOf`, `agentState`, `sessionMeta`, `isBusy`.
- **Live views:** `room`, `openRoom`, `releaseRoom`.
- **Tabs and peek tiles:** `attach`, `detach`, `setPeeks`.
- **The app's lifecycle:** `open` and `close`.

The harness, models, and settings exist only once `#open` has set them up, after the parts are made. So a part made with the app must not read them in its constructor; it reads them when it is called.

Extensions never see `PocketApp`. They get `PocketHost` (`host.ts`), whose functions call into the app lazily, and `web`, through which they add routes and a browser module to the app. `ExtensionWebs` (`extension-web.ts`) keeps what each module's version added, which the loader commits once the module installed and removes with it, running its cleanups. The HTTP layer parses a request, checks it, calls a part, and writes the answer; it holds no state of its own beyond invites and the event streams' pollers.

## Favorite folders

`FolderFavoritesDoc` (`pocket.folder-favorites`) stores each person's ordered favorite working folders in SQLite. `folder-favorites.ts` reads and changes only the signed-in person's list; explicit star/unstar operations run inside one harness transaction, so concurrent devices do not overwrite unrelated changes. The commit coordinator sends each connected client only its person's list as a `folder-favorites` event. `hello.folderFavorites` supplies the initial list and refreshes it on reconnect. The folder picker shows only what the server committed, so a failed save leaves its list as it was.

## Linked sessions

`LinkedSessions` (`linked-sessions.ts`, `app.linkedSessions`, `host.linkedSessions` as `LinkedSessionsApi`) starts a session from another and carries messages between them; Agent Teams (`extensions/agent-teams.ts`, off by default) is its only user. A linked session is an ordinary ownerless session in the source's folder. Its session entry's `linkedFrom` names the session that started it, and nothing else follows from it: it is not in `SubagentsDoc`, `parentOf`, or `rootOf`, so it gives no access, and stopping or archiving one leaves the other as it was.

- **Whom it acts for.** Each call acts as the person Pi works for in the source (`requesterOf`), with their checks: seeing the source, steering, the turn, spend, and, to start one, access to every session. The source in plan mode starts and sends nothing. A message goes through `Commands.submit` as sent for that person (a `p:` request id), with `[via linked session …]` and the message fenced (`defang`), so its text is never a slash command and Pi reads it as a request; the target's checks apply there too. The transcript knows such a message by that label and fence, not by the words before the fence.
- **Once.** Each call's key is hashed with the source into an item of `LinkedSessionCallsDoc` (`pocket.linked-session-calls`), which records the session it made or messaged, whom it acted for, and when. A start writes it in the same commit as the session, then sends the first message; a message's request id is made from the same hash, so a replay finds the session and the message it made. Records are kept 30 days, and the newest 1000.
- **Bounds.** A linked session starts none, and a session starts at most 10 (counted in the commit that makes one). `LinkedSessionRelayDoc` (`pocket.linked-session-relay`) on the team's top session counts messages between its sessions; past 20, sends are refused, and a person's own message in any of them (`Commands.submit` without a `via`) sets it back to 0. It is counted in a commit before each message goes, so it survives a restart. `Spend` counts a team against its top session's budget: the top session, every session linked under it, and their subagents.
- **What it shows.** Sessions know each other by addresses of their own (`LinkedSessionPeersDoc`, `pocket.linked-session-peers`), so no session id goes into a shared transcript; a fork starts with none. `list` reaches only the sessions the person sees, and names them only when everyone who sees the source sees them too. The session list (`PocketApp.sessions`) gives someone who cannot see the origin `linkedOrigin: true` in place of `linkedFrom`; a scoped person's tabs get their own list in every broadcast, not a filter of everyone's.
- **Models.** A start copies the source's agent settings (model, thinking, instructions, tools), not its history. It takes only the source's model or an entry in the shared `subagentModels` list; an empty list means source-model only for linked sessions. Thinking is capped at the source's level and fitted at or below that cap, unlike background subagents' nearest-supported fitting. `Providers.problem` asks its provider afresh: nothing is made with a model that is not allowed or cannot be used now.

Subagents leave Agent Teams out of every subagent (`extensions/subagents.ts`), even while it is off, so turning it on later gives no subagent a way to start sessions.

## PiP's conversation

PiP (`pip.ts`) is a conversation with a `pip` mark in its session entry, which `sessions()` leaves out of every list. The harness settings select every installed extension but PiP's (`pocket-pip`) by default; PiP's conversation stores its own selection (`PIP_EXTENSIONS`, without bash, write, or edit), which `ensure` sets again each time it opens, so PiP's tools reach no other conversation. Its tools act through `Commands` and `Schedules` as PiP's person, with that person's checks, so `canSee` keeps every PiP from everyone but its person: anyone who could write to it would act as them. Its messages to sessions are once per tool call (a request id hashed from the call's key), and each follow leaves a mark in its list (`FollowsDoc`) when it reports or is stopped, so a replayed call neither sends nor follows twice. A tab's PiP panel is a second client in PiP's room (`setPip`), whose `view` events reach the tab as `pipview`; `watching` counts it, so PiP's answers push nothing while it shows.

PiP's header model chip opens the existing picker with its own conversation ID and live view, not the session behind it. Its `pipPanel` configure request uses `Commands.configure`, checks private PiP ownership, and checks `LiveDoc.run` and compactions in the same commit as the model/thinking write. It leaves `lastModel` alone. Ordinary configure requests, including **Open as a conversation**, retain their behavior.

## Work from outside the app

A PR watch (`watches.ts`) is a `WatchDoc` in its session and a durable task there, which sleeps until its next look, looks with `gh` (`watches.gh`, which tests replace), and puts what to tell Pi in its checkpoint before sending it: the send's request id is the watch's task and count, so a restart sends it once. Comment ids told, and the commits whose failures and conflicts were told, stay in the watch. Webhooks (`hooks.ts`) are app-wide (`HooksDoc`); `/hook/…` is outside `/api` and its sign-in, and lets a post in only by its hook's secret. Both send through `Commands.submit` as their person, with a `via` that marks the message (`[via PR watch]`, `[via webhook NAME]`), so that person's checks and spend limit apply, and what came from outside is fenced (`fence.ts`, as PiP's session text is): no closing tag survives inside, in any case or spacing. A hook's address and secret are checked before its body is read. A signed hook (`signed`, for GitHub) lets a post in only by GitHub's signature: its secret is never in its address, so the address GitHub shows a repository's admins cannot post. Pi's `watch_pr` names a PR by number, which `gh` finds in the session's own repository, or one elsewhere by address only where `gh`'s account can push (`requirePush` in `github.ts`); what follows `--` is never an option.

A repository watch (`repo-watches.ts`) is an item of the app-wide `RepoWatchesDoc` and a durable task in the conversation it messages (PiP's, or a session's), with the same wait, look, and send phases as a PR watch: a look puts the message in the task's checkpoint, and the send's request id is the task's and its count's, so it goes once. It reads the repository's issues, pulls, workflow runs, releases, and comments through `gh api`, and keeps the ids it told. PiP's tools (`repo_watch`, `session_watch_pr`, `session_start` with `repo`) act through `Pip` as its person; a repository is worked on or watched only where `gh`'s account can push, and `Pip.checkout` finds a session's checkout whose `origin` is the repository, or clones it once into `repos/`.

## Who chooses models

Sessions and PiP keep their person-selected models, with no silent fallback. Background subagents retain Coop's explicit-model contract; linked sessions have a stricter policy:

- **Sessions** run on the model someone picked, or on what a new session starts with (`Commands.#defaultModel`): the owner's default, even when it is not signed in now, else a trusted project's model/thinking default, else the last model picked, else Pi's global default, else none. `project-model.ts` reads only the final session folder's `.pi/settings.json` at creation, without a cache; a fresh creation-local global-only settings reader supplies defaults and trust policy without changing `app.settings`. It checks Pi's trust store and global trust policy, validates a complete provider/model pair, and keeps known unsigned models rather than silently substituting one. Invalid trusted settings stop creation with a contained error. Thinking-only settings cannot change another source's model/thinking pair. Owner defaults bypass project settings. Imported sessions, forks, subagents, manual choices, and PiP's own conversation retain their previous selection behavior. A model the person explicitly named to PiP bypasses project defaults before its manual configuration step. Trust gained after creation applies only to later new sessions; existing choices never track file or folder changes. Extra project skill/prompt paths and per-project run policy are not supported yet; the shared app settings and older host APIs are unchanged.
- **Background subagents** (`extensions/subagents.ts`) always expose an optional `model` parameter; omission inherits the parent's model. An empty owner `subagentModels` list leaves explicit choices unrestricted. A nonempty list restricts extra models, but the parent's model is always allowed. `PocketApp.setSubagentModels` replaces the list; `allowSubagentModel`, behind the Providers sheet's `POST /api/subagent-models`, changes one entry with no wait between reading and writing, so concurrent changes count. The app reloads the module to refresh guidance, not to add or remove the parameter. Spawn and later sends check the current list; removing the last entry restores unrestricted choices. Explicit model selection refreshes the sign-in check; a later send to a child on another model checks its provider too. Spawn thinking, explicit or inherited, is fitted to the chosen model's nearest supported level, including `max` and levels above the parent's. Later work preserves the child's model and thinking; it never lowers thinking to match the parent. A model/provider failure names the model and tells Pi to stop and tell its person, never silently retry on another model.
- **Linked sessions** (Agent Teams, `linked-sessions.ts`) always treat the shared `subagentModels` list as an allowlist of extra models: empty means parent-only, unlike background subagents. They start on the source's model or a listed one. Thinking is capped at the source's level, then fitted to the highest supported level at or below that cap; no such level means refusal. A model that cannot be used now is refused before the session is made.
- **Session titles and project-goal names** use the cheapest available text-capable small model of the conversation's provider, falling back to the conversation's own model when none is available. Their usage counts against that conversation.
- **Compaction and PiP's summaries** use the conversation's own model.
- **PiP** passes a model, or names one in what it sends, only when its person named it in their own words (`pip.ts`, with `model-names.ts`): their own messages (`u:` request ids, from the authors document) since PiP's last new context (with those its last compaction kept), and the standing instructions of the watches and webhooks to PiP that they set up; never a watch PiP set up, what was posted, or what GitHub said.
- **Sign-ins:** `Providers` asks subscriptions' sign-ins afresh (the owner's Providers sheet, a model a subagent on another model or PiP is about to use, a run that failed on one, a run answered by a marked one) and keeps, in memory, the ones their provider refused to renew. Explicit subagent model choices (`resolveModel`, `modelProblem`), later work for subagents on another model, PiP, and linked sessions as they start (`Providers.problem`) check before use and refuse unusable models. A session's own run and a subagent inheriting its parent's model try it and fail where people see them, and a run that failed on an expired sign-in marks it; a title that fails is only logged. `modelList` and `agentInfo` mark them, and the owner is told. A check that began before a sign-in or sign-out here marks nothing.

**Manual model refresh.** `Providers.modelRefresh` (`model-refresh.ts`) shares one in-flight refresh across owner tabs. `POST /api/models/refresh` requires the owner and the normal `X-Pocket` header; `hello.server.refreshModels` gates the UI against an older server. It checks local configuration with Pi’s public runtime API before reloading it, then refreshes each configured provider in parallel with a separate eight-second limit and `force: true` (network stays off under `PI_OFFLINE`). Each completed provider sends the existing `models` event and refreshes room views, so a slow provider does not hold back a healthy one. Pi owns cache publication and cancellation generations; failed catalog fetches keep its cached/static models. Refresh never configures a conversation or changes the default or subagent allow-list. Counts compare available provider/id keys before and after; provider errors are safe fixed messages, not raw exceptions that could contain credentials.

`PocketApp.modelList` resolves Pi’s `enabledModels` through the SDK’s `resolveModelScopeWithDiagnostics` against available models, then `modelList` marks scope membership alongside sign-in state. Both `hello` and providers’ `models` updates use that list. Manual refresh rereads Pi settings before recomputing the scope; malformed scope values are ignored so the picker still opens. The model picker’s Scoped / All state lasts only while it is open and filters the list without changing Pi’s settings, the session’s model, or its default. Empty scopes mean all available models, not a ban on picking models.

## Memory

Lessons Pi keeps across sessions are one document for the whole app, `MemoryDoc` (`pocket.memory`), by id. Each is for a project or for everywhere. A project is keyed by the real path of its git common folder (`git rev-parse --git-common-dir`), so a repository and all its worktrees share lessons; outside a repository, by the folder itself. `Memory` (`memory.ts`) works out a folder's project (kept a minute per folder) and keeps the rules:

- The memory extension's section renders, before each request, the lessons in force for the conversation's folder: its project's and everywhere's, not pending, oldest first. It reads committed state only, so it renders the same text until a lesson changes. PiP has no project: it gets everywhere's.
- Pi proposes, the owner approves. Every lesson Pi saves, and every one a person who is not the owner saves, is pending, and no prompt has it until the owner approves it: what Pi read anywhere in its context could have talked it into one. Pi's (or a guest's) new text for a lesson in force, and Pi's forgetting one, are a `proposal` on the lesson, which stays as it was until the owner approves or discards it. The tool's result names the lesson (`details.lesson`), so the transcript offers Approve and Discard under the call. An approval names what it saw (`POST …/memory/:id/approve` with `{ text }` or `{ forget: true }`); when what waits differs, `change` answers 409, so text or a proposal swapped after the owner looked is not approved with it. Pi proposing the text in force withdraws its own waiting proposal. Pending lessons do not count toward a project's or everywhere's cap; approving one does. Only the owner, or whoever saved a lesson, changes or removes it, Pi included (as the person it works for).
- Pi's adds carry the tool call's key, so a replayed call finds its lesson. A subagent's lesson comes from its session (`rootOf`).
- Every write adds an activity line to the session's chat in the same commit. `#committed` tells `Memory` when the document changed; it sends tabs a `memory` event, and the Memory sheet and menu fetch the lessons again (`GET /api/c/:id/memory`).

**PiP's pending queue.** `GET /api/c/:id/memory?pending=all` lists new lessons and proposed edits or forgetting across every project and everywhere. It requires the human owner and their private PiP root as its anchor; queue approvals and discards use the same query on the existing mutation routes. Pi writers, other people, shared-session anchors, and queue add/edit/remove requests are refused before cross-project lookup. Approval retains the existing compare-with-what-was-shown check, limits, and transaction. Activity stays in the private PiP chat, not a shared session. The queue response has `pendingAll: true`, no project or add/edit controls, and project labels on lessons; an older running server's scoped response has no marker, so the new UI asks for a restart rather than claiming to show all projects. Browser memory fetches are keyed by person, role, conversation, and view, and refresh on memory events or a new connection.

## Startup

`PocketApp.#open` runs in this order, and the order matters:

1. Take the data folder's lock. Set up push, Pi's settings, and the HTTP settings for provider streams.
2. Load the models, activate approved Pi provider packages (or retained releases), then register the core tasks and every ordinary extension module that is on.
3. Open the storage and the harness.
4. `#recover`:
    - read the session list;
    - for each conversation, in turn: its run, agent, chat, who Pi works for (`attribution.recover`), and its subagents;
    - then write back, in one commit, the authors that a crash kept out of the authors documents (`attribution.repair`).
5. Load spend.
6. Subscribe to commits, approvals, and browser pages.
7. Warm Lancet Guard.
8. Resume the work the last process left unfinished, unless provider recovery mode holds scheduling.

Work resumes last, so that everything that follows commits is listening before the first one comes.

## The commit coordinator

Pi Durable publishes each commit's changes in no set order. `#committed` handles them in two passes:

1. **Usage first** (`spend.usageChanged`): what a commit's usage cost belongs to whoever Pi worked for before a message in the same commit changes that.
2. **Then each change:**
    - Document changes go to `#documentCommitted`. It tracks busy and ended runs, agents, the session list, and the documents the rooms show (`ROOM_DOCS`).
    - Submissions go to `attribution.submissionCommitted`.

Everything here is synchronous. A commit listener may not call the harness's session APIs, so a write it causes (noting a message's author, or moving a session up the list when Pi starts work there) runs in `setImmediate`. Keep this one coordinator: separate listeners would make their registration order a billing rule nobody can see.

Updates to tabs are coalesced:

| What                                                                       | How often, at most |
| -------------------------------------------------------------------------- | ------------------ |
| A room's changes                                                           | Every 90 ms        |
| Peek tiles                                                                 | Once a second      |
| The session list, and every subagent to tabs that show the subagents board | Every 400 ms       |

Each room update sends a tab its new entries, the live run, and some small fields. The fields that grow with the session, such as the queue, authors, reactions, and pins, go again only when they differ from what the tab has, because a turn sends an update every 90 ms. The queue sends each waiting input's full main text, its separate `editableText` and `hasAttachments` flag, and the names of the subagents in a message of reports. Image bytes and inline file bodies stay out of those rows; an input of images alone says how many. Its row preview and disclosure are presentation only: collapsing the queue never truncates the editable text or changes submissions, even when a paste or a batch of reports is megabytes. A tab's connection names what its code understands (`p`, `PROTOCOL` in `web/store.js`): a tab with code from before, as one asleep through an update keeps, names none, and gets the queue with each update, because its code drops a queue that an update leaves out.

## Who Pi works for

A message to Pi names its person in its request id (`requests.ts`):

- `u:<user>:<key>` is a person's own message.
- `p:<user>:<key>` is one sent for a person, such as a scheduled message or a subagent's task.

`attribution.ts` notes each one in the conversation's authors document. Pi works for whoever wrote the newest message (`requesterOf`). A subagent works for whoever its parent worked for when it sent the subagent its last message. Spend, approvals (the "someone else must allow" rule), schedules, and subagents all ask `requesterOf`. A message sent for someone must carry that person in its request id. One that names nobody does not change whom Pi works for: Pi goes on working for whoever it worked for before. Spend, when nobody is known, falls back to whoever started the session, then the owner.

## Background subagent reports

Each message sent to a subagent has a background reporter task. Its request ID makes delivery and the report to the parent idempotent across a restart. After submission, the reporter watches the child's live state while waiting for the answer. If the child becomes idle with that submission still queued, it withdraws only that submission and reports that it must be sent again. A placed or answered submission is left alone. Withdrawal rechecks idleness and the exact queued submission in one transaction. Its settlement, durable reason and queue removal commit together; reopening reads that reason rather than an in-memory flag, so it cannot be mistaken for someone's Stop. The watch is stopped on every exit, and any withdrawal already under way is joined before the phase ends.

Explicit Stop is silent: it sends no automatic failure report to the parent. A stranded-input withdrawal is different and reports that the message must be sent again, including after a restart.

The upstream batched courier is installed. Reporters append to `SubagentsDoc.outbox`; one durable `pocket.subagent-courier` task gathers them into a single message at the parent's next pause, waiting briefly when the parent is idle. Reports arriving while that batch is queued are merged into it, so the queue holds at most one report batch. `sending`, `batches`, and request IDs preserve delivery across restarts, and `held` explains reports waiting for a spend limit to be raised. Existing anchor and reporter task names, versions, and checkpoints remain compatible; the courier also accepts its older send checkpoint.

## A request

`http.ts` routes by the first path segment, and turns whatever a route throws into an answer: an `HttpError`'s status and message, or a logged 500.

`/api` (`http/api.ts`) checks, in this order:

1. who is signed in (the cookie, or a bearer token);
2. it notes the quick tunnel a guest came through;
3. the `X-Pocket` header, on everything but GET.

A conversation's routes (`/api/c/:id`) run only after `requireSee`.

`/api/x/:module/…` (`http/extension-routes.ts`) is an extension module's own route: after the checks above, and the `X-Pocket` header on a GET too (a module's GET may change things, and the cookie goes along with a link from another site), it answers only the people its `access` lets in (`mayUse`: the owner by default; never someone invited to one session). The header is checked before the route is looked up, and a route someone may not use is not there for them (404, and a 405 names only methods they may use), so nobody learns of routes that are not theirs. A `:name` part that decodes to `..` or holds a backslash or NUL is a 400. Only the owner reads a 500's words, but for those a module gave `web.error`, which it chose to show. `/x/:module/:rev/…` serves its browser module's files, outside `/api` but after a sign-in, to the same people: one file, or a folder's regular web files up to 8 MB, never its `.ts` files, hidden files, `node_modules`, or anything reached through a link. Each is opened without following a link or waiting (`O_NOFOLLOW | O_NONBLOCK`), and read only when its handle is a regular file and the file that was checked (the same device and inode, and on Linux the path `/proc/self/fd` gives), so nothing swapped in after the check, a folder on its way included, is read. Where there is no `/proc` (macOS), a folder swapped for a link within the check itself can still lead elsewhere: only someone who can write in the module's folder can do that, and they can already run code in the server, by editing the module.

Where the other checks live:

- **Commands and collaboration** check steering and driving themselves (`requireSteer`, `requireDriver`). They are called from routes, from tasks, and from each other.
- **Owner-only settings** are checked in `http/api.ts`: extension modules, provider sign-ins, restart. Changing people's access, the approval rule, the default model for new sessions, and the models subagents may use is checked in `app.ts`.
- **Invites** are checked in `http/api.ts` too: viewers and people invited to one session cannot create them, and only the owner makes an owner invite. An invite lasts one of `INVITE_MINUTES` (`auth.ts`; an owner invite, always 15) and is kept in `config.json` by its code's hash, so a day's or a week's outlives a restart. Only whoever made one ends it early (`POST /api/invite/cancel`), as the invite sheet does with the one it showed when its settings change, and with one that answers after it closed. One person keeps at most `MAX_INVITES` (`config.ts`) live, their oldest ending first; removing someone ends theirs, and a new owner token ends owner invites not yet used.
- **The workspace's path helpers** (`conversationFile`, `readableFile`) leave seeing the conversation to their caller.

Each browser tab is a `Client` (`room.ts`), fed by an event stream or by long polling (`http/events.ts`). On connecting, a tab gets:

1. `hello`;
2. the session list;
3. then, when it shows a conversation, the room's full view;
4. then only what changed.

## Extensions' commands

A module registers its commands with `web.command` while it loads. `ExtensionWebs` keeps them with the module's version, as it keeps routes: they count once the version installs, a version that fails leaves the ones before, and turning the module off removes them. Each registration has an id that is new with each version. `hello` lists the commands a person may run (`server.extensionCommands`, without handlers or files: viewers none, guests the conversation ones), and a change to them sends everyone's tabs `hello` again.

`POST /api/c/:id/extension-commands` goes to `app.extensionCommands` (`extension-commands.ts`), not to `app.commands`, which sends messages to Pi. Before a run's task is made, it checks seeing and steering, then driving for a conversation command or the owner for a global one, and that the person has fewer than 4 runs going; a retry of a request checks its person again. Nothing refuses a run once its task is made. The wait ends when the browser stops waiting; the run goes on.

A run is a `pocket.extension-command` task (`COMMAND_TASK`), made in one commit with its request id in the person's `pocket.extension-command-request` document for that session (`CommandRequestsDoc`), which keeps the last 100 finished ones and every one still going. A retry finds that task and waits for its result; the same id with other arguments or another registration is a 409. The handler the request chose is kept in memory until its task takes it. The task marks that it started before the handler runs, and keeps the result in a memo: after a restart, a task with no result reports that it was cut off, and its handler never runs again. A handler's own error words go to the owner in a notice; the person gets them only from `web.error` or an `HttpError`.

A card is a `pocket.extension-command` entry with only `kind` and `data`: no `model`, `head`, or `edits`, so Pi never gets it. Its write's request id is the task's, with no person's prefix (`requests.ts`), so it does not change whom Pi works for. A notice goes back only in the answer to the person who ran it.

In the browser, the composer keeps a command's request id while its send is unresolved, as for `!` commands: sending the same text again after a network error or a 5xx finds the same run. Running now names the command from its task, never its arguments, and shows global ones to the owner alone.

## The web app

Plain ES modules, served as they are, with no build. Editing a file under `web/` reloads every open tab, and a syntax error blanks the screen for everyone.

**Loading order matters.** `store.js` is the root, and a few modules do work when they load (listed in [map.md](map.md#web-web-preact-and-htm-no-build)). `theme.js` must load before anything that reads `prefs()` as it loads. `store.set` calls subscribers in the order they subscribed. When moving code between modules, keep both orders. `back.js` sits under `store.js` and imports nothing of the app's, so anything may use it.

**Completed-result read marks (`seen.js`).** The sidebar and peeks share the existing per-browser `pocket.peekSeen.*` and `pocket.peekSince` keys, server-clock adjustment and visible-open-thread read tracking. Both views use this owner rather than importing one another; `session-seen.js` exposes the Coop naming API without installing another observer. Tracking stays active with peeks disabled and preserves reload, cross-tab, visibility and the 30-day retention cutoff; the separate people-chat read marks remain in `store.js`.

**Themes (`themes.ts`, `theme.js`).** The page has three cascade layers, declared in `index.html`: `pocket` (`style.css`, imported into it, and extensions' stylesheets, which `pocket.style()` imports into it after), `palette` (the colors' variables, a `<style>` that `theme.js` writes), and `theme` (a theme folder's stylesheets). A later layer wins whatever the specificity, and an earlier layer's `!important` wins over a later one's, so a theme overrides the app's rules but not its reduced motion. Inline values beat every layer: only appearance settings (the UI font, text size, dragged widths, custom layout preferences) are inline, never a palette. A stylesheet added outside the layers (a `<link>`) would beat the app and the theme alike.

Theme compatibility uses the package version: Pi Coop's `0.14.0` version matches its Pocket 0.14.0 base so the bundled Lantern theme's `minPocket: "0.14.0"` is supported; the package identity and CLI remain `pi-coop`.

The server reads each theme folder (`readTheme`): its `theme.json`, `colors.toml`, and the CSS reachable from `theme.css` by `@import`, whose every `url()`, `image-set()` string, `src()`, and `@import` must name a file of the folder (`themes/css.ts` tokenizes as CSS Syntax 3 does, escapes resolved; `themeFile` resolves as the browser's URL parser). The checked CSS is kept in memory and served from there, with each font, image, and `@import` named by its full address (a path inside a custom property would otherwise resolve against `style.css`); fonts and images are read from disk at each request, only if the same file that was listed, and sniffed. A version that fails its checks leaves the last good one in force for the life of the process, and the owner gets one notice for each new problem. `hello.themes` and the `themes` event carry the list. The theme's addresses carry a hash of its files, so a change gives tabs a new address: `theme.js` adds the new `<style>` and removes the old once it loaded. `pocket.themeCache` keeps the addresses, and `index.html` writes them into the page with `document.write` before anything paints, which a parser-inserted stylesheet blocks; in safe mode it writes none. Reply HTML keeps no `data-` attributes but a code block's language, so Pi's words never match a theme's part selectors.

What a browser shows is its person's choice of theme (`look`) and colors (`theme`, its name from before themes), else the owner's `config.themeDefault` (`hello.server.themeDefault`, kept as `pocket.themeDefault` so the next load paints it before `hello`): `theme.js` keeps the person's own choices (`pocket.appearance`) apart from the ones in force, with a separate inheritance marker: only genuinely new browsers follow the owner's default. Every pre-existing appearance record is personal, even when it matches the defaults. Layout, font and saved-slot edits do not count as explicit color choices; an explicit mode, color or look choice opts out of inheritance. Startup does not rewrite an existing preference record or persist inherited defaults as a personal choice. Files under a theme's current version are served `immutable`; any other version serves the files as they are now, uncached. Script that depends on where a region is laid out reads it (`useSide` in `ui.js`, looked at again on `pocket:theme`, which `theme.js` sends once a theme's stylesheets load) rather than assuming the sidebar is on the left.

**Live thinking (`transcript.js`).** `theme.js` owns the browser's opt-in; the tab keeps each session's disclosure state. Only an open disclosure selects and draws a thought, memoized separately from the live timer. The active generation, or the latest saved response in the current turn during tools, is authoritative even when it has no thinking. Response and block identity reset follow-scroll for a new thought; only that response's handoff to storage keeps the reader's position.

**Launcher openings (`app.js`, `launcher.js`).** `LauncherHost` observes store transitions synchronously, before Preact batches renders, and keys each logical opening separately. A rapid close/reopen therefore gets a fresh query, selection, and theme-commit flag even when the outgoing launcher is still present for its fade-out. The launcher focuses after DOM reconciliation and isolates its background only while open. Large primary windows use `aria-hidden` and a focus guard, rather than the costly native `inert` traversal of thousands of controls; the overlay blocks pointer access. Other background layers use `inert`. Attribute observers keep the owners' current intent through retained-layer transitions, and close restores that intent before destination focus is restored. Its combobox keeps focus while arrows or Tab move the active option; search-type buttons are a separate group outside the listbox. Field highlights do not change the fuzzy scorer's text or group-first ordering.

**Appearance (`theme.js`).** Bundled palettes, saved Dark/Light choices, color mode, UI font and layout preferences live per browser. `theme` is the live palette; assigning `darkTheme` / `lightTheme` does not change it or the active mode. `chooseMode` activates the corresponding saved choice; System also follows later device changes and resolves the current device preference at startup. Slots select native palettes, not recolorings: a dark palette assigned to Light stays dark. Older saves keep their native palette/mode in force without an automatic preference rewrite; missing slots use the current native palette where applicable, otherwise Tokyo Night for Dark and Catppuccin Latte for Light. `FONTS` offers bundled JetBrains Mono, system sans, system mono and serif; the UI font stack is cached before first paint, while code and terminals keep `--mono`. `sheets/appearance.js` discloses sibling assignment buttons on fine-pointer hover, keyboard focus or a pointer-tracked, cancellable touch hold. Retained Settings panels receive their active state, so hidden Appearance panels cancel timers and do not intercept Escape. Palette cards, slash commands and launcher commits share the manual selection boundary: they choose the live palette and its natural mode without changing the saved slots; committing an already visible launcher preview does not replay its reveal. Optional theme folders retain their CSS, paired palettes, cache and safe-mode handling. A native pair follows its own halves through the additive internal browser preference `systemPalette`; explicitly selecting System instead activates the saved Dark/Light slots. Slots may name folder palettes, whose half resolves after the server lists them, without rewriting an existing save at startup. `chooseTheme` selects live colors, while `chooseLook` selects optional theme-folder CSS and brings that folder's own colors when provided. A temporary launcher preview remains visible when a System media-query change updates the underlying palette. Private and shared routes use the same outer `.window` tiling and active-border rules; Private's compact terminal controls do not override those tokens. No server desktop-theme or wallpaper integration runs, and there are no desktop-theme or wallpaper routes. Theme-folder CRUD remains available. Desktop is not a supported color source for `Themes.hasColors` or Duplicate; an obsolete server theme default falls back to `tokyo-night`. Bundled and custom-theme parsing stays in `themes/format.ts`, including its private pure `parseColors` helper, without operating-system desktop reads.

**Mobile platform guardrails.** `style.css` owns coarse-pointer field font floors, control-only touch defaults and press fills, app-root vertical overscroll suppression and inner-scroll containment. Hover rules in `style.css`, `reviews.css` and `terminal-grid.css` require both hover capability and a fine pointer; focus, selected and disabled states remain independent. Terminal canvas gestures, release/cancellation and focus/input delivery are unchanged; existing `terminal-grid.test.ts` coverage owns those contracts.

Root `--safe-left` / `--safe-right` tokens use platform safe-area insets. `.layout` owns normal horizontal bounds; viewport-level overlays and undocked panels own theirs, without adding nested composer/terminal padding. Existing `ui.js` `popAnchor()` owns anchored-menu placement and now clamps horizontal width/left to those tokens with 8px margins, not extra menu padding. Its vertical visual-viewport/keyboard logic is unchanged. No shell keyboard-viewport adaptation was added: clipping was not reproduced, and Safari, OS-keyboard and installed-PWA behavior still need hardware verification.

**App settings (`sheets/settings.js`).** One sheet hosts Appearance, Providers, Agents, Notifications, Browser, Extensions & safety, Account & access, and Usage & limits. Content comes from `sheets/appearance.js`, `sheets/providers.js`, `notify.js`, `sheets/extensions.js`, `sheets/account.js` (with the access list from `sheets/people.js`), and `sheets/spend.js`. The active category is `sheet.tab`; tab changes update the existing sheet rather than adding history layers. Panels mount on their first visit and stay mounted while the popup is open, keeping drafts, search and scroll position without loading unused categories. The owner-only `sheets/agents.js` panel lists the seven built-in roles with reused `thread-type.js` indicators, per-agent editors, save/error feedback and explicit default restoration. Prompts start read-only; a floating pencil enables and focuses editing. Save and Cancel return to read mode, restoring field focus; Cancel discards unsaved changes and a failed save keeps the editor active. Action icons float directly over the textarea, with no reserved header strip or shared toolbar background. Fine-pointer hover and action focus reveal them; input suppresses them until pointer movement/entry or field blur. Non-hover devices retain visible 40px actions when not typing; `server.agentSettings >= 1` gates loading until the updated server is running. Prompts are fetched separately, never exposed in `hello`, and drafts remain local to the open popup. Legacy settings sheet types share the same history key and component boundary. Provider sign-in prompts still use the separate `AuthDialog`, and invitations use `InviteSheet` only after an explicit action; visiting Settings never creates an invite. Back from an invitation returns to the selected category. Existing settings permission checks and routes remain unchanged; Agents uses the new owner-only prompt routes.

**New Session (`sheets/session.js`).** The sidebar and home screen use one dialog for starting fresh and importing existing Pi history. Start new embeds `ProjectSessionPanel` from `sheets/session-projects.js` on a Projects-capable server, with project selection, optional goal/new-goal intent, path override, worktree selection and a one-time Chat escape. Older servers retain `FolderPicker` from `sheets/folder.js`. The owner-only Import tab embeds `ImportPanel` from `sheets/import.js`; imported threads initially remain unassigned Chats. Panels mount on first use and stay mounted across tab changes, preserving options and drafts. Legacy `cwd` with `mode: "new"` and ordinary `import` sheet entry points share the `new-session` history key and component boundary, so tab changes do not add Back steps. Working directory and private Import & share remain separate sheets; import permissions, confirmation and server routes are unchanged.

**Thread-specific side panels (`store.js`).** One `pocket.panels.<conversationId>` session-storage record owns the selected Files, Browser or docked People panel and the Files/Changes tab. Explicit navigation and route Back/Forward restore the destination's record; unseen threads, home and private routes start without a panel. Open files and browser pages retain their existing conversation-specific owners. Legacy global panel preferences migrate only to the thread open at upgrade. Mobile panel Back callbacks check their originating conversation before closing, so an outgoing overlay cannot close a panel restored for another thread.

**Model picker (`sheets/model.js`).** Shared sessions and Private Chat use the same provider-grouped presentation. Provider expansion is local to the open picker, with the current provider first and expanded by default. Search resets expansion overrides and reveals matching groups; model keyboard navigation uses only expanded rows. Provider disclosure buttons sit outside the per-provider listboxes, separate from model selection. The shared configure action and private callback remain unchanged.

**History is the back stack (`back.js`).** Only `back.js` writes history. Each route (`/s/12`) and each layer over it (a sheet, the drawer, the launcher, the Files tile or Browser panel where they cover the screen, a file over the tile's tree) is an entry, and each entry says how many layers it stands for and how many steps back the session list's entry is. The app's state is the truth and history follows it a moment later: opening a layer pushes an entry, closing one with a tap goes back past it, and a new route first goes back past the layers above the current one. Back that the person makes closes the layers above the entry it lands on; back to another route reaches `store.js` through `onRoute`. Traversals `back.js` makes itself reach no one. So:

- Navigate with `navigate()` (which calls `pushRoute`); do not call `history.pushState` or `history.back()` elsewhere. To drop a query from the address, use `replaceAddress`, which keeps the entry's marks.
- Something new that covers the screen, or that back should close, is a layer: `useBack(open, close)` in the component that shows it, where `close` makes `open` false. Sheets get theirs from `sheets.js`, one per sheet opened from another (the menu, then the model picker).
- On phones the window clips sideways: the conversation sliding in from the right (a route, a swipe's lean) would make the page wider than the screen, and a phone's browser widen and pan its view to fit.
- A finger's or a mouse's press and click within 280 ms of a layer opening or closing, or a route opening, at a tap (a pointer let go in the 400 ms before) is let go, focus and all: a quick second tap would land on whatever slid in under it (a tile of the sheet that rose, the scrim that closes it). What moves on its own (a reply opening a session, the server closing a sheet, Escape) holds nothing back, and keys and scripts never are.
- New entries wait for the page's first tap or key, since Chrome's back button skips entries a page adds before anyone touches it: the list's entry under a conversation opened straight away on a narrow screen, and the entries of layers already open at load (the chat a notification opened, a panel the tab kept).

**PiP chat (`pip.js`, `pip-attachments.js`).** The panel's uploads, submits, image thumbnails, and Markdown image paths use its own conversation ID, never the session behind it. The browser-only attachment draft outlives panel mounts, scopes itself to account and PiP ID, and holds upload identities and submit tokens so late callbacks cannot restore removed files or clear newer drafts. Unknown authentication or conversation IDs during reconnect are not a scope change. Files survive closing and reopening the panel, not a page reload; text keeps its existing local-storage draft. The normal upload and submit endpoints retain their size, file-access, and image-capability checks; PiP does not choose another model for an attachment. Opening the pending-memory sheet uses the private PiP ID even on Home. Panel cleanup restores focus only if it is still in the outgoing panel or on the body, not when a destination sheet already took it.

**PiP resize (`pip-window.js`).** Resize uses pointer capture on the same edge/corner zones for mouse and touch, at widths of 768px and above. The preferred size is local to the account/browser; CSS clamps it to the viewport without overwriting it.

**Extensions' browser modules (`extension-ui.js`).** `hello` lists the browser modules a person's tabs load (`server.ui`: each module's name, title, and address, with its version in it). The tab imports each, and imports it again when its address changes: the server sends `hello` again when a browser module comes, goes, changes who it is for, or one of the files it serves changes (`ExtensionWebs` watches its folders), and when its module's new version installs other tools. A reload that leaves all that as it was leaves the address as it was, so tabs keep the browser module they loaded (they may hear `hello` again for other reasons). Event streams and poll queues cut off a tab more than 8 MB behind that took nothing for 30 s, or any tab 128 MB behind (`http/events.ts`); it connects again and gets a full view. A large first view is no reason: the tab has had no time to take it. A polling tab with an answer on its way is taking it until it polls again (one that never does ends 60 s after its last poll or answer), and a stream's ping checks too, so a stalled tab is cut off with no new events for it. A browser module is meant to add only through `pocket` (it runs in the page, so nothing stops it from more), and one that throws is caught there: its notice, its row in the Extensions sheet, its page's error box. One that failed stays listed (`dead`) but adds nothing more, until its module installs other tools: then the tab loads it again, as it may have failed on a tool the server did not have yet. Its events come as `ext` (`{ module, event, data }`). How a module's tools' calls show (`pocket.toolCall`) reaches `calls.js` and `turns.js` through setters, as they import nothing. Each `ui` entry lists the tools its module installs (from the loader), and a module describes only those; what a describer gives is used only when it is text. When a module goes, `sheets.js` takes its sheets out of the ones back would bring back (`onExtensionsGone`). A tab in safe mode (`?noext=1`, kept as `pocket.noext` in session storage) loads none of them.

**Contracts with the server.**

- Event names and shapes (`hello`, `view`, `chat`, `peek`, `subagents`, `ext`, …) and the sheet types the server names (`sheet: "chat"`).
- Queued input edits use `edit-queued` with the submission ID, new text and expected previous text. The server checks access and edits `pi.inbox` in one commit, retaining the submission, order, mode and non-text content. A boundary that already placed the message or a conflicting edit rejects the save. The composer keeps edits separate from its persisted draft and restores that draft after saving or cancelling. Queue disclosure is local UI state; collapsing the list does not pause or change pending submissions.
- The `pocket.*` keys in local and session storage.
- Extensions' API: `web` on the server and `pocket` in the browser, at `POCKET_API`. Modules outside this repository depend on them: add to them freely, and change what they do only with a new version.
- `ATTACHMENTS_HEADING` and `splitAttachments` (which also reads the form sent before 0.14.0), which `ui.js` repeats from `entry-format.ts`.

## Quick file edits and language servers

The file viewer loads CodeMirror only on **Edit**. `http/editor-assets.ts` bundles the installed editor packages once in memory (invalidated by entry or lockfile changes); the ordinary app still has no build step or CDN dependency. `file-editor.js` uses CodeMirror's official LSP client, not a second completion or diagnostics implementation. Unsaved drafts stay in the current tab's session storage and survive Back and web reloads; Cancel discards them and Save removes them. Editing uses the viewer's bounded flex height so only CodeMirror scrolls. The footer holds save state and clickable keyboard shortcuts. Escape consumed by the editor or its status menu does not close the enclosing sheet.

`workspace.saveFile` checks steering, turns, busy state and canonical path access. Complete UTF-8 files up to the viewer's byte limit carry a hash of their original bytes. `file-edits.ts` serializes saves per canonical path, rejects stale revisions and replaces the file atomically after rechecking its identity and bytes. App state and Pi's settings are not writable through this route. Save informs Pi and the people in the conversation; it does not submit model work.

`LanguageServices` binds opaque document leases to the owner, conversation and original working directory. It rechecks access and paths on every message/poll. `LspPool` lazily initializes one owned server per canonical project root and server type. Git projects use their checkout root, keeping worktrees separate. The bundled TypeScript/JavaScript server is the pinned TypeScript 7 Go-native preview (`tsgo --lsp --stdio`); other supported servers are fixed executables on PATH, not commands read from a browser or project file. `vscode-jsonrpc` owns stdio framing. Browser request IDs and responses remain isolated, and a document has one unsaved-buffer lease at a time.

`file-lsp-status.js` uses the owner's `status` action to inspect the live pool. `LspPool.status()` returns named starting/running/idle servers with opaque IDs, projects and document counts, without spawning, recycling or renewing leases. The menu refreshes only while open, uses the shared Back stack and closes independently of the editor.

Lease heartbeats, expiry, idle recycling and bounded queues keep abandoned editors from retaining servers forever. App shutdown closes the pool and terminates only its own children. Language services never write files or execute browser-provided commands; formatting edits only the browser buffer. A missing, busy or failed server falls back to ordinary editing. This is quick editing, not a multi-file IDE or collaborative buffer.

## Browser application selection

Clean sessions use an installed desktop/PATH browser before a cached Playwright Chromium download. Coop does not require another Chrome installation or download one automatically. The cache is only a fallback and must contain a download-completion marker and an executable browser in a recognized layout for the current platform. An explicit `PI_POCKET_BROWSER` takes precedence; an invalid explicit path does not silently select another browser. Imported defaults continue to use their source browser executable for native credentials.

Separate profile directories do not give headless and desktop Chrome separate macOS application identities. A Dock launch activating the headless process without opening a visible window is one possible explanation for the reported opening problem, but it has not been confirmed. Keeping installed Chrome preferred is not a demonstrated fix for that symptom. A manual diagnostic using the same installation is `open -n -a "Google Chrome"`: Apple's `open(1)` documents `-n` as opening a new instance even if one is already running. Coop does not run this against the owner's personal profile. Whether it opens the usual window, and whether subsequent Dock launches work normally, still needs to be checked.

Discovery does not alter personal profiles, the Chrome app bundle, LaunchServices registration, localhost access or workflow permissions. The executable is cached by the running browser manager, so changed discovery code requires a server restart before it applies.

## Imported browser defaults

`Browsers.profiles` discovers local Chromium-family profiles for the owner through `/api/browser-profiles`. Discovery reads profile metadata only; an opaque selection ID, not a client-selected import path, identifies the source. Custom discovery accepts a server-local profile path and the executable for that browser. Import requires explicit app-wide confirmation, refuses an in-use source and copies into a private, app-owned directory before atomically selecting it. Source profiles are never launched or modified. Caches, passwords, autofill, extensions and restored tabs are excluded.

The clean default retains temporary, isolated contexts. An imported default instead uses the copied profile's persistent default context with the source browser executable and native OS credential storage. Every conversation shares its cookies and site storage; existing Browser-panel access checks still apply. `Browsers` supplies the app's authentication-cookie name from `auth.ts` to Chromium's launch-time cookie stripping. The launch promise does not resolve until these cookies are removed from the copied default context, so even simultaneous page openings cannot inherit the owner's app sign-in. The Settings panel warns about this account access before import. Popup routing in that shared context requires the conversation page's opener ID, so opening another conversation cannot capture or close its tab.

A switch serializes against other switches and page openings, closes app-browser pages and gracefully stops Chromium before changing the selection. Shutdown asks Chromium to flush persistent storage. A retained stopping promise prevents another writer from launching until the old process exits, and target/close callbacks ignore replaced browser generations. Failed target attachment also closes its unclaimed persistent target. Returning to clean sessions deselects the import without deleting the copy. Firefox/Safari profiles are not directly compatible. Import currently supports macOS and Linux, not Windows (no reliable closed-source check yet) or Snap executables (cannot use the private import directory). OS-encrypted or site-bound logins may require signing in again.

## Checking a change

- **Every change:** `npm run check` (types, and no unused imports or locals in the TypeScript), `npm run lint`, and `npm test`.
- **Server:** the tests drive a real `PocketApp` with a scripted model, a restart included (`openApp` on the same folder). The built-in browser and peek tiles also run in a real Chromium where one is installed.
- **Web:**
    - `node --check` each file you edit.
    - Then open the app and use what you changed, with the console open.
    - A change that moves code between modules is a move only when the moved code is the same and the loading order above is kept.
