# Architecture

How Pi Coop's parts depend on each other, and the orderings the code relies on. [map.md](map.md) says where things are; this says what to keep when changing them.

## Durable truth and what memory keeps

Pi Durable owns the lasting state of conversations: conversations, entries, tasks, and Pi Pocket's documents (`docs.ts`), in `pocket.sqlite`. People and settings, push subscriptions, uploads, and worktrees are files beside it ([map.md](map.md#data-pi-durable-app-or-pi_pocket_dir)). What `PocketApp` keeps in memory about conversations is read back from storage:

- At startup, `#recover` reads each conversation's run, agent, chat, subagents, and who Pi works for in it.
- After that, every commit goes through `#committed`, which keeps the memory up to date.

Current-only app documents opt into `doc-checkpoint.ts`'s periodic bases. After 64 stored deltas, the next changing write stores a new base and Durable prunes earlier revisions. Existing long tails compact on their next change, not at startup. Document kinds, versions, scope, history and fork settings stay unchanged; this bounds replay work, not document size or family-member count.

Some state lives in this process alone, and a restart forgets it. For example:

- who is connected, typing, or away;
- which tool calls wait for approval;
- the browser's pages;
- when each run ended, which peek tiles and session-list squares use, and whether its last run failed;
- provider sign-ins in progress.

## Project organization

Projects live in the session-scoped `pocket.projects` document and directly contain threads and Work Items. Typed-thread membership remains additive catalogue metadata in `pocket.sessions`; it does not change the conversation/task ownership tree. `app.projects` owns validation, filtered projections and independent project placement. Startup durably marks ordinary legacy threads without a type as Worker and untyped linked roots as independent Chats; explicit types remain unchanged. New linked roots are Chats and inherit their source’s project, pinned destination and owner-only restriction, never its Work Item membership or Durable parentage. Project cwd is a creation-time default, not live inheritance. The additive owner-private `defaultAgentId` selects a named identity for new Home drafts; it is validated against the current owner's identities and grants no access. `web/home.js` composes native project filters/forms, workspace/session controls and `agent-drafts.js`, rather than owning a parallel chat model. `web/store.js` routes New Session to Home and projects to `/projects/:id`; a project route opens no conversation. `web/project-view.js` combines filtered ordinary sessions with each owner-private named Chat's exact `projectId`, never the identity's remit. `web/project-groups.js` nests owned work using the passive owner-private `groupingParentChatId` catalogue field, separately from the live `supervisor.parentChatId` authority projection. Stop/finish can remove live activity without erasing accepted ownership. Chats appear once in their actual project; explicitly moved work retains its own placement without duplicate Chat references. Recent and Archived include saved private Chats only for their owner.

The commit coordinator adopts project changes into the module's cache synchronously, then the same coalesced session-list pass sends a filtered `projects` event to each tab. Session changes also refresh that projection, keeping scoped catalogue membership and scoped project visibility current. Initial connection and access refresh send it too. Project documents and creation receipts are not room documents. New UI is gated by `hello.server.projects >= 1` until the server restarts.

`web/session-moves.js` routes native sidebar drags, touch drags admitted by the row hold chooser, and the touch/keyboard picker through the existing session metadata action. Only a drag originating in that list is accepted, and destinations are a project or No project. Hover timers and edge scrolling live only while the drag does. The original native source retains its own `dragend` listener, so cancellation still cleans up after hovering between tabs detaches the Preact row. Initial feedback waits one animation frame for the browser to capture its drag preview. Multi-row placement uses one transaction per independent thread or whole Work Item, with explicit partial failure reporting across those targets, not a bulk atomic edit; no client-side optimistic membership is published. Thread type, archive state, directory and access remain untouched.

`web/session-hold.js` owns a thread’s initial hold and fresh slide-to-choose gate, expansion/fill dwell, early release and contact cancellation. Activated touch drags transfer to the list-level drag owner so switching sidebar tabs can detach the source without losing release/cancel handling. `web/sidebar-context.js` owns scoped right-click/Context Menu/Shift+F10 access and project-header touch holds; native thread callouts cannot bypass the chooser. `web/sheets/sidebar-options.js` invokes existing actions against the selected catalogue ID, independent of the open conversation, in a bounded desktop menu or touch bottom sheet. Thread Options retains its source drawer so Select still targets that list. A held contact remains consumed through release and compatibility click even after catalogue-driven row removal. It uses the existing sheets Back stack, restores keyboard focus, and adds no server/storage path. Replies, files, diffs, text fields and terminal gestures remain unchanged.

Sidebar type indicators share `web/thread-type.js` with the labeled conversation-header tags. The access-filtered `app.sessions()` projection reads each visible session's current checkout HEAD through the existing cached `app.workspace.head()` lookup; this branch/short-commit context is derived, not stored catalogue metadata. When an open room detects a HEAD change, including a terminal checkout while idle, it schedules the same coalesced catalogue refresh so sidebar clients receive the new context too. `web/sessions.js` displays it with the path on standalone rows and grouped Work Item headers, while member rows stay compact.

`project-access.ts` validates additive owner-authored `projectAccess` selectors (`all`, `local`, exact SSH `hosts`, opaque `projectIds`). New collaborator invitations always persist an explicit grant, defaulting to `{}`; absence retains legacy stored scope. Broad grants include future matching projects. `Projects.canAccess` reloads current identity and grants; `PocketApp.canSee` combines project access with existing single-session and owner-only rules, and machine/local grants also check a thread's actual namespace. All-project access excludes unassigned conversations. Only the owner edits projects, moves membership, browses arbitrary directories or chooses new destinations. Collaborator creation accepts only a granted project's exact saved host/cwd, without worktree overrides. It does not prepare an arbitrary target or read remote model defaults. Viewers still cannot create or steer. Config grant changes and project/catalogue commits evict now-hidden rooms and peeks before later updates; projections, requester snapshots and environment/read cache identities include project grants. Normal permitted project code is trusted account-level execution, not a project filesystem jail.

Thread creation commits its project placement and creation retry receipt with the new conversation. There is no project-goal layer or background project-goal naming task. The separate `/until` completion-check feature remains unchanged. See [projects.md](projects.md).

## SSH file namespaces

`SessionMeta.location` and a project’s optional default location are additive catalogue metadata, never inferred from cwd. Absence means the Coop host. Thread creation pins the resolved target alongside cwd, includes it in retry identity, and rechecks project defaults before committing. Project moves/default edits do not reconfigure threads. Project directory preparation runs outside Durable’s global mutation line; the final transaction rechecks the caller, retry receipt and captured defaults before publishing them. Locally running subagents resolve their root thread’s target; linked roots and forks copy it. Human environment caches include conversation, location, cwd, token and role/session/project scope.

`app.sshSessions` owns authorized host discovery, exact-person/token/host password capabilities, arbitrary-destination preparation, pinned workspace operations, remote resources/trust and shutdown. Its `ssh-sessions/` modules own authentication, guarded backend assembly, operation cancellation/joining and resource policy. `withWorkspace` captures the caller and destination, supplies a guarded backend, owns the compound-read lifetime, reauthorizes the result and joins cleanup; callers do not receive a raw SSH environment or confinement escape. Shutdown revokes credentials, cancels and joins pending operations/logins, then cleans environments. The `ExecutionEnv` factory selects local workflow execution or a guarded SSH capability, wrapped by one shared live policy decorator. Human Files/shell operations bind the actual requester and token; agent operations resolve live attribution. Credential selection never borrows another person’s last turn merely because a thread is shared. An explicit project grant may delegate the owner's current exact-host password capability only to an actual visible thread at its pinned host/cwd/membership. The service captures and rechecks that owner's token and selected credential alongside the requester grant, including before streamed output and command/native-read results; no guest receives credentials, handles or authentication status. Arbitrary preparation/discovery/authentication/trust remains owner-only, and legacy implicit scope or session-only access does not delegate passwords. Human capabilities snapshot role/session/project scope as well as token: changes invalidate in-flight results and require a fresh request even when thread visibility remains. The decorator checks authority before and after awaited operations, and direct human SFTP environments also check at packet dispatch before effects and after responses. The decorator rechecks roles, access, writer ownership and workflow/publication locks for cached environments too. Managed SSH enters a sanitized fixed supervisor and target-native `sandbox-exec`; workload environment variables are installed beneath confinement. Unsupported confinement fails that command without unrestricted retry. Local seatbelt around SSH is not a remote boundary. Message-box shell uses the same destination factory.

`SshExecutionEnv.absolutePath` resolves already-absolute paths and paths under an absolute cwd lexically, without opening SSH. Compound Files, folder and review reads use a lazy request-scoped SFTP session through `withSshFileSystem`: readers release handles without closing the shared transport, borrowing the transport rechecks the live password capability, cancellation closes the session, and the outer callback always closes it. Open handles retain their per-call cancellation checks. There is no retained connection pool or cross-person credential/session sharing. Identical pending mention/Changes reads may share one aggregate operation only for the exact caller/token/role/scope, thread and pinned destination/cwd. Each consumer independently cancels and reauthorizes; the last departing consumer cancels and joins the aggregate. Remote mention names have a bounded five-second freshness cache, with fresh canonical-root/type validation before reuse; canonical-path results and file contents are not cached across operations. Existing per-user password lifetimes remain unchanged.

`WorkspaceBackend` binds canonical filesystem operations and bounded byte-safe Git to that destination. Ordinary UI operations reserve the live writer; trusted Pull/publication staging already owns the whole-item lock and must not reserve a competing writer. Git stdout uses validated base64 framing over the text transport, and text consumers reject malformed UTF-8 paths. Checkout fingerprints include destination identity, canonical cwd/root, HEAD/index/status, physical file bytes/modes and raw symlink targets. Worktrees, Changes, branches and review anchors reuse these capabilities, not parallel host-local fallbacks. Remote worktrees carry additive destination identity and use private persistent target storage.

`ssh-hosts.ts` passively reads bounded concrete aliases from the host’s user SSH configuration and Include files, and remembered host names from `known_hosts`. Owner-only `GET /api/ssh-hosts` returns uncached destination suggestions and rechecks authentication after scanning; it exposes no keys or configuration directives. Saved nonstandard ports use native SSH URIs, preserved intact through metadata, commands and SFTP. Hashed names and marked/revoked entries are skipped; saved login usernames cannot be inferred. Discovery never invokes SSH, evaluates `Match exec`/proxy commands, probes machines or inspects live terminal sessions. The existing location picker keeps manual host entry usable during discovery and failures. `workspace-field.js` mounts location/authentication controls only behind Change, and mounts the folder browser only after Browse. `ssh-status.js` records bounded, short-lived, current-user browser evidence from explicit filesystem reads or verified password login, never host discovery, cached credentials or project-list probes; the same remote/status marker appears in project picking and all Collab sidebars.

Owner-only `GET/POST /api/ssh-auth` handles password status, login and forgetting over the authenticated API. Login requires HTTPS/localhost, a fresh owner/token check after body and probe I/O, and an actual password prompt plus successful SFTP probe. `ssh-passwords.ts` holds bounded, expiring memory-only capabilities keyed by person/token and exact target; no durable document contains a password or authentication handle. Each SSH child gets a private one-use FIFO and secret-free `ssh-askpass.ts` launcher. Only the authorized parent SSH PID can consume it. Passwords never appear in regular files, argv or environment values. Password-mode SSH disables control-master reuse, strictly checks known host keys and refuses non-password challenges. Logout, forgetting, expiry and shutdown wipe capabilities; cancellation during preparation cannot start a new SSH child. The capability-gated `web/ssh-login.js` is shared by existing destination/folder/thread-details flows; it clears the field before sending and never retries a login or mutation automatically. Login-status refresh uses a server-relative remaining lifetime, not the phone’s wall clock; hidden/offline/pagehide suspends requests and timers, and return performs one fresh status read.

OpenSSH carries ordinary noninteractive Bash and a byte-safe SFTP v3 subsystem; no remote agent/service/credential installation is involved. Per-operation connections and bounded paginated readers avoid a persistent remote helper. Remote HEAD refreshes require a visible actual reader; hiding or disconnecting the last such tab cancels pending HEAD work. Passive catalogue projections do not start it. Mutations/commands are not retried on ambiguous delivery. Cancellation requests remote process-group TERM/KILL and reports unconfirmed completion rather than promising durable jobs. Agent SFTP edits use optimistic conflict checks, not atomic CAS. Files quick edits instead require a native Python 3 snapshot/prepare/finalize protocol: coherent bytes/revision, no-follow identity checks, private transfer, metadata preservation, live human reauthorization and adjacent replacement. Eligible editable text uses the native snapshot directly, without first downloading the same bytes over SFTP; unsafe, binary or unsupported snapshots retain the ordinary read-only preview path. Missing native capabilities leave an explicitly noneditable preview; the final external rename race remains best-effort.

Remote context, Files, inline mentions and image reads use that namespace. Host-global instructions, skills, provider settings, memory storage and uploads stay local. Remote memory keys include SSH identity and normalized path rather than probing a matching local repository. `host_skill` reads bounded registered host resources; `stage_upload` copies only an explicitly selected thread attachment. Remote project resource trust is explicit host-owned state keyed by filesystem identity and canonical root; trusted remote skills/templates/default models never load host namesakes or remote credentials. Slash skills carry their bounded remote content into expansion. Resource discovery is bounded but does not yet match Pi ignore files. Hidden review context uses the native opened-snapshot boundary. Language services and watchers remain unsupported, not host namesake fallbacks.

External acquisition and publication stay on Coop. Pull fetches into sanitized host bare storage, transfers a capped bundle and explicit ref manifest, and imports remotely offline. Publication pins the target, checkpoint, commit, remote configuration and body-file bytes before exporting an offline snapshot to host staging. Approvals include host authentication configuration; execution retains durable receipts and uncertainty/reconciliation. Unsupported target hooks/configuration are rejected before approval, never silently reproduced or run online.

## Cross-thread handoffs

Work Items and Agent Teams are sibling consumers of core session machinery. `session-roots.ts` creates independent ownerless conversations, agent settings and catalogue entries inside each caller’s existing authority/receipt transaction. Linked peers inherit the source configuration; handoff successors inherit only cwd/model/thinking, never source instructions. `host.sessions.linked` is the sole public linked-peer path, while `host.sessions.handoff` derives authority from the actual tool invocation and placed human input. `app.workItems` owns the first-party lifecycle and handoff tool, independently of optional extensions. `app.piSessions` remains the local Pi history discovery/import module; it does not own work lifecycle.

The public `handoff` descriptor is shared by core and private selections. `work-items.ts` dispatches
from the actual source before taking the ordinary transfer lock: named main Chats use
`work-items/named-handoff.ts` with private native invocation/owner authority and the coding tool's
filesystem pin, native `Pip.start`, inert controller opening and an exact accepted controller send.
They are not retired or enrolled in execution membership. `work-items/controller-handoff.ts` retains
`orchestration.perform` and the private controller-transfer adapter, requiring an explicit expected
active execution source; its controller Chat stays independent. Native assignment receipts retain
accepted send identity for existing wait/continuation correlation. Exact existing recipients are
never silently retargeted. Status shares actor admission and reports actual refusal reasons. Stored
legacy adapters/selections remain replayable; new public session creation selects ordinary Chat.
Generic execution role/workflow prompts do not apply to private Chats. No document contracts change.

The disclosed Work Item creation panel reads only the current registered profiles. Its project default is the first
starter other than the core Chat profile. Work Items orders Worker before Researcher to preserve
its Worker default; core does not hardcode that workflow's profile names. Explicit ordinary Chat
remains independent of Work Items.

`app.workItems` owns the built-in catalog and declarative graph, cached workflow/group state, permission-filtered work views and receipts, active-writer ownership and whole-item organization. Projects and Commands use that interface rather than reading membership or expanding groups themselves. A private `Handoffs` engine retains durable transfer admission, tasks, recovery and atomic transactions, consulting the WorkItems catalog. Stored document/task names, versions, scopes, history/fork contracts and replay receipts do not change.

First-party Work Items is always installed and is not listed in Extensions. The owner pauses or resumes **Work Item execution** in Settings → **Agents**. The additive native `workItemsEnabled` setting takes precedence; when absent, the legacy disabled `work-items.ts` choice is read only as migration input, preserving a pause without silently resuming work. Explicit native changes persist `workItemsEnabled`; the extension-enablement endpoint cannot change WorkItems. Owner-only `POST /api/agents` accepts `{ workItemsEnabled: boolean }`, and `GET /api/agents` plus `hello` metadata expose effective state. Pausing does not unload profiles or controls. Non-Chat built-in starters and new built-in handoffs are unavailable, and new managed effects are blocked. Accepted legacy transfer recovery and passive receipt lookup remain installed, with live authorization checks; recovery does not bypass the execution pause. Ordinary ungrouped Chats and Agent Teams continue without Work Item membership. Owner prompt overrides and stable built-in IDs remain intact.

Third-party `web.workflow` declarations still follow the loader's staged lifecycle: failed/superseded loads cannot leak choices, replacement is atomic, and disabling removes that module's admissions and profile instructions. Namespaced profiles and graphs remain independent of the first-party pause. Missing managed/unknown profiles stay managed, block writes and receive unavailable-role guidance; they never become Chats. Accepted transfers retain access, spend, ownership and idle checks. Unavailable destination delivery keeps a durable blocked reason until its profile returns, using the same receipt.

WorkItems' browser assets live in `src/server/work-items/browser/`. Core registers `src/server/work-items` with client entry `browser` through the shared web registry, preserving `/x/work-items/…` asset URLs. There is no first-party Work Items entry or source module under `src/server/extensions/`. Its picker, inline controls, hints and styles intentionally reuse the generic public presentation infrastructure for compatibility; generic sidebar/Settings rendering stays in core. Static assets retain conversation access, and scoped `GET /api/c/:id/x/work-items/handoffs` and `POST /api/c/:id/x/work-items/work-item` retain request-bound WorkItems operations. Each request checks current source visibility and role after asynchronous body arrival. App-wide extension routes still exclude scoped invitees. Public `host.sessions.handoff`, `web.workflow`, scoped routes and browser controls remain supported; no internal browser imports or DOM patching are involved. Eligibility uses an initial/context-change read, with a shared 10-second interval only while a Picker is mounted; always-mounted controls do not admit polling. Opening, explicit Refresh and routing hints request fresh options. Semantic changes invalidate displayed hints and coalesce in-flight reads into a current result. Outside the Picker, unannounced filesystem/driver/task-only changes wait for the next relevant public event or explicit demand; server admission still rechecks authority.

`app.workItems` exposes state-based destinations and agent-executed handoffs without exposing the transfer engine. Humans request a handoff through an actual message, in English or with `/handoff`; commands no longer invoke a separate app-generated source-summary round trip. The agent infers a clear intended type or asks for clarification, then executes status/start with its brief. It cannot add readiness gates, autonomously advance or silently substitute an unrelated available role. Options depend on the active type, same-item history and existing diff; steering, visibility, driving, idleness and single-writer checks still apply. The header picker and message box share one human-input path. `src/server/work-items/browser/sheet.js` loads current eligibility for each opening, offers role selection followed by optional steering, and submits an explicit slash command via public `pocket.submit`. It closes on input acceptance without waiting for the agent's summary, and stays dismissible during a slow POST. Per-user/thread tab drafts preserve selection and steering; draft revisions and opening identity protect later edits and reopened sheets from delayed responses. `/handoff` argument completion loads current eligibility on entry and refreshes when busy state changes. The browser-local `commands.js` matches routing arguments without executing them or completing words in the human's instructions. `pocket.inputCommand` contributes those hints; generic `web/commands.js` and `web/composer.js` handle draft-only selection, keyboard completion and sending. Browser-local `state.js` shares in-flight eligibility reads across the picker, controls and hints with user/source fencing. Its polling and reads suspend while hidden/offline or after pagehide, aborting and fencing pending responses; visibility/online/pageshow resumes the current scope once. An open picker joins replacement reads after suspension or access-scope changes without losing its draft, including when hide and return are batched before rendering. Disposal removes its timer and lifecycle listeners. `pocket.sessionControl` supplies the header button and composer context; opening the picker starts no transfer. The picker consolidates repeated disabled-option reasons into one accessible warning without changing eligibility; unique destination reasons remain inline. The composer retains a Work Item status indicator without predecessor, source or active-thread navigation buttons; use the sidebar’s thread rows for navigation.

`src/server/handoff-input.ts` owns command routing and an opaque correlation derived from the real human submission identity. Slash-command type/relationship, when explicit, constrain the tool call; English intent is interpreted by the agent, not a keyword-based runtime gate. Tool execution resolves real human input in its current main run, excludes synthetic couriers, schedules and helper inputs, checks the allowed transition and live access/driver/ownership, then atomically creates the successor and receipt and retires the source. Only the tool's invocation/run and exact incoming placed courier are exempt from full task-graph idleness. Before successor admission, the tool writes the brief and exact human direction to a real `handoff.md` in a private temporary directory in the source/successor filesystem (on the target for SSH). The existing courier sends only a path/read instruction with application provenance; new records and recurring prompts do not duplicate the file body. Historical inline records retain their original delivery/request identities. There is no new file subsystem, model job or reader tool, and no fabricated source user message. The composer clears when the actual input is accepted, not after successor creation. `web/store.js` pins each outgoing payload's retry identity before transmission, retaining uncertain attempts for explicit retry without automatically replaying input. The authenticated `GET /api/c/:id/submit?requestId=…` route passively looks up only that person's accepted input, including after source retirement, and returns its opaque handoff correlation; missing input stays missing. Accepted correlations resolve a matching outgoing record on session updates/reload; recovery never redirects another viewer or a user who navigated away. Draft revisions prevent a delayed acknowledgement from clearing newer edits even if their text matches the submitted draft. Core `GET /api/c/:id/transfers` passively returns only the current person's accepted outgoing receipts from this exact source, including while Work Item execution is paused. Summary/delivery tasks remain registered solely for recovery of already-accepted data; there is no public summary-first admission or retry endpoint. A legacy summary-only request still forbids tools and further work. The goals extension pauses `/until` during those requests and on retired writers. The handoff tool exposes status/start, not prepare, complete, record-review or recommendation controls.

Same-work choices are Worker → Reviewer/Researcher, Reviewer → Follow-up/Worker/Land/Researcher, Land → Publish/Worker/Follow-up, Follow-up → Land/Worker, Researcher → Worker/Follow-up and Pull → Worker/Researcher/Follow-up. Publish is the delivery/end stage with no additional same-work edges to Worker or Follow-up. Pull is additionally available from any type except Pull itself. Land stays available after any earlier Reviewer in the same Work Item; Follow-up requires a Reviewer or Pull in that history, counting the source. No same-work transition repeats the current role. Worker → Reviewer also requires a nonempty current Pi diff (`Changes.files`); `Changes.piOnly` is historical edit attribution, not a current diff, and a new checkpoint alone does not qualify. From every active stage, Worker, Researcher and Pull are offered as new-work starters, including the current starter type because the destination belongs to a distinct Work Item. `/handoff worker` defaults to same-work; `/handoff worker --new`, `/handoff researcher --new` or `/handoff pull --new` selects new work. Remaining text after routing arguments is human direction. Server and browser source target the same current API without handoff-version flags or older-host fallback branches.

`src/server/work-item-profiles.ts` declares the built-in profile labels, playbooks, starter choices and transition graph used by WorkItems, separately from third-party `web.workflow` registration. `src/server/session-workflows.ts` validates immutable declarations. `src/server/thread-prompts.ts` retains only non-editable shared scope guidance and the unavailable-profile prompt. The non-toggleable core renders `thread_role` before every request from the owning root thread's committed type, including initial threads and inherited descendant helpers. Owner-edited `config.agentPrompts` override only that type's role instructions; missing entries use bundled defaults. `/api/agents` lists these instructions for the owner, and per-type saves validate length/content and the expected previous prompt before atomically persisting the merged configuration. Failed persistence restores the live configuration. Saving the bundled default removes the override. Shared scope guidance and hard execution/approval gates are not editable settings. Common prompt rules explicitly override saved legacy role instructions that prohibit executing human-requested handoffs, make the tool status-only, record readiness or require risk acceptance before Land. This per-agent system-prompt amendment is separate from `workflow` state and the user-message handoff brief; shared prompt sections and repository instructions remain loaded. Each successor has its own conversation/agent configuration: cwd/model/thinking choices may carry forward, but source-local `agent.instructions` do not. Custom instructions added to a destination belong only to that agent and persist across restart. Retired conversations keep their historical role while read-only workflow state overrides its working loop. Prompts guide iteration and validation scope; they do not replace the generation loop, plan/explicit goal hooks, or hard execution/approval gates. A handoff summary supplies context, not role authority or proof that checks passed.

A handoff successor is an independent user-facing conversation, not a task-owned subagent and not Durable's same-conversation reset/handoff. A durable background task delivers the received source summary with an attributed request ID. Restarted delivery finds the same submission. A model names the destination from that summary; its response memo prevents a completed naming response from being applied or billed twice. Usage, guarded naming and task settlement commit together, and a manual rename wins.

Work Items keep same-work successors together. The first same-work handoff creates membership lazily; standalone roots are not enrolled on creation or upgrade. WorkItems derives membership and placement from the source, and movement/archive/restore update all members together. Hidden members block whole-item mutations; grouping grants no access. Project reassignment changes organization only. Successors retain the source's pinned destination and normally its cwd, including new-work handoffs, and workspace/SSH modules retain destination access and execution checks. An explicit owner-only new-work `worktree: true` choice changes only the successor checkout on that same destination. `Handoffs` reserves stable coordinates before Git effects, reuses destination-aware Worktrees, holds the workflow exclusion lock, fingerprints source and target outside transactions and revalidates live admission before atomic transfer. Partial/uncertain setup is retained for reconciliation without retiring the source or allocating another checkout; defaults and legacy/controller recovery still inherit. See [optional handoff worktrees](handoffs.md#optional-handoff-worktrees). Existing document kind/scope/history/fork contracts stay unchanged.

Review evidence remains factual context. Reviewer independently assesses code/test quality and wider regressions; Follow-up makes bounded repairs following review or Pull, while Researcher separates sourced findings from hypotheses. Summaries retain actual checks/results, unavailable or deferred checks, provenance and material changes that make earlier evidence stale. Research findings and self-attestation are not independent review. Land admission has no review, readiness, checkpoint or risk-acceptance gate: choosing Land is not a claim that inspection or validation passed and does not authorize a commit, rebase or cleanup. Land performs only human-authorized local integration through ordinary offline bash/Git, including scoped commits, stash preservation/restoration, rebase and local main fast-forward. Settled Git exit/output, checkpoint and dirty-work preservation evidence are the local receipt; there is no second Land API/action or approval-receipt gate. Shared non-editable and controller guidance retain this distinction even with saved role overrides. Land reports cleanliness and impact checks. Publish follows Land for approved external delivery, including PR creation and ticket updates. Landed and published remain distinct facts.

Existing milestone fingerprints, `externalReview` source/findings/scope/checkpoint records, `reviewAssessment`, `reviewApplicability` and append-only `validationAcceptances` remain stored with their original identities and limitations. Historical acceptance records preserve who accepted which named gaps for which assessment/checkpoint; they do not turn failed checks into passes, approve publication or control thread creation. The first acceptance remains a durable historical decision, not a mutable readiness flag. Public projections continue to omit private submission/request IDs, raw external-review findings and inspected Git status. Obsolete completion, external-review intake and validation-acceptance writers and their core HTTP paths are removed; existing records remain historical evidence. Existing durable kind/version/scope/history/fork contracts do not change.

Execution restrictions are part of `pocket-core` and the conversation's environment. They cover direct filesystem methods, shell execution and inherited descendant capabilities, rather than relying on a model's instructions or the optional Lancet extension. Managed filesystem operations, writable shell children and mutating Browser-panel requests hold reservations through settlement; handoff, Pull, research and publication share a workflow lock that rejects existing reservations and excludes later writers. Panel mutations reserve before asynchronous admission/body handling and recheck current identity, visibility, steering, driving and active write ownership before effects, including after page creation. Passive state, frame and console reads do not reserve a writer. Fetch also checks `app.workItems`' full ownership/task graph while holding that lock, exempting its own main invocation/run and the exact incoming brief courier already placed into that run, before any Git inspection or external execution. Queued/unrelated deliveries and helper reporters remain blocking work. GitHub helper reads do not use that idle gate. The offline ref import rejects symbolic destinations for the staged branch names, including dangling/chained symbols and remote branches named `HEAD`. It also refuses checkout URL rewrites of the staging import path so an unchecked file remote cannot replace the inspected source. Managed shell distinguishes known local Git operations (including `stash push` and `rebase`) from publication after parsing supported global options and plain command boundaries. In that parsed subset, direct `git commit` message operands and verified `rg`/`grep` search operands are data, not nested commands. Commit-message exemptions support only known non-editing options and no pipelines; compound lists must contain only verified inspection or bounded local-integration commands. An editor or later interpreter can execute the message file, and a consumer can execute the printed subject. Search exemptions require a single invocation or a wholly verified inspection command list, so a pipeline into an interpreter stays conservative. Nested shell/configuration/script text is still inspected; unknown Git operations/options and unsupported shell syntax (including substitutions and redirects) retain conservative lexical publication refusal and can still reject literal prose or local `stash push` in an embedded program. The classifier preserves whether refusal came from an operation in a known executable position or conservative token matching in opaque arguments, nested text or unsupported syntax, so the production environment can explain the latter without claiming that publication ran or Git reported a conflict. The accepted/blocked command set is unchanged; supported standalone Git commands are the normal local-integration form, not an interpreter/heredoc exemption. These narrow exemptions do not imply a full shell parser. This is not a general shell interpreter or a hostile-code filesystem sandbox. Publication uses a separate exact-command approval path from the active Publish thread after Land. Admission inspects the current clean Publish checkout rather than an inherited `ready` milestone. Each action pins the actual content/checkpoint and executable inputs and needs its own human approval; changed inputs need fresh authorization. Its intent and approver are stored before external execution; an interrupted external effect remains uncertain, never automatically replayed. Thread creation cannot approve any action.

Worker keeps research, optional planning and implementation in its existing thread. Researcher can start a new Work Item or investigate a pointed question mid-work, producing cited findings and application guidance without implementing the feature. Humans may choose Worker to apply research-only evidence or Follow-up for bounded repairs when same-item history permits it. `workflow-research.ts` grants active Worker/Researcher/Follow-up roots and helpers bounded public-document reads and isolated shallow GitHub snapshots without updating working refs. `public-read.ts` validates/pins public IPv4 HTTPS destinations with redirect, time and size bounds; `browser/page.ts` uses it to render semantic-only evidence in temporary contexts with browser networking and scripts disabled. These pages never inherit imported browser accounts. Reader downloads are cancelled when superseded, stopped or closed. Cancelling a saved-address restoration stops its download only when no waiting caller still needs it; another caller's shared page remains open. Reader writes are serialized, and a cancelled dispatched write restores the last committed document before a replacement can render, so stale content cannot overwrite newer evidence. Plan mode permits research reads/clones but still blocks working-checkout writes and research cleanup. General research does not change Pull's ref-integration adapter or Publish's approval gates.

## Comment-first code reviews

`app.reviews` stores discussion alongside the session's current Changes. A first comment makes its author a reviewer; there is no create, assignment, snapshot, verdict or close step. Every person who can see the conversation, including a viewer and the owner, can comment on all changes, a file or an old/new line or inclusive range, and reply. Pi activity never blocks discussion. Comments retain their original line context rather than claiming a stable checkout; ordinary composers show no routine busy, range-limit or invocation instructions.

Review metadata is a separate conversation-scoped, latest-history, initial-fork document. `Room.reviews` projects `{threads, rev}`, not retry receipts. Forks start with no comments. The former round and snapshot document kinds stay registered with their original settings but are no longer read or projected; their data is not migrated.

`GET /api/c/:id/reviews/changes` and `/reviews/diff?path=…` expose read-only changes inside the session's working folder to visible participants. A single diff validates its own current Git status/prefix and captured checkout root, with fresh pre/post path-scope checks; it does not rebuild line counts, attribution or file versions for unrelated changes. `/reviews/context?path=…` supplies bounded, complete text for unchanged lines in a currently changed file, so viewers can expand context and see comments on those lines inline too. These routes do not grant viewers access to the generic workspace/file/editor routes, unchanged files, or files elsewhere in an enclosing repository. Context reads reject binary, oversized and unsafe files and recheck membership, folder and file identity. Comments keep Git paths exactly, including spaces, and a working-folder identity. A changed or missing anchor remains accessible as outdated discussion instead of being silently attached to a different line.

`POST /reviews/comment` creates a thread or reply. `POST /reviews/resolve` resolves or reopens an explicit set of thread IDs atomically: the owner can handle anyone's threads, and other people can handle only their own. Mutations recheck current membership, record server-authored identity, enforce bounds and use durable request receipts. Resolving never deletes discussion or rewrites its authorship. These discussion routes never edit files or commit Git. An explicit human `@PiP` mention can admit an independent, work-scoped answer under the existing steering, turn and spend permissions.

Review composers share `mention-composer.js` with side chat: caret-aware human/PiP choices, keyboard/IME handling and posted mention highlighting. The DOM-free `pip-mention-text.js` owns the same literal-mention grammar for server admission and rendering, reusing `marked` tokens with original source offsets. Quoted, indented/fenced code and multiline inline code cannot become invocations; message ingestion and review submission preserve leading Markdown indentation. Human choices remain available to viewers; PiP choices keep the existing steering/pause rules.

Inclusive ranges are selected directly in the diff gutter: mouse drag, Shift-click, or touch hold-and-drag on phone and tablet widths; endpoint taps remain an alternative. Touch motion before the stationary hold keeps native scrolling, and multi-touch/cancellation/blur discard the preview. Touch listeners block movement only on the originating gutter control after selection intent; pinch zoom and surrounding scrolling remain native. Gesture-only global listeners are removed on settlement. The composer displays the selected location, not numeric range inputs or duplicate evidence/help panels. Selection stays on one file/side; pointer cancellation and window blur discard drag previews. A range contains at most 100 inclusive lines and 8,000 characters of complete captured evidence, including omitted unchanged lines read through the scoped context route. Missing or excessive evidence disables submission rather than clipping it. Single-line requests keep their existing 1,000-character limit and omit `startLine`. Endpoint drafts and uncertain retry identities survive reopening the composer; changed ranges receive new request identities. Displayed diff, context reads and Reviewer evidence use the same CRLF normalization.

`web/reviews.js` groups threads by their original author and derives each person's open/resolved status. Its sticky, collapsible reviewer index shows avatars and the owner's badge, navigates to inline comments, and offers reply/resolve icons. Selecting comments reveals a single bulk-resolution check button. People status links open Changes, expand the selected reviewer and highlight the item. Stored line/range discussions highlight every validated inclusive line and its gutter in unified and split diffs, independently of the composing selection, with the comment below the end line. Omitted unchanged range lines are revealed without drawing unrelated gaps; outdated ranges never highlight replacement code. File discussions render below the filename. Comment composers keep post/cancel icons inside the input. Explicit bot buttons send attributed feedback for one reviewer or all reviewers through the ordinary submission route, without changing the main composer draft. These sends use captured conversation IDs and durable retry IDs, require steering and driving rights, and queue a follow-up while Pi is busy. Posting or resolving comments alone never starts Pi. New review controls require `server.localReviews >= 2`; old servers keep ordinary steering-only Changes until restarted.

## Pi provider compatibility

The owner-selected, restart-only compatibility module is a virtual Extensions row (`pi-providers.ts`), not a watched built-in. `ProviderPackages` resolves installed package metadata through Pi's public package SDK without executing it, stages exact npm releases with scripts disabled in separate Coop-owned trees, and stores requested versus applied selections. ## Who owns what

`PocketApp` (`app.ts`) creates the app's parts and hands each one the app.

**Its parts:**

- `commands`, `extensionCommands`, `collab`, `alerts`, `providers`, `schedules`, `goals`, `shell`, `spend`
- `workspace`, `transcripts`, `attribution`, `piSessions`, `sshSessions`, `pip`, `watches`, `hooks`, `memory`, `gallery`, `reviews`, `projects`, `workItems`
- `browsers`, `linkedSessions`, `languages`, `providerPackages`, `providerExtensions`

**What stays on `PocketApp`** (the parts call these rather than keeping copies):

- **The conversation tree:** `rootOf`, `parentOf`, `conversationsOf`.
- **Where a conversation works:** `cwdOf`, `agentState`, `sessionMeta`, `isBusy`.

- **Tabs and peek tiles:** `attach`, `detach`, `setPeeks`.
- **The app's lifecycle:** `open` and `close`.

The harness, models, and settings exist only once `#open` has set them up, after the parts are made. So a part made with the app must not read them in its constructor; it reads them when it is called.

Extensions never see `PocketApp`. They get `PocketHost` (`host.ts`), whose functions call into the app lazily, and `web`, through which they add routes and a browser module to the app. `ExtensionWebs` (`extension-web.ts`) keeps what each module's version added, which the loader commits once the module installed and removes with it, running its cleanups. The HTTP layer parses a request, checks it, calls a part, and writes the answer; it holds no state of its own beyond invites and the event streams' pollers.

## Linked sessions

`LinkedSessions` (`linked-sessions.ts`, `app.linkedSessions`, `host.sessions.linked` as `LinkedSessionsApi`) starts a session from another and carries messages between them; Agent Teams (`extensions/agent-teams.ts`, off by default) is its only user. A linked session is an ordinary ownerless session in the source's folder. Its session entry's `linkedFrom` names the session that started it, and nothing else follows from it: it is not in `SubagentsDoc`, `parentOf`, or `rootOf`, so it gives no access, and stopping or archiving one leaves the other as it was.

- **Whom it acts for.** Each call acts as the person Pi works for in the source (`requesterOf`), with their checks: seeing the source, steering, the turn, spend, and, to start one, no single-session restriction. Project collaborators inherit the visible source's project and pinned destination. The source in plan mode starts and sends nothing. A message goes through `Commands.submit` as sent for that person (a `p:` request id), with `[via linked session …]` and the message fenced (`defang`), so its text is never a slash command and Pi reads it as a request; the target's checks apply there too. The transcript knows such a message by that label and fence, not by the words before the fence.
- **Once.** Each call's key is hashed with the source into an item of `LinkedSessionCallsDoc` (`pocket.linked-session-calls`), which records the session it made or messaged, whom it acted for, and when. A start writes it in the same commit as the session, then sends the first message; a message's request id is made from the same hash, so a replay finds the session and the message it made. Records are kept 30 days, and the newest 1000.
- **Bounds.** A linked session starts none, and a session starts at most 10 (counted in the commit that makes one). `LinkedSessionRelayDoc` (`pocket.linked-session-relay`) on the team's top session counts messages between its sessions; past 20, sends are refused, and a person's own message in any of them (`Commands.submit` without a `via`) sets it back to 0. It is counted in a commit before each message goes, so it survives a restart. `Spend` counts a team against its top session's budget: the top session, every session linked under it, and their subagents.
- **What it shows.** Sessions know each other by addresses of their own (`LinkedSessionPeersDoc`, `pocket.linked-session-peers`), so no session id goes into a shared transcript; a fork starts with none. `list` reaches only the sessions the person sees, and names them only when everyone who sees the source sees them too. The session list (`PocketApp.sessions`) gives someone who cannot see the origin `linkedOrigin: true` in place of `linkedFrom`; a scoped person's tabs get their own list in every broadcast, not a filter of everyone's.
- **Models.** A start copies the source's agent settings (model, thinking, instructions, tools), not its history. It takes only the source's model or an entry in the shared `subagentModels` list; an empty list means source-model only for linked sessions. Thinking is capped at the source's level and fitted at or below that cap, unlike background subagents' nearest-supported fitting. `Providers.problem` asks its provider afresh: nothing is made with a model that is not allowed or cannot be used now.

Subagents leave Agent Teams out of every subagent (`extensions/subagents.ts`), even while it is off, so turning it on later gives no subagent a way to start sessions.

## Private failure diagnostics

`app.diagnostics` owns three passive tools for the current owner's **global private PiP**:
`collab_status`, `collab_failures` and `collab_trace`. Every read checks the actual private
conversation and running tool task, captures the owner's token, resolves authorized execution
membership before storage reads, and rechecks ownership, token, PiP availability and membership
across awaits. Named private agents, shared agents, shared mentions, helpers and Work Item controllers
cannot use this reader, even if a tool registration is copied into their selection. Owner scope is explicit;
session, Work Item and project scopes exclude all private PiP and hidden mention conversations.
No HTTP route, shared event or public extension-host database capability is added.

`diagnostics/runtime.ts` decorates the registry's read side, preserving task definitions' stored
names, versions, checkpoints and replay rules. Its invocation context correlates phase, hook,
environment construction, tool execution and nested codemode observations. Workspace method
observations retain local/SSH identity but no host, path or command. The existing model-stream
wrapper records provider/model response outcomes in this context. Successful execution is not a
claim that a test passed or a task achieved its goal. Returned tool errors, thrown failures,
intentional blocks, cancellation, interruption and unknown causes stay distinct. Structural codes
are used where available; free-form errors are not mined for signatures. Task phases, executions,
receipts and child operations are separate populations, never summed into an alleged call count.
The commit coordinator also captures native tool, terminal-task and input-settlement receipts;
imported tool history without native task attribution is excluded. Receipt status/reason is separate
from operation identity, so completed and failed receipts have the same population denominator.
A terminal task marked failed does not establish a domain or infrastructure cause by itself.
Codemode validation rejected before any hook/execute wrapper is not independently captured;
environment reader-handle methods and watcher callbacks are also outside coverage. These gaps
are disclosed in query results rather than treated as zero failures.

Capture retains only identifiers, controlled categories, timestamps, outcomes and evidence links,
not prompts, reasoning, arguments/results, environment variables, credentials or exception text.
Unavailable tool names emitted by a model are not trusted registration metadata and are replaced
with a controlled label, not retained as arbitrary identifiers.
A best-effort queue holds at most 1,024 observations, coalesces start/end writes by observation ID,
and upserts into the new conversation-scoped `pocket.diagnostics` document. This document keeps
256 observations, uses latest history with initial-fork semantics and periodic checkpoints, and
is not a room document. Observer write failures are counted in process memory and do not fail or
repeat business work. Records not written before a crash/storage failure cannot be recovered;
shutdown drains capture before closing Harness, so final interruptions may remain unobserved.
There is no historical backfill, database/SQL tool, external exporter, repair or notification loop.

Queries scan at most 1,000 cached catalogue/membership entries, then read at most three journals
(768 retained observations) per page. Status additionally reads at most 24 tasks per nonterminal
state per selected conversation, outside aggregation; only whitelisted task metadata is extracted.
The installed storage adapter still materializes selected task records, so this is not a hard bound
on underlying database I/O for unusually large stored inputs. Output is bounded to 32 KiB with
explicit omitted-row counts, and reads have a five-second cancellation deadline. Cursors are
bounded, expiring, process-local and bound to the owner token, caller, scope and membership;
pages read current state, not one frozen multi-page snapshot. Scope truncation, missing journals,
eviction, unfinished observations, pending/failed observer writes and output omissions are exposed.
Failures group by controlled component/stage/operation/cause, with per-population observed
success/finished denominators, logical IDs when known, and first/last retained sightings. A later
observed success in an affected session is evidence of recovery at that operation only, not proof
of repair. No recent failure, idleness or a completed task is a health/correctness certificate.
Historical active runtime, provider-side retries, complete usage/accounting, retrospective exact
attempt counts and notifications remain outside this diagnostic slice.

## Work from outside the app

A PR watch (`watches.ts`) is a `WatchDoc` in its session and a durable task there, which sleeps until its next look, looks with `gh` (`watches.gh`, which tests replace), and puts what to tell Pi in its checkpoint before sending it: the send's request id is the watch's task and count, so a restart sends it once. Comment ids told, and the commits whose failures and conflicts were told, stay in the watch. Webhooks (`hooks.ts`) are app-wide (`HooksDoc`); `/hook/…` is outside `/api` and its sign-in, and lets a post in only by its hook's secret. Both send through `Commands.submit` as their person, with a `via` that marks the message (`[via PR watch]`, `[via webhook NAME]`), so that person's checks and spend limit apply, and what came from outside is fenced (`fence.ts`, as PiP's session text is): no closing tag survives inside, in any case or spacing. A hook's address and secret are checked before its body is read. A signed hook (`signed`, for GitHub) lets a post in only by GitHub's signature: its secret is never in its address, so the address GitHub shows a repository's admins cannot post. Pi's `watch_pr` names a PR by number, which `gh` finds in the session's own repository, or one elsewhere by address only where `gh`'s account can push (`requirePush` in `github.ts`); what follows `--` is never an option.

A repository watch (`repo-watches.ts`) is an item of the app-wide `RepoWatchesDoc` and a durable task in the conversation it messages (PiP's, or a session's), with the same wait, look, and send phases as a PR watch: a look puts the message in the task's checkpoint, and the send's request id is the task's and its count's, so it goes once. It reads the repository's issues, pulls, workflow runs, releases, and comments through `gh api`, and keeps the ids it told. PiP's tools (`repo_watch`, `session_watch_pr`, `session_start` with `repo`) act through `Pip` as its person; a repository is worked on or watched only where `gh`'s account can push, and `Pip.checkout` finds a session's checkout whose `origin` is the repository, or clones it once into `repos/`.

## Who chooses models

Sessions and PiP keep their person-selected models, with no silent fallback. Background subagents retain Coop's explicit-model contract; linked sessions have a stricter policy:

- **Sessions** run on the model someone picked, or on what a new session starts with (`Commands.#defaultModel`): the owner's default, even when it is not signed in now, else a trusted project's model/thinking default, else the last model picked, else Pi's global default, else none. `project-model.ts` reads only the final session folder's `.pi/settings.json` at creation, without a cache; a fresh creation-local global-only settings reader supplies defaults and trust policy without changing `app.settings`. It checks Pi's trust store and global trust policy, validates a complete provider/model pair, and keeps known unsigned models rather than silently substituting one. Invalid trusted settings stop creation with a contained error. Thinking-only settings cannot change another source's model/thinking pair. Owner defaults bypass project settings. Imported sessions, forks, subagents, manual choices, and PiP's own conversation retain their previous selection behavior. A model the person explicitly named to PiP bypasses project defaults before its manual configuration step. Trust gained after creation applies only to later new sessions; existing choices never track file or folder changes. Extra project skill/prompt paths and per-project run policy are not supported yet; the shared app settings and older host APIs are unchanged.
- **Resends and edits** (`Commands.resend`) explicitly configure their new fork with the source's current selected provider/model and current thinking fitted to that model, unless the request names an explicit model override. They do not restore the historical model at the fork cutoff. Original attachment lists, image-capability filtering, author attribution, retry receipts and fork/workflow access rules remain in their existing paths.
- **Background subagents** (`extensions/subagents.ts`) always expose an optional `model` parameter; omission inherits the parent's model. An empty owner `subagentModels` list leaves explicit choices unrestricted. A nonempty list restricts extra models, but the parent's model is always allowed. `PocketApp.setSubagentModels` replaces the list; `allowSubagentModel`, behind the Providers sheet's `POST /api/subagent-models`, changes one entry with no wait between reading and writing, so concurrent changes count. The app reloads the module to refresh guidance, not to add or remove the parameter. Spawn and later sends check the current list; removing the last entry restores unrestricted choices. Explicit model selection refreshes the sign-in check; a later send to a child on another model checks its provider too. Spawn thinking, explicit or inherited, is fitted to the chosen model's nearest supported level, including `max` and levels above the parent's. Later work preserves the child's model and thinking; it never lowers thinking to match the parent. A model/provider failure names the model and tells Pi to stop and tell its person, never silently retry on another model.
- **Linked sessions** (Agent Teams, `linked-sessions.ts`) always treat the shared `subagentModels` list as an allowlist of extra models: empty means parent-only, unlike background subagents. They start on the source's model or a listed one. Thinking is capped at the source's level, then fitted to the highest supported level at or below that cap; no such level means refusal. A model that cannot be used now is refused before the session is made.
- **Session titles** use the cheapest available text-capable small model of the conversation's provider, falling back to the conversation's own model when none is available. Title-model usage counts against that conversation.
- **Compaction and PiP's summaries** use the conversation's own model.
- **PiP** passes a model, or names one in what it sends, only when its person named it in their own words (`pip.ts`, with `model-names.ts`): their own messages (`u:` request ids, from the authors document) since PiP's last new context (with those its last compaction kept), and the standing instructions of the watches and webhooks to PiP that they set up; never a watch PiP set up, what was posted, or what GitHub said. Model-name tokenization recognizes Han/Kana/Hangul edges next to Latin model IDs without dictionary segmentation. Longest-name, short-family, per-message and explicit provider-ambiguity checks still decide whether the person named a model; token matching grants no model or handoff authority.
- **Sign-ins:** `Providers` asks subscriptions' sign-ins afresh (the owner's Providers sheet, a model a subagent on another model or PiP is about to use, a run that failed on one, a run answered by a marked one) and keeps, in memory, the ones their provider refused to renew. Explicit subagent model choices (`resolveModel`, `modelProblem`), later work for subagents on another model, PiP, and linked sessions as they start (`Providers.problem`) check before use and refuse unusable models. A session's own run and a subagent inheriting its parent's model try it and fail where people see them, and a run that failed on an expired sign-in marks it; a title that fails is only logged. `modelList` and `agentInfo` mark them, and the owner is told. A check that began before a sign-in or sign-out here marks nothing.

**Manual model refresh.** `Providers.modelRefresh` (`model-refresh.ts`) shares one in-flight refresh across owner tabs. `POST /api/models/refresh` requires the owner and the normal `X-Pocket` header; `hello.server.refreshModels` gates the UI against an older server. It checks local configuration with Pi’s public runtime API before reloading it, then refreshes each configured provider in parallel with a separate eight-second limit and `force: true` (network stays off under `PI_OFFLINE`). Each completed provider sends the existing `models` event and refreshes room views, so a slow provider does not hold back a healthy one. Pi owns cache publication and cancellation generations; failed catalog fetches keep its cached/static models. Refresh never configures a conversation or changes the default or subagent allow-list. Counts compare available provider/id keys before and after; provider errors are safe fixed messages, not raw exceptions that could contain credentials.

`PocketApp.modelList` resolves Pi’s `enabledModels` through the SDK’s `resolveModelScopeWithDiagnostics` against available models, then `modelList` marks scope membership alongside sign-in state. Both `hello` and providers’ `models` updates use that list. Manual refresh rereads Pi settings before recomputing the scope; malformed scope values are ignored so the picker still opens. The model picker’s Scoped / All state lasts only while it is open and filters the list without changing Pi’s settings, the session’s model, or its default. Empty scopes mean all available models, not a ban on picking models.

## Memory

Lessons Pi keeps across sessions are one document for the whole app, `MemoryDoc` (`pocket.memory`), by id. Each belongs to a private identity, a project or everywhere; private lessons never enter either shared namespace. A project is keyed by the real path of its git common folder (`git rev-parse --git-common-dir`), so a repository and all its worktrees share lessons; outside a repository, by the folder itself. `Memory` (`memory.ts`) works out a folder's project (kept a minute per folder) and keeps the rules:

- The memory extension's section renders, before each request, the lessons in force for the conversation's folder: its project's and everywhere's, not pending, oldest first. It reads committed state only, so it renders the same text until a lesson changes. Generic PiP has no project and gets everywhere's; persistent private identities get only their own server-derived private-agent lessons, never shared lessons.
- For shared lessons, Pi proposes and the owner approves. Every shared lesson Pi saves, and every one a person who is not the owner saves, is pending, and no prompt has it until the owner approves it: what Pi read anywhere in its context could have talked it into one. Pi's (or a guest's) new text for a lesson in force, and Pi's forgetting one, are a `proposal` on the lesson, which stays as it was until the owner approves or discards it. The tool's result names the lesson (`details.lesson`), so the transcript offers Approve and Discard under the call. An approval names what it saw (`POST …/memory/:id/approve` with `{ text }` or `{ forget: true }`); when what waits differs, `change` answers 409, so text or a proposal swapped after the owner looked is not approved with it. Pi proposing the text in force withdraws its own waiting proposal. Pending lessons do not count toward a project's or everywhere's cap; approving one does. Only the owner, or whoever saved a lesson, changes or removes it, Pi included (as the person it works for).
- Private identities maintain learned Memory automatically. The server derives `(ownerId, agentId)` from the actual chat, not tool arguments. Private correction/removal requires the observed lesson revision; registered tool writes also require the current native generation, owner token and identity epoch. Text-free request tombstones survive correction, deletion and restart, preventing stale replay or resurrection. Shared approval behavior is unchanged.
- Pi's adds carry the tool call's key, so a replayed call finds its lesson. A subagent's lesson comes from its session (`rootOf`).
- Every write adds an activity line to the session's chat in the same commit. `#committed` tells `Memory` when the document changed; it sends only authorized tabs in the changed namespace a `memory` event, and the Memory sheet and menu fetch the lessons again (`GET /api/c/:id/memory`).

**PiP's pending queue.** `GET /api/c/:id/memory?pending=all` lists new lessons and proposed edits or forgetting across every project and everywhere. It requires the human owner and their private PiP root as its anchor; queue approvals and discards use the same query on the existing mutation routes. Pi writers, other people, shared-session anchors, and queue add/edit/remove requests are refused before cross-project lookup. Approval retains the existing compare-with-what-was-shown check, limits, and transaction. Activity stays in the private PiP chat, not a shared session. The queue response has `pendingAll: true`, no project or add/edit controls, and project labels on lessons; an older running server's scoped response has no marker, so the new UI asks for a restart rather than claiming to show all projects. Browser memory fetches are keyed by person, role, conversation, and view, and refresh on memory events or a new connection.

## Startup

The server entry point binds its listener before `PocketApp.open`, so bind/setup failure cannot resume durable work in an unreachable process. Explicit `--access tailscale-https` makes the launcher preflight native Tailscale certificates before replacing the current transport, then starts the server with `--tailscale-https`. Existing `tailscale` settings remain HTTP. `tailscale-https.ts` validates the active profile, full `.ts.net` identity, requested bind address and certificate/key before creating an HTTP/1.1 `https.Server`; it binds only that Tailscale IPv4 address. Requests retain the existing handler, native TLS origin/Secure-cookie detection and WebSocket upgrade/auth path. No second listener or plaintext fallback is created.

A pending startup stop is honored before opening the app; a stop during opening closes the opened app before routes or readiness are published. TLS renewal is single-flight every 12 hours, requests at least `168h` validity, refuses identity changes before requesting another certificate, and replaces the TLS context without restarting work. Refresh failures retain the previous context with a safe warning; browsers still reject an expired certificate. Native Tailscale owns its cache; Coop holds the stdout pair only in memory and wipes discarded key buffers where practical. The TLS lifecycle `close()` cancels/joins renewal; the entry point separately closes the listener and `app.close()` (including upgraded connections). See [setup and Certificate Transparency disclosure](../README.md#private-https-with-tailscale).

`PocketApp.#open` runs in this order, and the order matters:

1. Take the data folder's lock. Set up push, Pi's settings, and the HTTP settings for provider streams.
2. Load the models, activate approved Pi provider packages (or retained releases), then register the core tasks and every ordinary extension module that is on.
3. Open the storage and the harness.
4. `#recover`:
    - read the session list;
    - for each conversation, in turn: its run, agent, chat, who Pi works for (`attribution.recover`), and its subagents;
    - then write back, in one commit, the authors that a crash kept out of the authors documents (`attribution.repair`).
5. Load spend.
6. Subscribe to commits, approvals, and browser pages.
7. Warm Lancet Guard.
8. Resume the work the last process left unfinished, unless provider recovery mode holds scheduling.

Work resumes last, so that everything that follows commits is listening before the first one comes.

## The commit coordinator

Pi Durable publishes each commit's changes in no set order. `#committed` handles them in two passes:

1. **Usage first** (`spend.usageChanged`): what a commit's usage cost belongs to whoever Pi worked for before a message in the same commit changes that.
2. **Then each change:**
    - Document changes go to `#documentCommitted`. It tracks busy and ended runs, agents, the session list, and the documents the rooms show (`ROOM_DOCS`).
    - Submissions go to `attribution.submissionCommitted`.

Everything here is synchronous. A commit listener may not call the harness's session APIs, so a write it causes (noting a message's author, or moving a session up the list when Pi starts work there) runs in `setImmediate`. Keep this one coordinator: separate listeners would make their registration order a billing rule nobody can see.

Updates to tabs are coalesced:

| What                                                                       | How often, at most |
| -------------------------------------------------------------------------- | ------------------ |
| A room's changes                                                           | Every 90 ms        |
| Peek tiles                                                                 | Once a second      |
| The session list, and every subagent to tabs that show the subagents board | Every 400 ms       |

Each connection keeps the JSON of its last session list and receives another `sessions` event only when that person's projection differs. Initial attachment always sends a list. Access refresh still sends hello/projects and evicts hidden rooms and peeks; catalogue equality never substitutes another person's projection.

Each room update sends a tab its new entries, the live run, and some small fields. Protocol 3 sends the live message as unchanged leading blocks, replacement blocks and an optional text/thinking suffix. `web/live.js` reconstructs it; a mismatched base requests a full reconnect. Full views reset the base, PiP has its own room client, and protocol 2 and older connections still receive whole messages. The live run is projected once per immutable committed state. The fields that grow with the session, such as the queue, authors, reactions, and pins, go again only when they differ from what the tab has, because a turn sends an update every 90 ms. The queue sends each waiting input's full main text, its separate `editableText` and `hasAttachments` flag, and the names of the subagents in a message of reports. Image bytes and inline file bodies stay out of those rows; an input of images alone says how many. Its row preview and disclosure are presentation only: collapsing the queue never truncates the editable text or changes submissions, even when a paste or a batch of reports is megabytes. A tab's connection names what its code understands (`p`, `PROTOCOL` in `web/store.js`): a tab with code from before, as one asleep through an update keeps, names none, and gets the queue with each update, because its code drops a queue that an update leaves out.

## Who Pi works for

A message to Pi names its person in its request id (`requests.ts`):

- `u:<user>:<key>` is a person's own message.
- `p:<user>:<key>` is one sent for a person, such as a scheduled message or a subagent's task.

`attribution.ts` notes each one in the conversation's authors document. Pi works for whoever wrote the newest message (`requesterOf`). A subagent works for whoever its parent worked for when it sent the subagent its last message. Spend, approvals (the "someone else must allow" rule), schedules, and subagents all ask `requesterOf`. A message sent for someone must carry that person in its request id. One that names nobody does not change whom Pi works for: Pi goes on working for whoever it worked for before. Spend, when nobody is known, falls back to whoever started the session, then the owner. Auxiliary requests such as shared PiP answers instead carry an explicit immutable requester/source in their own receipt ledger; they never infer their payer from a later message.

## Background subagent reports

Each message sent to a subagent has a background reporter task. Its request ID makes delivery and the report to the parent idempotent across a restart. After submission, the reporter watches the child's live state while waiting for the answer. If the child becomes idle with that submission still queued, it withdraws only that submission and reports that it must be sent again. A placed or answered submission is left alone. Withdrawal rechecks idleness and the exact queued submission in one transaction. Its settlement, durable reason and queue removal commit together; reopening reads that reason rather than an in-memory flag, so it cannot be mistaken for someone's Stop. The watch is stopped on every exit, and any withdrawal already under way is joined before the phase ends.

Explicit Stop is silent: it sends no automatic failure report to the parent. A stranded-input withdrawal is different and reports that the message must be sent again, including after a restart.

The upstream batched courier is installed. Reporters append to `SubagentsDoc.outbox`; one durable `pocket.subagent-courier` task gathers them into a single message at the parent's next pause, waiting briefly when the parent is idle. Reports arriving while that batch is queued are merged into it, so the queue holds at most one report batch. `sending`, `batches`, and request IDs preserve delivery across restarts, and `held` explains reports waiting for a spend limit to be raised. Existing anchor and reporter task names, versions, and checkpoints remain compatible; the courier also accepts its older send checkpoint.

## A request

`http.ts` routes by the first path segment, and turns whatever a route throws into an answer: an `HttpError`'s status and message, or a logged 500.

Ordinary app/vendor files revalidate with content ETags and 304 responses. Their bounded byte cache retains negotiated asynchronous compression only for settled file versions; recent edits bypass reuse even when timestamps are coarse. The app document keeps its live-reload revision and CSP and preloads its static module graph, not dynamic editor/terminal payloads. Large immutable renderer builds keep their separate streamed delivery path.

Text/API answers of at least 1 KB negotiate asynchronous Brotli or gzip; already encoded and binary answers stay unchanged. SSE uses one compressor per connection, flushing every event and ping. Compressed output follows HTTP backpressure, pending input is bounded, and abort/close destroys the compressor and detaches its client. Long polls use ordinary compressed JSON responses with the existing acknowledgement queue. Vary retains existing cache dimensions. Compression can trade server CPU for wire bytes; tunnel latency and device behavior need separate measurements.

`/api` (`http/api.ts`) checks, in this order:

1. who is signed in (the cookie, or a bearer token), synchronously cloning that request's identity before any route await so token/grant changes cannot mutate its captured authority;
2. it notes the quick tunnel a guest came through;
3. the `X-Pocket` header, on everything but GET.

A conversation's routes (`/api/c/:id`) run only after `requireSee`.

`/api/x/:module/…` (`http/extension-routes.ts`) is an extension module's own route: after the checks above, and the `X-Pocket` header on a GET too (a module's GET may change things, and the cookie goes along with a link from another site), it answers only the people its `access` lets in (`mayUse`: the owner by default; never someone invited to one session). The header is checked before the route is looked up, and a route someone may not use is not there for them (404, and a 405 names only methods they may use), so nobody learns of routes that are not theirs. A `:name` part that decodes to `..` or holds a backslash or NUL is a 400. Only the owner reads a 500's words, but for those a module gave `web.error`, which it chose to show. `/x/:module/:rev/…` serves its browser module's files, outside `/api` but after a sign-in, under the declared browser access: one file, or a folder's regular web files up to 8 MB, never its `.ts` files, hidden files, `node_modules`, or anything reached through a link. Each is opened without following a link or waiting (`O_NOFOLLOW | O_NONBLOCK`), and read only when its handle is a regular file and the file that was checked (the same device and inode, and on Linux the path `/proc/self/fd` gives), so nothing swapped in after the check, a folder on its way included, is read. Where there is no `/proc` (macOS), a folder swapped for a link within the check itself can still lead elsewhere: only someone who can write in the module's folder can do that, and they can already run code in the server, by editing the module.

`/api/c/:id/x/:module/…` is a separate scoped route registry. Current source visibility and declared
role access are checked again after body reading and on each request-bound transfer-service call.
`client(..., { access: "conversation" })` permits scoped invitees to load static assets only; it does
not widen app-wide `/api/x/` routes or expose other sessions. Core `/api/c/:id/transfers` remains a
passive own-receipt lookup, independent of extension routes and enablement.

Where the other checks live:

- **Commands and collaboration** check steering and driving themselves (`requireSteer`, `requireDriver`). They are called from routes, from tasks, and from each other.
- **Owner-only settings** are checked in `http/api.ts`: extension modules, provider sign-ins, restart. Changing people's access, the approval rule, the default model for new sessions, and the models subagents may use is checked in `app.ts`.
- **Invites** are owner-only in both `http/api.ts` and `Auth`, and redemption rechecks the creator's current owner authority. New collaborator invites carry explicit project grants, defaulting to none; changing roles does not widen those grants. Host Pi-history continuation cannot be granted through new invitations. An invite lasts one of `INVITE_MINUTES` (`auth.ts`; an owner invite, always 15) and is kept in `config.json` by its code's hash, so a day's or a week's outlives a restart. Only whoever made one ends it early (`POST /api/invite/cancel`), as the invite sheet does with the one it showed when its settings change, and with one that answers after it closed. One person keeps at most `MAX_INVITES` (`config.ts`) live, their oldest ending first; removing someone ends theirs, and a new owner token ends owner invites not yet used.
- **The workspace's path helpers** (`conversationFile`, `readableFile`) leave seeing the conversation to their caller.

Each browser tab is a `Client` (`room.ts`), fed by an event stream or by long polling (`http/events.ts`). Subscription registration alone retains the live configured person for presence/access updates; registration is synchronous after authentication, not an awaited mutation request. On connecting, a tab gets:

1. `hello`;
2. the session list;
3. then, when it shows a conversation, the room's full view;
4. then only what changed.

## Extensions' commands

A module registers its commands with `web.command` while it loads. `ExtensionWebs` keeps them with the module's version, as it keeps routes: they count once the version installs, a version that fails leaves the ones before, and turning the module off removes them. Each registration has an id that is new with each version. `hello` lists the commands a person may run (`server.extensionCommands`, without handlers or files: viewers none, guests the conversation ones), and a change to them sends everyone's tabs `hello` again.

`POST /api/c/:id/extension-commands` goes to `app.extensionCommands` (`extension-commands.ts`), not to `app.commands`, which sends messages to Pi. Before a run's task is made, it checks seeing and steering, then driving for a conversation command or the owner for a global one, and that the person has fewer than 4 runs going; a retry of a request checks its person again. Nothing refuses a run once its task is made. The wait ends when the browser stops waiting; the run goes on.

A run is a `pocket.extension-command` task (`COMMAND_TASK`), made in one commit with its request id in the person's `pocket.extension-command-request` document for that session (`CommandRequestsDoc`), which keeps the last 100 finished ones and every one still going. A retry finds that task and waits for its result; the same id with other arguments or another registration is a 409. The handler the request chose is kept in memory until its task takes it. The task marks that it started before the handler runs, and keeps the result in a memo: after a restart, a task with no result reports that it was cut off, and its handler never runs again. A handler's own error words go to the owner in a notice; the person gets them only from `web.error` or an `HttpError`.

A card is a `pocket.extension-command` entry with only `kind` and `data`: no `model`, `head`, or `edits`, so Pi never gets it. Its write's request id is the task's, with no person's prefix (`requests.ts`), so it does not change whom Pi works for. A notice goes back only in the answer to the person who ran it.

In the browser, the composer keeps a command's request id while its send is unresolved, as for `!` commands: sending the same text again after a network error or a 5xx finds the same run. Running now names the command from its task, never its arguments, and shows global ones to the owner alone.

## The web app

Plain ES modules, served as they are, with no build. Editing a file under `web/` reloads every open tab, and a syntax error blanks the screen for everyone.

**Loading order matters.** `store.js` is the root, and a few modules do work when they load (listed in [map.md](map.md#web-web-preact-and-htm-no-build)). `theme.js` must load before anything that reads `prefs()` as it loads. `store.set` calls subscribers in the order they subscribed. When moving code between modules, keep both orders. `back.js` sits under `store.js` and imports nothing of the app's, so anything may use it.

**Drawing streamed replies (`ui.js`, `sessions.js`).** The session list and rail use `apartFromViews` to skip store updates that change only `view` or `pipView`. Local component state, changed props, other store fields and explicit `store.set({})` still redraw them. These subtrees must not read either view. Streaming Markdown re-lexes top-level blocks and reuses unchanged sanitized/highlighted parts from the preceding update. Image/link context and private read-only mode are part of that cache's scope. Whole HTML pages keep their single fenced preview; completed text uses the finished LRU cache and resolves cross-block references. A reference defined in another block, or HTML split by a blank line, may display differently until completion.

**Themes (`themes.ts`, `theme.js`).** The page has three cascade layers, declared in `index.html`: `pocket` (`style.css`, imported into it, and extensions' stylesheets, which `pocket.style()` imports into it after), `palette` (the colors' variables, a `<style>` that `theme.js` writes), and `theme` (a theme folder's stylesheets). A later layer wins whatever the specificity, and an earlier layer's `!important` wins over a later one's, so a theme overrides the app's rules but not its reduced motion. Inline values beat every layer: only appearance settings (the UI font, text size, dragged widths, custom layout preferences) are inline, never a palette. Startup does not rewrite an existing preference record or persist inherited defaults as a personal choice. **Workspace reads (`diff.js`, `files.js`, `files-panel.js`, file/folder sheets).** Changes has one conversation/caller/cwd/namespace-scoped lifecycle shared by its header, Files and review consumers. Mounting another consumer does not force another read. Hidden, offline and departed pages suspend it; returning refreshes once, and explicit Refresh remains available. Superseded or unmounted file/folder/diff/context reads abort, cancelled queued diffs are removed before dispatch, and late results cannot refill abandoned caches. `http/io.ts` ties workspace/review GET contexts to request abort and response close; cancellation reaches SFTP, Git and native snapshots, and the route awaits their cleanup. This is read cancellation, not proof of remote mutation termination or permission to replay a mutation.

**Thread-specific side panels (`store.js`).** One `pocket.panels.<conversationId>` session-storage record owns the selected Files, Browser or docked People panel and the Files/Changes tab. Explicit navigation and route Back/Forward restore the destination's record; unseen threads, home and private routes start without a panel. Open files and browser pages retain their existing conversation-specific owners. Legacy global panel preferences migrate only to the thread open at upgrade. Mobile panel Back callbacks check their originating conversation before closing, so an outgoing overlay cannot close a panel restored for another thread.

**Model picker (`sheets/model.js`).** Shared sessions and Private Chat use the same provider-grouped presentation. Provider expansion is local to the open picker, with the current provider first and expanded by default. Search resets expansion overrides and reveals matching groups; model keyboard navigation uses only expanded rows. Provider disclosure buttons sit outside the per-provider listboxes, separate from model selection. The shared configure action and private callback remain unchanged.

**History is the back stack (`back.js`).** Only `back.js` writes history. Each route (`/s/12`) and each layer over it (a sheet, the drawer, the launcher, the Files tile or Browser panel where they cover the screen, a file over the tile's tree) is an entry, and each entry says how many layers it stands for and how many steps back the session list's entry is. The app's state is the truth and history follows it a moment later: opening a layer pushes an entry, closing one with a tap goes back past it, and a new route first goes back past the layers above the current one. Back that the person makes closes the layers above the entry it lands on; back to another route reaches `store.js` through `onRoute`. Traversals `back.js` makes itself reach no one. So:

- Navigate with `navigate()` (which calls `pushRoute`); do not call `history.pushState` or `history.back()` elsewhere. To drop a query from the address, use `replaceAddress`, which keeps the entry's marks.
- Something new that covers the screen, or that back should close, is a layer: `useBack(open, close)` in the component that shows it, where `close` makes `open` false. Sheets get theirs from `sheets.js`, one per sheet opened from another (the menu, then the model picker).
- On phones the window clips sideways: the conversation sliding in from the right (a route, a swipe's lean) would make the page wider than the screen, and a phone's browser widen and pan its view to fit.
- A finger's or a mouse's press and click within 280 ms of a layer opening or closing, or a route opening, at a tap (a pointer let go in the 400 ms before) is let go, focus and all: a quick second tap would land on whatever slid in under it (a tile of the sheet that rose, the scrim that closes it). What moves on its own (a reply opening a session, the server closing a sheet, Escape) holds nothing back, and keys and scripts never are.
- New entries wait for the page's first tap or key, since Chrome's back button skips entries a page adds before anyone touches it: the list's entry under a conversation opened straight away on a narrow screen, and the entries of layers already open at load (the chat a notification opened, a panel the tab kept).

**PiP chat (`pip.js`, `pip-attachments.js`).** The panel's uploads, submits, image thumbnails, and Markdown image paths use its own conversation ID, never the session behind it. The browser-only attachment draft outlives panel mounts, scopes itself to account and PiP ID, and holds upload identities and submit tokens so late callbacks cannot restore removed files or clear newer drafts. Unknown authentication or conversation IDs during reconnect are not a scope change. Files survive closing and reopening the panel, not a page reload; text keeps its existing local-storage draft. The normal upload and submit endpoints retain their size, file-access, and image-capability checks; PiP does not choose another model for an attachment. Opening the pending-memory sheet uses the private PiP ID even on Home. Panel cleanup restores focus only if it is still in the outgoing panel or on the body, not when a destination sheet already took it.

**PiP resize (`pip-window.js`).** Resize uses pointer capture on the same edge/corner zones for mouse and touch, at widths of 768px and above. The preferred size is local to the account/browser; CSS clamps it to the viewport without overwriting it.

**Extensions' browser modules (`extension-ui.js`).** `hello` lists the browser modules a person's tabs load (`server.ui`: each module's name, title, and address, with its version in it). The tab imports each, and imports it again when its address changes: the server sends `hello` again when a browser module comes, goes, changes who it is for, or one of the files it serves changes (`ExtensionWebs` watches its folders), and when its module's new version installs other tools. A reload that leaves all that as it was leaves the address as it was, so tabs keep the browser module they loaded (they may hear `hello` again for other reasons). Event streams and poll queues cut off a tab more than 8 MB behind that took nothing for 30 s, or any tab 128 MB behind (`http/events.ts`); it connects again and gets a full view. A large first view is no reason: the tab has had no time to take it. A polling tab with an answer on its way is taking it until it polls again (one that never does ends 60 s after its last poll or answer), and a stream's ping checks too, so a stalled tab is cut off with no new events for it. A browser module is meant to add only through `pocket` (it runs in the page, so nothing stops it from more), and one that throws is caught there: its notice, its row in the Extensions sheet, its page's error box. One that failed stays listed (`dead`) but adds nothing more, until its module installs other tools: then the tab loads it again, as it may have failed on a tool the server did not have yet. Its events come as `ext` (`{ module, event, data }`). How a module's tools' calls show (`pocket.toolCall`) reaches `calls.js` and `turns.js` through setters, as they import nothing. Each `ui` entry lists the tools its module installs (from the loader), and a module describes only those; what a describer gives is used only when it is text. When a module goes, `sheets.js` takes its sheets out of the ones back would bring back (`onExtensionsGone`). A tab in safe mode (`?noext=1`, kept as `pocket.noext` in session storage) loads none of them.

Inline controls and input hints use the same guarded extension renderer as pages and sheets.
`pocket.session()` and `onSessionChange` expose deeply frozen copies of the filtered catalogue and
public profile metadata, not store objects. The conversation copy contains only id/kind/title/profile/
folder, never settings, prompts or raw view. Catalogue/profile copies are cached per immutable input
object. `AgentProfileTag` uses registered metadata, not a
core role-label table. `sessionApi` calls only the module's scoped routes; `submit` uses the generic
human-input journal. `SheetProps` stay flat, and `close`/`isOpen` pin the actual logical opening so a
retained closing component or late callback cannot act on a newer sheet, including during the closing
animation. Work Items' sheet receives flat `{ close, isOpen, id, opening }` props. `pocket.requestId()`
uses core's ID generator for submissions, revisions and opening tokens, including on plain-HTTP LAN
origins. Host and browser target the same source version.

**Contracts with the server.**

- Event names and shapes (`hello`, `view`, `chat`, `peek`, `subagents`, `ext`, …) and the sheet types the server names (`sheet: "chat"`).
- Queued input edits use `edit-queued` with the submission ID, new text and expected previous text. The server checks access and edits `pi.inbox` in one commit, retaining the submission, order, mode and non-text content. Provenance-marked application events and agent answers are not editable: changing their body must not retain trusted service authorship or diverge from the immutable answer receipt. They can still be withdrawn, or superseded by fresh human input. A boundary that already placed the message or a conflicting edit rejects the save. The composer keeps edits separate from its persisted draft and restores that draft after saving or cancelling. Queue disclosure is local UI state; collapsing the list does not pause or change pending submissions.
- The `pocket.*` keys in local and session storage.
- Extensions' API: `web` on the server and `pocket` in the browser, at `POCKET_API`. Modules outside this repository depend on them: add to them freely, and change what they do only with a new version.
- `ATTACHMENTS_HEADING` and `splitAttachments` (which also reads the form sent before 0.14.0), which `ui.js` repeats from `entry-format.ts`.

## Quick file edits and language servers

The file viewer loads CodeMirror only on **Edit**. `http/editor-assets.ts` bundles the installed editor packages once in memory (invalidated by entry or lockfile changes); the ordinary app still has no build step or CDN dependency. `file-language.js` owns restartable CodeMirror LSP clients/transports independently of `file-editor.js`'s persistent editor view, not a second completion or diagnostics implementation. Unsaved drafts stay in the current tab's session storage and survive Back and web reloads; Cancel discards them and Save removes them. Editing uses the viewer's bounded flex height so only CodeMirror scrolls. The footer holds save state and clickable keyboard shortcuts. Escape consumed by the editor or its status menu does not close the enclosing sheet.

`workspace.saveFile` checks steering, turns, busy state and canonical path access. Complete UTF-8 files up to the viewer's byte limit carry a hash of their original bytes. `file-edits.ts` serializes saves per canonical path, rejects stale revisions and replaces the file atomically after rechecking its identity and bytes. App state and Pi's settings are not writable through this route. Save informs Pi and the people in the conversation; it does not submit model work.

`LanguageServices` binds opaque document leases to the owner, conversation and original working directory. It rechecks access and paths on every message/poll. `LspPool` lazily initializes one owned server per canonical project root and server type. Git projects use their checkout root, keeping worktrees separate. The bundled TypeScript/JavaScript server is the pinned TypeScript 7 Go-native preview (`tsgo --lsp --stdio`); other supported servers are fixed executables on PATH, not commands read from a browser or project file. `vscode-jsonrpc` owns stdio framing. Browser request IDs and responses remain isolated, and a document has one unsaved-buffer lease at a time.

`file-lsp-status.js` uses the owner's `status` action to inspect the live pool. `LspPool.status()` returns named starting/running/idle servers with opaque IDs, projects and document counts, without spawning, recycling or renewing leases. The menu refreshes only while open and visible/online, uses the shared Back stack and closes independently of the editor. Hide/offline/pagehide immediately abort its read, clear its refresh timer and dismiss the transient menu.

`file-language.js` releases its lease and stops polling when hidden, offline, leaving the page or losing owner access. Returning opens a new lease/client and reconfigures only the LSP compartment on the same view, so the fresh plugin sees the current unsaved document without resetting selection, history or focus. Retirement removes stale diagnostics and formatting, aborts transport requests and discards deferred sends. Generation ownership fences late open/initialize/failure results; ordered lease close precedes replacement open, with failed offline closes retried only on the next active opening. Initialization is not awaited by the lease queue: the official client's disconnect does not cancel initialization. Small close requests use keepalive on unload; normal lease expiry remains the fallback if cleanup cannot be delivered. Lease heartbeats, expiry, idle recycling and bounded queues keep abandoned editors from retaining servers forever. App shutdown closes the pool and terminates only its own children. Language services never write files or execute browser-provided commands; formatting edits only the browser buffer. A missing, busy or failed server falls back to ordinary editing. This is quick editing, not a multi-file IDE or collaborative buffer.

## Browser application selection

Clean sessions use an installed desktop/PATH browser before a cached Playwright Chromium download. Coop does not require another Chrome installation or download one automatically. The cache is only a fallback and must contain a download-completion marker and an executable browser in a recognized layout for the current platform. An explicit `PI_POCKET_BROWSER` takes precedence; an invalid explicit path does not silently select another browser. Imported defaults continue to use their source browser executable for native credentials.

Separate profile directories do not give headless and desktop Chrome separate macOS application identities. A Dock launch activating the headless process without opening a visible window is one possible explanation for the reported opening problem, but it has not been confirmed. Keeping installed Chrome preferred is not a demonstrated fix for that symptom. A manual diagnostic using the same installation is `open -n -a "Google Chrome"`: Apple's `open(1)` documents `-n` as opening a new instance even if one is already running. Coop does not run this against the owner's personal profile. Whether it opens the usual window, and whether subsequent Dock launches work normally, still needs to be checked.

Discovery does not alter personal profiles, the Chrome app bundle, LaunchServices registration, localhost access or workflow permissions. The executable is cached by the running browser manager, so changed discovery code requires a server restart before it applies.

Page-target descriptions and label lookup in `browser/page-scripts.ts` omit password-input values, including when describing a covering or invisible element. Public labels, placeholders and normal control values still work. `BrowserPage.locate` handles coordinates with a generic point description and no DOM-value read; it does not use upstream's newer point/fill API. Snapshot password masking remains unchanged. This is not a redaction boundary for arbitrary page scripts, page text or caller-supplied selectors.

## Imported browser defaults

`Browsers.profiles` discovers local Chromium-family profiles for the owner through `/api/browser-profiles`. Discovery reads profile metadata only; an opaque selection ID, not a client-selected import path, identifies the source. Custom discovery accepts a server-local profile path and the executable for that browser. Import requires explicit app-wide confirmation, refuses an in-use source and copies into a private, app-owned directory before atomically selecting it. Source profiles are never launched or modified. Caches, passwords, autofill, extensions and restored tabs are excluded.

The clean default retains temporary, isolated contexts. An imported default instead uses the copied profile's persistent default context with the source browser executable and native OS credential storage. Every conversation shares its cookies and site storage; existing Browser-panel access checks still apply. `Browsers` supplies the app's authentication-cookie name from `auth.ts` to Chromium's launch-time cookie stripping. The launch promise does not resolve until these cookies are removed from the copied default context, so even simultaneous page openings cannot inherit the owner's app sign-in. The Settings panel warns about this account access before import. Popup routing in that shared context requires the conversation page's opener ID, so opening another conversation cannot capture or close its tab.

A switch serializes against other switches and page openings, closes app-browser pages and gracefully stops Chromium before changing the selection. Shutdown asks Chromium to flush persistent storage. A retained stopping promise prevents another writer from launching until the old process exits, and target/close callbacks ignore replaced browser generations. Failed target attachment also closes its unclaimed persistent target. Returning to clean sessions deselects the import without deleting the copy. Firefox/Safari profiles are not directly compatible. Import currently supports macOS and Linux, not Windows (no reliable closed-source check yet) or Snap executables (cannot use the private import directory). OS-encrypted or site-bound logins may require signing in again.

## Checking a change

- **Every change:** `npm run check` (types, and no unused imports or locals in the TypeScript), `npm run lint`, and `npm test`.
- **Server:** the tests drive a real `PocketApp` with a scripted model, a restart included (`openApp` on the same folder). The built-in browser and peek tiles also run in a real Chromium where one is installed.
- **Web:**
    - `node --check` each file you edit.
    - Then open the app and use what you changed, with the console open.
    - A change that moves code between modules is a move only when the moved code is the same and the loading order above is kept.
