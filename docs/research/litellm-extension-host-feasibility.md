# Hosting the unmodified LiteLLM Pi extension in Coop

Research only, 2026-10-11. **pi-provider-litellm 4.2.0; Pi 1.1.0.** No activation, installs, tests, inference, credential/configuration inspection or modification, source edits, or restart. Only this report was written. Findings are source-derived, not runtime validation.

Citation roots: `L/` = `/Users/enkelm/.pi/agent/npm/node_modules/pi-provider-litellm/`; `C/` = repo `node_modules/@earendil-works/pi-coding-agent/`; `A/` = repo `node_modules/@earendil-works/pi-ai/`; `D/` = repo `node_modules/@earendil-works/pi-durable/`. Other paths are repo-relative. Citations below identify exact installed primary sources.

## Conclusion: YES, conditional on a restricted provider-extension host

**An upstream provider-only library export is not required for this alternative.** Coop can activate the package's ordinary, supported Pi extension entry through Pi's public loader, collect its native providers, and run its public `ExtensionRunner` event methods around requests. This executes the package's own private auth, discovery, request-policy and final-message code without copying it or maintaining a fork. The previous notes [provider reuse](litellm-provider-reuse.md) and [package management](provider-package-management.md) evaluated a narrower provider-library boundary; their packaging rejection is not a rejection of this different host boundary. The package explicitly supports Pi-extension loading and declares `pi.extensions: ["./src/index.ts"]`. [L/README.md:25–33; L/package.json:1–32]

This is **not available in current Coop**, nor a claim that all Pi extensions will work. The useful first supported profile is API-key auth, default `litellm` plus aliases, discovered/cached chat models, native inference, mandatory request events, and terminal transformations before persistence. It requires fresh activation state per independent execution lane, complete callback piping, strict failure handling and bounded startup. UI, budget, MCP, skills, SSO/ADC, custom-model overrides and arbitrary extension actions are outside that profile. No silently missing critical event is acceptable.

Two limits must remain explicit: the unmodified extension's cost parser/allocator is imperfect, and headers do not establish invoice-final streaming charges. Precommit transformation can be guaranteed for completed requests; complete billing of externally charged requests interrupted by cancellation/crash cannot be promised with the present Durable path.

## 1. The actual public activation boundary

- Root exports **`discoverAndLoadExtensions`, `createExtensionRuntime`, `ExtensionRunner`, `ModelRegistry`, `ModelRuntime`, `SessionManager` and their relevant types**. An `AgentSession`/ordinary Pi agent loop is not required to use those exports. The runner constructor accepts extension objects, their runtime, cwd, a session manager and model registry; `bindCore` has explicit native-provider registration actions. [C/dist/index.d.ts:7–21; C/dist/core/extensions/runner.d.ts:79–131]
- **`loadExtensions` is not a package-root export** in 1.1.0, despite being exported from the internal extensions index. Do not recommend a blocked `dist/core/...` subpath. The public `discoverAndLoadExtensions([installedPackageRoot], loaderCwd, discoveryAgentDir, eventBus)` resolves the package manifest and invokes the normal loader. It also scans `loaderCwd/.pi/extensions` and `discoveryAgentDir/extensions`; use dedicated empty discovery roots, not conversation workspaces or the owner's extension directory, to constrain execution to approved packages. [C/dist/index.d.ts:9; C/dist/core/extensions/index.d.ts:5; C/package.json:14–27; C/dist/core/extensions/loader.js:661–699]
- The normal loader uses Jiti, host Pi aliases (including `pi-ai/compat`), and `moduleCache:false`, then awaits `default(ExtensionAPI)`. It stages runtime registrations until the factory succeeds. This is the supported route for the package's TypeScript and `.js` relative specifiers; no native Node deep import or copied alias machinery is necessary. Loading errors are returned, not necessarily thrown: the host must check the entire result. [C/dist/core/extensions/loader.js:33–83,459–482,510–576]
- `ExtensionRunner.bindCore` flushes queued native registrations and can send them to host `registerNativeProvider` actions. Registration failures are caught and reported through `onError`, so binding also needs a failure gate. Capture each activation's providers into its own lane rather than repeatedly replacing global providers with the same IDs. [C/dist/core/extensions/runner.js:205–302; C/dist/core/extensions/runner.d.ts:147–148]
- **Discovery-root isolation is not configuration isolation.** The extension directly reads `getAgentDir()/settings.json` and `auth.json`, and uses process environment. The loader's `agentDir` argument only changes extension discovery. `SettingsManager.inMemory` does not override these direct reads. A separate configuration namespace would require an explicitly configured process/agent directory, not transient `process.env` changes around concurrent activation. Keep activation/auth store roots consistent. [L/src/index.ts:96–132,1937,2088–2092; C/dist/config.js:475–497]

Installing a dependency therefore solves delivery only. It remains trusted server code with credential access and activation-time network effects. Pin package/Pi versions and verify the approved manifest, dependencies and host-module bindings; do not treat this host as a sandbox. The package version check itself only requires Pi >=0.99.2. [L/src/index.ts:1876–1885; C/dist/core/extensions/loader.js:33–83]

### Optional capabilities do not all disappear automatically

- **MCP, skills and budget default ON.** They disable only with objects such as `litellm.mcp.enabled:false`, `skills.enabled:false`, `budget.enabled:false`; a bare boolean `false` does not disable them. These are conditions for a proposed deployment, not configuration changes performed in this research. [L/src/index.ts:492–498,1886–1890]
- With MCP disabled, guarded startup/turn registration does not run. Otherwise activation can call `registerMcpServer`, and later login/root changes can call `unregisterMcpServer`; the normal Pi registry alone is not a working Coop MCP client. Reject the enabled feature unless implemented, rather than quietly accepting disconnected servers. [L/src/index.ts:1918–1972,2318–2324]
- With skills disabled, no gateway tools register and the unconditional `before_agent_start` callback returns before auth/network/UI work. Enabled skills require registered tools, request auth, gateway calls and system-prompt enrichment, outside this minimum. [L/src/index.ts:2253–2257,2297–2316]
- With budget disabled, its commands/hooks are not installed. `hasUI:false` alone gates automatic budget polling, **not the registered budget command**, which can still perform network work; prefer explicit disablement. Budget observations are not required for inference or request-cost replacement. [L/src/index.ts:2236–2251; L/src/budget.ts:461–537]
- **SSO has no corresponding off switch:** default `litellm` always registers OAuth alongside API-key auth; aliases do not. Merely hiding Login UI does not stop stored OAuth being used, refreshed, or read during startup seeding. An API-key-only host must reject unsupported stored auth before activation/request use and expose only allowed login methods; never silently fall back to an environment key. ADC is opt-in via `LITELLM_GCLOUD_TOKEN_AUTH`; command key/header helpers also need an explicit supported/forbidden policy, including activation/discovery paths. Initial scope should require ADC off and no command helpers. [L/src/index.ts:500–523,1539–1635,1987–2007,2088–2095; L/src/gcloud-token.ts:41–44; A/dist/auth/resolve.js:49–100]
- Unsupported action bindings should throw, not return fabricated success. The runner's public `bindCore` requires a broad typed action object, but this profile invokes only the narrower paths above. Register and check its error listener before binding/dispatch; reject unexpected capabilities after loading. That is a pinned supported profile, not a general extension compatibility promise. [C/dist/core/extensions/types.d.ts:1616–1695; C/dist/core/extensions/runner.js:205–302,607–691]

## 3. Generic piping can run before Durable's commit

Pi already supplies the template: `sdk.js` wires Models `transformHeaders` to `emitBeforeProviderHeaders`, payload callbacks to `emitBeforeProviderRequest`, and response callbacks to `runner.emit({type:"after_provider_response",status,headers})`. The public runner separately provides `emitMessageEnd`. These are generic APIs, not LiteLLM-private helpers. [C/dist/core/sdk.js:196–250; C/dist/core/extensions/runner.d.ts:179–193]

A portable host needs the following request sequence:

1. Select the isolated lane, obtain its serial lease, and bind a **request-local physical model/session/signal** context before any asynchronous auth or callback work. Do not use the conversation's currently selected model as a proxy for the physical model used by compaction, title generation or another auxiliary call.
2. Let native Models/ModelRuntime resolve auth. Compose `transformHeaders` at the Models boundary, which receives assembled auth/options headers. A raw `Provider.stream` wrapper alone is too late to receive this Models-only transform option: native Models removes it before dispatch. Payload and response callbacks do reach providers; all three LiteLLM transports await them around the HTTP request, before consuming its response stream. [A/dist/models.d.ts:42–50; A/dist/models.js:424–461; A/dist/api/openai-completions.js:188–203; A/dist/api/openai-responses.js:124–138; A/dist/api/anthropic-messages.js:429–443]
3. Compose caller callbacks deliberately, preserving their replacements, then run required extension policy as the final outbound policy stage. Set/update context from the physical model passed to transport callbacks, including metadata, not stale selected-model state. Await response handlers. Retain cancellation, sessionId, timeout, retry and transport options. [A/dist/types.d.ts:59–95,113–159; C/dist/core/extensions/runner.js:1066–1122]
4. Pump the native stream into a new `AssistantMessageEventStream`. On terminal `done` or `error`, await `emitMessageEnd({type:"message_end",message})`, apply its replacement and validate the final assistant/usage shape. Only then publish the terminal event and resolve the wrapper result. A terminal `error` uses `event.error`, not `event.message`. Also handle terminal-result-only/end paths and unexpected throws without leaving unresolved consumers. [C/dist/core/extensions/runner.js:864–905; A/dist/utils/event-stream.js:35–82,87–128]
5. Release the lease only after terminal processing and callback completion; abandon/recreate the activation if an interrupted stream leaves uncertain pending state.

**Fail-closed dispatch is additional host work.** Runner request/header/message handlers and generic `emit` catch exceptions, notify `onError`, then continue with previous values. Simply invoking those methods therefore is not a safety guarantee. With an isolated serial lane, collect per-dispatch errors and check them after each awaited call; a mandatory hook failure must prevent transport or acceptance of the untransformed successful result. The listener alone, without a gate, silently preserves Pi's fail-open behavior. Report possible already-sent requests separately; do not turn an accounting failure into a success or silently encourage blind retry. [C/dist/core/extensions/runner.js:812–839,864–905,1066–1122]

This placement covers generation **and compaction**: generation reads `runtime.models.streamSimple(...).result()`; compaction calls `completeSimple` and commits its usage separately. Generation's `beforeRequest` only transforms messages, not protocol payload/headers. `afterResponse` is preclassification but returns no replacement, and compaction has no corresponding final-response hook. Thus Durable hooks alone are not an equivalent general bridge; the Models/stream layer is the correct common boundary. [D/dist/harness/types.d.ts:555–607; D/dist/harness/generation.js:103–121,294–304,336,523–529; D/dist/harness/compaction.js:119–145]

## 4. Concurrency, stable IDs and asynchronous auth

The extension's cost state is a **Map keyed only by provider ID**, allocated inside each activation's `setupLiteLLMCostTracking`. A response with no valid header deletes that provider's slot. Two requests on one shared activation using the same alias can overwrite/clear each other's charge. Separate runner objects around the **same loaded Extension** do not help: handler closures still share that map. Native Provider instances alone do not isolate it either: the state is in separately registered event handlers. [L/src/index.ts:2234; L/src/cost.ts:3–32]

| Isolation choice                                              | Assessment                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One activation/runner for the server                          | Only safe if all requests through it serialize from response through final message, and request context is also serialized through auth/headers/payload. This destroys independent-conversation concurrency.                                                                                                                                                                                                                            |
| Fresh activation + runner + native providers per conversation | **Useful minimum.** Separate factory calls allocate separate cost maps. Serialize the entire request lifecycle within each conversation lane, including compaction and same-conversation auxiliary/tool model calls. Durable conversation identity is not proof that all such work never overlaps. Different conversations remain concurrent.                                                                                           |
| Fresh activation + runner per request                         | Strongest state isolation, including same-conversation parallel requests; no cross-request cost slot survives. But normal activation performs settings/auth reads and bounded seed discovery for every activation. This is heavier than cloning a runner; the public discovery loader does not provide a root-exported factory-cache/reinstantiate shortcut. Do not copy handlers or toggle global offline env around concurrent calls. |

A workable generic arrangement is a **routing Models facade** passed to Harness, with an owner/catalog runtime and lane-local native providers/runner state. Catalog reads retain stable `provider/model` IDs; `stream`, `streamSimple`, `complete` and `completeSimple` all pass through the routing layer. Select the lane from `options.sessionId` **before** lazy async auth/dispatch, not from a mutable global “current conversation.” Resolve auth once through native Models semantics and dispatch to that lane's captured native provider with the resolved options, or use a lane-local Models collection for the whole request. Never re-register each lane's `litellm` globally: native registration replaces by ID. The public registration actions, Provider interface and Models interface suffice for this composition; it is proposed host code, not an existing Coop facility. [C/dist/core/extensions/runner.d.ts:118–131; C/dist/core/model-runtime.js:627–635; A/dist/models.d.ts:65–128,129–198; A/dist/models.js:424–461]

For an API-key profile, auth/config/store roots must agree across catalog and lane activations. Independent activation reads can yield different settings if an owner changes them; version/config changes need a coordinated drain/rebuild, not silent mixed definitions. Ensure lane provider protocol/catalog availability cannot divert a canonical model into a global fallback. Pin request model metadata for both `ctx.model` and the final `modelRegistry.find` lookup; a public `ModelRegistry` adapter/subclass can delegate other operations while returning the in-flight physical model for that lookup. A real in-memory `SessionManager`, or an explicit narrow adapter, can supply only the persisted ID needed here without creating a competing Pi journal. This is a restricted adapter contract; no claim of full SessionManager behavior. [C/dist/core/model-registry.d.ts:21–56; C/dist/core/session-manager.d.ts:210–246,386; L/src/index.ts:2326–2335]

Durable supplies a persistent UUID `pi.provider.sessionId` for generation and compaction; forks get a new identity, restart preserves it. This routes lanes without changing stored model IDs. Calls with no sessionId need a host-assigned independent auxiliary lane or must fail explicitly for hosted providers. **Current goal naming calls `app.models.completeSimple` with signal but no sessionId**, so passing a facade only to Harness would miss it. Auxiliary calls need the same facade/context contract, not the selected conversation model. [D/dist/harness/provider.js:1–33; D/dist/harness/generation.js:113–118; D/dist/harness/compaction.js:119–126; src/server/goal-names.ts:87–103; src/server/app.ts:262–264,316]

## 5. Accounting and failure limits

- The unmodified cost handler replaces the local estimated total, not adds another charge, and apportions components **by token fraction**, not proxy-reported component prices. It uses `parseFloat` and accepts negative/nonfinite/prefix-junk values except NaN. Isolation fixes races, not parsing or provenance. A restricted supported proxy contract must provide well-formed finite nonnegative costs; the host must at least validate final usage, and should use an explicit declarative raw-header validity gate if strict parsing is required. Do not claim the extension itself validates it, or silently reinterpret token-proportional components as invoices. [L/src/cost.ts:13–18,33–51]
- Missing/headerless responses leave native rate estimates; discovery can publish zero for unknown rates. This is not evidence of free usage or complete actual-charge recovery. Budget/key-spend is a cumulative account value, not a substitute request charge. Header finality depends on the deployed proxy; previous research records the exact upstream evidence and its deployment limitation. [L/src/cost.ts:21,30–32; L/src/model-groups.ts:633–653; L/src/budget.ts:221–233; litellm-provider-reuse.md, §4]
- Correct terminal piping makes Durable commit transformed usage with the assistant entry, and compaction usage with its result. It does not require modifying Durable internals or revising already committed spend. [D/dist/harness/generation.js:523–529; D/dist/harness/compaction.js:138–145]
- Preserve cancellation during queued-lane acquisition and auth/transport. If cancelled after a response but before terminal processing, discard the lane or ensure terminal cleanup; otherwise its private pending map can affect the next request. Runner lifecycle shutdown does **not** clear the cost map. [L/src/cost.ts:3–53; L/src/index.ts:1911–1915]
- Durable checks its abort signal before classification/compaction commit. A request may already have incurred external charges even when its final usage is not committed after abort/close/crash. This host cannot guarantee a complete remote-charge ledger, and cannot safely repair it through late ordinary message events. Restart reconstructs ephemeral lanes, not lost response headers. [D/dist/harness/generation.js:314–315; D/dist/harness/compaction.js:129–131; docs/architecture.md, “Startup”]

## Minimum portable host feature matrix

| Feature              | Required supported behavior / rejection rule                                                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dependency loading   | Approved pinned package manifest via public Pi loader; no ambient project extensions; awaited activation; all load/bind errors fatal for selected provider.      |
| Registration/context | Native Provider capture, stable IDs, headless context, registry/request-model lookup, persisted session ID; unsupported actions throw.                           |
| Auth/config          | Native async API-key resolution/store/root headers; consistent agentDir; explicit unsupported-auth/helper/ADC policy, including startup reads.                   |
| Catalog              | Bounded seed/cache/explicit refresh, full metadata, availability checks; no empty-catalog success claim or silent model substitution.                            |
| Transport            | Both stream methods and completion methods, composed payload/header/response callbacks, signal/options preservation, mandatory-event error gates.                |
| Finalization         | Ordered message replacements, terminal event/result agreement, validated usage before generation/compaction persistence.                                         |
| Isolation            | Fresh extension activation per independent lane; serial same-lane requests or fresh request activation; abandon uncertain state.                                 |
| Auxiliary calls      | Physical model and explicit lane/session routing, including calls outside Harness; missing routing fails visibly.                                                |
| Unsupported paths    | Custom models/overrides/global API fallback, virtual routing, deferred/non-chat APIs and enabled optional gateways rejected unless separately implemented.       |
| Lifecycle            | Async startup before resume, provider presence gate, drain/dispose/rebuild on owner-approved update/restart; no hot replacement while requests use old closures. |

**Custom-model warning:** Pi composition can select a global API when the native base catalog does not contain that API, bypassing LiteLLM's guarded native stream. Piping hooks at the outer Models layer helps coverage but does not restore bypassed native root/protocol/tool guards. The first profile should prohibit overrides/off-catalog models for hosted providers and insist on discovered native paths; do not silently allow `models.json` to change this guarantee. [C/dist/core/provider-composer.js:372–388; L/src/provider.ts:96–137]

**Startup/missing provider:** Current Coop's `configureModels` callback is synchronous; the ordinary extension factory is asynchronous and may discover models before registration. Add an awaited provider-host startup gate before Harness resume, verify the selected package/provider and catalog, and recreate routing state on recovery. Missing/failed packages or aliases must produce owner-visible unavailable-provider errors, never fall back to another provider/model. Coop already resumes last, but the new host must fit that ordering. [src/server/app.ts:115,262–264; L/src/index.ts:1876,2110,2185; D/dist/harness/generation.js:103–105; docs/architecture.md, “Startup”]

### Decision

**YES conditional:** no fork or upstream change is inherently necessary for the API-key/discovered-chat subset. The maintenance burden moves to a reusable Coop-owned Pi provider-extension host: public activation, capability gating, request-local context/routing, serialized isolated state, generic event piping and precommit terminal replacement. None of that requires copying LiteLLM auth/discovery/policy algorithms.

**NO to broader claims:** simply installing/registering the package is insufficient; a shared runner is race-prone; event no-ops or fail-open handler errors break required policies; stored SSO and default-on gateways cannot be wished away; custom-model fallbacks and untagged auxiliary calls can bypass the host; header parsing/finality and aborted-request accounting remain limitations of the unmodified source/runtime. Future isolated validation is required before calling the conditional design supported in production.
