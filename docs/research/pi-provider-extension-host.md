# Hosting ordinary Pi provider extensions without forks

2026-10-11. **Source inspection only**, against installed Pi 1.1.0 and LiteLLM 4.2.0. No imports/execution of providers, installs, tests, activation, auth/secret-file reads, inference, network requests or restart. Only this note was written. `C/` below means `node_modules/@earendil-works/pi-coding-agent/`; `A/` means `node_modules/@earendil-works/pi-ai/`; `L/` means `/Users/enkelm/.pi/agent/npm/node_modules/pi-provider-litellm/`. Citations are to installed primary source, not the earlier recommendations.

## Answer

**Yes: an official-loader/runner host is a credible no-fork alternative.** Pi publicly exports the components needed to execute an ordinary extension with Pi's _actual_ `ExtensionAPI` and register its providers into the **same `ModelRuntime` supplied to Durable**. Coop need not copy Jiti aliases, implement a counterfeit `ExtensionAPI`, import LiteLLM's private auth factory, or require an upstream provider-library export. LiteLLM's ordinary extension constructs its own auth/discovery/provider objects and passes them through `pi.registerProvider`. [1][2][3]

The earlier requirement for a provider-only library entry was conditional on **not hosting Pi extensions**. It is not a blocker once this alternative is admitted. However, **registration is supported composition; Durable lifecycle/request parity is Coop-owned integration, not an SDK feature already implemented**. Loading an extension does not make its Pi session hooks run on Durable requests. [3][8][9]

**Strongest first path:** a dedicated, startup-only, owner-allowlisted **public Pi loader + `ExtensionRunner` host**, sharing Coop's runtime through `new ModelRegistry(app.models)`. Start with explicit provider-host semantics and no UI/tools/MCP; add a reusable request/event bridge only for the supported semantic subset. Prefer this over a dormant full AgentSession or stock Pi RPC. Do not advertise arbitrary Pi-extension compatibility or production LiteLLM parity before the concurrency/affinity/final-message issues below are resolved. No upstream changes are prerequisite to trying this architecture. [1][3][4]

Thus: **exact owner-selected loading without executing workspace/built-ins is possible; literal zero discovery through the public discovery function is not**. Coop must validate selected installed paths/version/manifest and controlled-root contents itself. An `extensionsOverride` is post-load and cannot undo unwanted execution. [2][4]

The loader handles TS and its host mappings internally, including current/legacy Pi names and `pi-ai` compatibility. Use root SDK imports and pin the host release. Packages must not bring duplicate host runtimes: Pi warns that physical copies can bypass mappings in compiled ESM. LiteLLM declares compatible optional peers and the TS extension manifest; its factory checks the actual host `VERSION`. No private alias import is needed, but singleton/version identity still requires dependency-tree verification. [1][2][6]

## Minimum runner host — no full agent required

The runner constructor requires **loaded extensions, their returned runtime, cwd, a real `SessionManager`, and a real `ModelRegistry`**. `SessionManager.inMemory(hostCwd)` is public; `ModelRegistry` is a compatibility facade over a supplied `ModelRuntime`. No selected model is required by `ExtensionRunner`. Use the loader's returned runtime; separately creating another runtime would disconnect the extension APIs from the runner. [1][3][7]

`bindCore` is not a two-method provider binder. Its public contract requires:

- **15 `ExtensionActions`:** sendMessage/sendUserMessage; appendEntry; set/getSessionName; setLabel; getActiveTools/getAllTools/getSettings/setActiveTools/refreshTools/getCommands; setModel; get/setThinkingLevel.
- **11 required context actions:** getModel/getScopedModels/isIdle/isProjectTrusted/getSignal/abort/hasPendingMessages/shutdown/getContextUsage/compact/getSystemPrompt. (`getSystemPromptOptions`, nested tool execution and callable tools are optional.)
- Optional provider/virtual-model registration overrides, optional UI, and optional command-context actions. The default UI is headless; command session-navigation defaults are no-ops, so leave commands inaccessible or explicitly reject unsupported operations rather than implying they worked. [3]

**Adapter-owned semantics:** real in-memory host entries/name/labels, settings snapshots, empty tool lists, diagnostic routing, selected request model/signal, and owner-controlled shutdown. Unsupported agent submission/compaction/navigation/tool actions should fail explicitly. These are implementations of an official host binding contract, not a fabricated full Pi API. They are nevertheless **not Durable conversation/session semantics** unless Coop deliberately supplies that integration. Omitting required bindings or reporting success for unavailable actions is not compatibility. [3][7]

### Registration is already piped

During factory loading the official API stages runtime changes; successful factories commit them, failed factories discard their pending changes/subscriptions. Before binding, provider registrations queue. `bindCore` flushes compatibility/native/virtual registrations into `ModelRegistry` (or the provided overrides), clears queues, then installs immediate register/unregister callbacks. Subscribe to runner errors **before binding**: flush errors are reported, not thrown as a startup failure. Coop must make those diagnostics fatal when required providers failed and must await catalog/availability synchronization. [2][3][10]

Registration overrides can enforce provider-ID ownership/conflicts and keep a cleanup ledger. The callback receives the provider/config, not its originating extension path; per-package runners or a host/package association are needed for precise attribution. Loader failure cleanup does not roll back arbitrary module effects, network activity or timers. [2][3]

`createAgentSessionServices({modelRuntime:app.models, settingsManager:inMemorySettings, ...})` is another **public infrastructure-only** path: creates/loads resources, flushes queued registrations into that runtime and awaits `refresh({allowNetwork:false})`, without constructing an AgentSession or selecting a model. It does **not** bind runtime action callbacks or dispatch `session_start`; a runner is still needed for ongoing extension use. Its diagnostics do not automatically abort startup, and loader errors remain in the resource result. [10]

## Auth and request lifecycle: reuse, but wire it explicitly

**Auth can remain entirely provider-owned.** LiteLLM's extension invokes its private `createProviderAuth`, constructs `createLiteLLMProvider`, then registers it. The shared runtime's public login/logout/getAuth/catalog/stream APIs invoke that provider; Coop already bridges `AuthInteraction` to browser prompts. No deep-source auth adapter is needed. [8][11]

**Important configuration limitation:** in-memory SDK settings and a supplied loader `agentDir` do not override extension code that imports global `getAgentDir()`. LiteLLM directly reads global settings/credentials and seeds models in its factory; its skills/MCP/budget features default enabled. `getAgentDir()` follows the process-wide environment/home, not runner cwd. A dedicated loader root prevents unrelated extension discovery, **not provider access to ordinary Pi configuration**. Existing Coop uses the same default Pi auth root, but a future isolated store must account for this mismatch. Do not temporarily change process-wide environment around concurrent live requests. A separate host process offers a cleaner independent environment. `allowNetwork:false` on SDK refresh also does not constrain the factory's own discovery. [8][12]

Official AgentSession wiring supplies the pattern for a Coop-owned bridge:

1. public request `transformHeaders` → `runner.emitBeforeProviderHeaders`;
2. public `onPayload` → `emitBeforeProviderRequest`;
3. `onResponse`/stream-event callbacks → runner response/stream events;
4. terminal assistant → **`emitMessageEnd`**, honoring its replacement result _before_ Durable persists/classifies/accounts for the message;
5. explicit startup/shutdown and any deliberately supported context/turn events. [9][13]

These are reusable SDK seams. **No bridge exists automatically merely because Harness and runner share models.** Durable's `Models.streamSimple` boundary can be decorated to attach callbacks and transform terminal messages while forwarding catalog/auth to the canonical runtime. That is Coop-owned `Models`/event-stream integration, not a second provider runtime. Durable's `beforeRequest` sees normalized messages, not provider payload/HTTP headers; its `afterResponse` returns void, not a message replacement. Emitting generic `runner.emit({type:"message_end", ...})` also ignores replacement returns: use the dedicated method. [9][13][14]

### Semantic limits that must not be hidden

- **Conversation identity/concurrency:** a runner has one fixed SessionManager/cwd and extension instance. `getModel` is host-bound; it must represent the actual request, including routed models. A mutable global “current model” is unsafe with concurrent Durable conversations. Request-local bindings can address model/signal, but do not make the fixed SessionManager represent different conversations. LiteLLM adds its session ID from that manager, independently of Durable's request `sessionId`. Decide explicitly whether it denotes one provider-host session or a true conversation; the latter needs additional design. [3][8][14]
- **Extension-owned shared state:** LiteLLM costs are queued **by provider, not request** between HTTP response and `message_end`; concurrent requests to the same provider can overwrite/consume each other's costs. Request-local context alone cannot fix that closure. Full logical-request serialization or correctly isolated extension lifetimes is required for that behavior; neither is free. Loading independent per-conversation hosts into one runtime also needs a registration/ownership design, because providers/auth closures may be replaced or diverge. No general solution is proven here. [15]
- **Feature parity:** LiteLLM request policy, final think-tag normalization and cost replacement are outside bare registration. Skills, MCP and budget behavior use additional tools/prompt/events/UI; budget polling skips headless session startup. Explicitly disable unsupported features through provider-supported configuration or document their absence; do not silently claim they are hosted. A real official loader permits registration of these features but does not adapt them to Durable. [8][15]
- **Error semantics:** runner event transforms commonly report errors and continue. Coop must observe diagnostics and choose whether a required policy failure prevents dispatch. Do not assume thrown handler errors always block a request. [13]

## Compare the three no-fork choices

| Choice                            | Supported advantage                                                                                                                                                                                                                                           | Remaining cost                                                                                                                                                                                                                                                                                                                                                                            |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Loader + runner (recommended)** | Real Pi API/TS loader; no Agent/selected model/inference needed; direct same-runtime registration and native auth.                                                                                                                                            | Coop owns required action/context semantics, event piping, diagnostics, concurrency and cleanup. Provider-host subset, not arbitrary agent-extension parity.                                                                                                                                                                                                                              |
| **Dormant full AgentSession**     | `createAgentSession`/services and `SessionManager.inMemory`, `SettingsManager.inMemory`, supplied shared runtime are public. Real agent actions/runner wiring; `bindExtensions` emits startup, `AgentSessionRuntime.dispose` emits shutdown then invalidates. | Those hooks run on that AgentSession's requests, **not Durable's**. Calling `prompt()` introduces a second agent/tool loop, not provider piping. Merely keeping it dormant still needs the Durable bridge and context mapping. `noTools:"all"` disables agent tools, not factory side effects. [7][9][16]                                                                                 |
| **Subprocess Pi service**         | Official RPC hosts ordinary extensions and gives process/environment isolation. A custom child service built against public SDK can also expose a Coop-owned provider protocol without modifying Pi/packages.                                                 | A child cannot share the same JS runtime object. Stock RPC is session/prompt control, not `Models`/provider-stream/auth transport; it exposes no direct `streamSimple` or provider login command. Stock prompting runs Pi's agent loop. A custom service needs its own auth/catalog/stream/cancellation IPC and proxy `Models`/Provider facade in Coop. More isolation, larger seam. [17] |

**“No model selected” is genuinely supported by the services-only/runner composition.** Full session creation tolerates no available model, but omission is _not_ a force-no-model option: SDK attempts settings/default/first-available selection. With none, agent-core stores an `unknown` placeholder; the session getter returns that object. Do not promise literal `ctx.model === undefined` in a dormant full session or rely on it as an inference guard. None of these constructors inherently requires paid inference, but trusted factory/hook code can itself perform I/O or request work. [7][9][18]

## Lifecycle and recommendation boundary

Coop should own package pins/allowlist, startup gating and provider-ID ledger; retain one canonical runtime. Initialize the selected host **before Harness opening/resumption**. After Durable and auth operations have drained, emit/await `session_shutdown`, inspect diagnostics, invalidate the runner, then unregister owned providers/virtual models and clean host-owned resources. Runner invalidation removes tracked event-bus subscriptions and blocks stale API use; it does not unregister providers, clear extension timers or drain streams/logins. Even `AgentSessionRuntime.dispose` does not dispose native provider objects or unregister them. Use owner-approved restart activation initially, not hot replacement. [2][3][16][19]

**Recommendation:** pursue the official runner host, not a mandatory upstream library export. Keep the package unmodified and the adapter provider-agnostic; require explicit compatibility limits for provider packages whose behavior assumes a whole Pi session. The strongest source-supported conclusion is **registration/auth hosting is feasible today through public APIs**; multi-conversation request/lifecycle parity is feasible integration work in principle but **not proven plug-and-play**, particularly LiteLLM cost/affinity behavior. A dormant session adds little for the provider-only objective, while subprocess hosting is the fallback when configuration isolation or uncooperative cleanup justifies a larger protocol.
