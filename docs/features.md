# Pi Pocket features

The full tour. For setup, see the [README](../README.md). This fork retains Pocket's existing features below; retaining them does not mean each has been extended or fully revalidated here.

- **Compact application reports.** Native Work Item, exact-thread and private helper reports use quiet expandable step rows, not ordinary assistant answers. Source links retain their captured destinations; details preserve the full evidence and warnings. Held delivery uses caution text/color, never a green success certificate. Questions and attributed agent answers stay expanded. Blank/tool-only outcomes do not produce fresh reports, and repeated hints or reloads do not recopy an old final. Separate source events with identical text remain distinct. Display and navigation do not activate work or change authority. Recognized historical native reports remain readable without rewriting stored history; untrusted lookalikes are not folded.

- **SSH workspaces.** Project/thread creation keeps the inherited folder compact; only the owner sees **Change** and local/SSH destination options. Collaborators can create threads in owner-granted SSH projects at their saved host and directory. SSH setup, discovery, login, browsing and destination changes stay owner-only. Pinned visible project work can use the owner's current exact-host password login through the service without exposing a password or login status; grants and both identities are rechecked, and forget/expiry/rotation revoke old authority. Remote projects share a status-dot icon in the picker and sidebars, based on recent explicit use rather than background probes. Folder, Files and review reads share one SFTP transport within each request instead of reauthenticating for every path check; requests never share credentials or retain a connection afterward. Thread types, workflows and handoffs retain their usual controls; files, Git and project scripts use the pinned SSH destination, while agents/models/history, research and external acquisition stay on Coop. Changes, branches, worktrees and review diffs/comments use the destination backend. Managed commands require target-native offline confinement and fail safely when it is unavailable. Helpers, linked threads and forks inherit the target. The owner can choose passively discovered SSH aliases/known hosts, including nonstandard-port URIs, or enter a host manually. Existing SSH configuration/key authentication is used, with owner-only expiring memory-only password login over HTTPS/localhost. No remote Coop service or terminal dashboard is installed. Failures never switch to local namesakes or replay uncertain mutations. Files quick edits and expanded review context require native Python 3 file-identity checks, with no weaker save fallback. Remote skills/templates/model defaults use explicit host-owned project trust. Platform confinement, resource ignore matching, language services and watchers retain documented limits; see [SSH support and limits](projects.md#ssh-workspaces).
- **Rust/GPUI terminal renderer.** Herdr’s Terminal view uses the pinned Rust/WASM painter with no Canvas2D alternative or renderer toggle. The existing connection, browser-owned input and parent geometry remain intact. Focusing another pane in the same split retains acknowledged pixels without a renderer-loading flash; changed input targets still wait for their own paint receipt. Startup/failure blocks blind input and offers an explicit renderer-only retry without reconnecting or replaying input. The bundled Nerd Mono font covers ordinary terminal symbols and private-use icons. After owner sign-in, idle background loading downloads/compiles the public WASM once per retained revision; Terminal entry and renderer retry reuse it without hidden GPU windows or terminal control. Fresh manifest checks pick up new builds, and failed preloads can recover. Hashed static assets support immutable caching and gzip; private terminal content is never cached. Browser/device rendering and performance remain unverified. See [build and lifecycle details](../native/herdr-renderer/README.md).
- **Handoffs and Work Items.** Use the header's **Choose next thread** button for a two-step role/steering popup, ask for a handoff in ordinary English, or use `/handoff [role] [--new] [instructions]` in the message box. The popup closes when its input is accepted, without waiting for the summary or successor. It stays dismissible even during a slow send; rejection and close/reopen preserve selection and steering, and late responses cannot close a newer popup. Argument autocomplete shows state-based roles, same/new-work choices and reasons for unavailable options. In the picker, repeated blocking reasons appear once above the choices; destination-specific reasons stay beside their disabled option. Tab or a tap fills the draft without sending, leaving room for steering instructions. Those instructions guide the summary and are saved verbatim with it in a temporary Markdown file. The successor receives a prompt to read that file with the existing read tool, on the local or SSH target filesystem. There is no separate context-file feature or repeated inline summary, and no handoff-specific editorial length cap. Available choices come from app state, not an agent recommendation or readiness declaration. The actual message is accepted once and the composer clears without waiting for the handoff. There is no second app-generated message pretending to be you. The agent infers a clear intended type or asks a follow-up if the request is confusing, ambiguous or unavailable, then executes the handoff tool with its brief. The runtime enforces state-based transitions and atomically creates the successor, transfers the active-writer position and makes the predecessor permanently read-only. A model names the new thread from the received summary; retries do not apply or bill a completed naming response twice, and a manual rename wins. Other work must settle before transfer; only the executing tool's own invocation/run and exact incoming placed courier are exempt from the full task-graph check. A compact status indicator sits inside the chatbox; thread navigation stays in the sidebar, not the composer. Same-work threads share an expandable Work Item named after its first thread; move, archive and restore apply to the whole item. Accepted input, summary delivery and tool receipts survive restart. An opaque input correlation restores navigation in the initiating tab. Already-accepted summary/delivery work retains core recovery tasks; there is no public summary-first admission or retry path. Automatic redirect is limited to the initiating tab/user while still on the source thread. The `handoff` tool supports status/start, not agent-authored readiness gates or automatic advancement; an explicit slash-command role/relationship cannot be changed by its call. See [handoffs.md](handoffs.md).
    - **Source-aware agent handoffs.** One public `handoff` tool derives authority from its actual caller. Execution mains retain human-correlated transfer/retirement; named main Chats can create native starter Work Items/controllers or send a saved brief to an exact supported recipient while keeping their originating Chat. Creation returns the real accepted controller-send identity, directly usable for wait/continuation without another assignment. Controllers transfer only their exact observed active execution source and retain their own Chat. Access, models, budgets, questions, helper settlement and publication safeguards remain native; unsupported cross-filesystem brief delivery refuses rather than retargeting. New `session_start` calls create ordinary Chats; accepted legacy workflow calls remain replayable.
    - **Same work.** Worker offers Reviewer (only with a nonempty current Pi diff, not historical committed edits or a new checkpoint alone) or Researcher; Reviewer offers Follow-up, Worker, Land or Researcher; Land offers Publish, Worker or Follow-up; Follow-up offers Land or Worker; Researcher offers Worker or Follow-up; Pull offers Worker, Researcher or Follow-up. Publish is the delivery/end stage, without additional same-work edges to Worker or Follow-up. Pull is also available from any stage other than Pull. Land remains available after any earlier Reviewer in that Work Item. Follow-up needs a Reviewer or Pull in the same-item history, counting the current thread. The same role cannot follow itself within one Work Item. `/handoff worker` means same-work without a `--same` flag.
    - **New work.** Every active stage offers Worker, Researcher and Pull as new Work Item starters, including the current starter type. Use `/handoff worker --new`, `/handoff researcher --new` or `/handoff pull --new`. The summary distinguishes the new scope from unfinished previous work.
    - **Evidence and authority.** Worker handles research, planning, implementation and focused checks; Researcher provides cited investigations; Reviewer independently inspects code, test quality and wider regressions; Follow-up repairs bounded gaps after review or Pull. Results must distinguish actual passes from failed, unavailable or deferred checks; research and self-attestation are not independent review. Existing review/checkpoint and historical validation-risk acceptance records retain their evidence, named gaps and decision history, but no longer unlock or block thread creation. Land has no review/readiness/checkpoint/risk-acceptance admission gate and does not itself authorize commits, rebases or cleanup. Publish follows Land for pushes, PR creation and ticket updates, using the actual clean Publish checkout and separate human approval for each exact external action. Single-writer ownership, retired roots, offline shell and publication content-pinning/uncertain-receipt protections remain enforced; selecting a thread is never publication approval.

- **Work Item execution.** Work Items and its built-in agent profiles are part of the app, not an optional extension. The owner pauses or resumes **Work Item execution** in Settings → **Agents**. Work Items is not listed in Extensions. Turning it off pauses execution without hiding profile instructions, history or controls. Non-Chat built-in starters and new built-in handoffs are unavailable, and managed writes are blocked. An earlier disabled Work Items setting stays paused after upgrade until the owner explicitly changes the native control; it never silently resumes work. Accepted transfers and passive receipts remain recoverable, but recovery grants no bypass for new managed effects. Retired writers remain permanently read-only. Ordinary ungrouped Chats and Agent Teams continue independently, without joining a Work Item. Owner prompt overrides stay intact. Third-party namespaced workflow profiles remain independently loadable; missing or unknown managed profiles stay restricted, never become unrestricted Chats. Permission checks, offline execution and individual external-action approvals remain mandatory. See [the pause and compatibility contract](handoffs.md#availability-and-execution-pause).

- **Private Herdr mirror.** The owner gets a separate **Herdr** sidebar tab with a theme-colored ram-and-terminal mark, beside **Collab** with a people icon. Herdr is grouped by local instance, workspace, tab and pane. Collab and Herdr fill their two-button track without changing height when selected. Spaces and Agents fold independently; their rows follow the chosen theme's corners. Spaces nests linked worktrees under their repository with branch names and local collapse controls. Supported agents have a labeled Import action with a tray-and-arrow icon; confirmation is still required before sharing. Opening it leaves agents running in their terminals. Private Chat reuses Durable's transcript layout, user bubbles, assistant messages, thinking and paired tool cards, plus its compact message box and send control. A passive visible-terminal snapshot stays collapsed below saved messages; verified idle Pi panes accept prompts, native slash commands and private file uploads through the bridge, never a Durable room. Chat offers command completion and the shared model picker; model changes follow saved Pi configuration. Attach files with the paperclip, paste or drag/drop; Pi receives private server paths and reads the files, including images. Terminal-only dialogs and multiline/shell input still need Terminal mode. Chat is read-only for shells, other agents and busy/blocked Pi. A separate [structured Terminal view](terminal-mode.md) controls existing Herdr terminals. It defaults on desktop, connects on opening, and reuses existing connections across foreground navigation without replaying input. Hidden/offline pages close terminal sockets; returning reconnects only an open Terminal view, not a retained connection behind Collab or Chat. Metadata/frame availability updates do not repeatedly reannounce unchanged geometry to shared panes; real viewport changes and fresh connections still resize as needed. Desktop uses Herdr keyboard bindings; mobile gets a full collapsible touch keyboard with letters, numbers, symbols, function/navigation keys and one-shot or locked Ctrl/Alt/Cmd/Shift. Touch and Native form a keyboard-type button group in the bottom-right footer, with a chevron beside them to collapse or expand the selected keyboard. The tab/split/zoom quick-action bar stays, with a Paste icon at its far right visible only in Touch/UI keyboard mode. The footer type selector remains available to switch back from Native, and modifier guidance stays in Help. It does not open the native keyboard unless explicitly selected. Paste opens a normal text field for the phone’s paste menu; Paste into pane sends the text without an extra Enter or clipboard permission. Cancel or a target/connection/access change clears the paste draft. The Rust/GPUI/WASM painter owns terminal pixels; the parent retains its DOM input, cursor and geometry. Herdr prefix chords survive focus moves between on-screen keys, while leaving the terminal cancels prefix mode. Wheel/touch input stays immediate and retains fractional movement across pointer positions. Remote scrolling still waits for Herdr; there is no local history cache. In terminal panes, swipe to scroll; hold, then drag, to select text. A small hold-point pulse (static with reduced motion) confirms selection without moving the terminal; pinch zoom remains available. Temporary Terminal Help → **Copy diagnostics** exports a bounded memory-only metadata report for the ongoing scroll-jump investigation, without terminal text or key values; clipboard failure offers a selectable report instead. The terminal and Safari parity checks are still in progress. **Import & share** copies the selected Pi's saved branch into a shared Durable conversation. Pi keeps running, even when busy; no abort or stop is sent. The full source archive stays owner-only. Guests cannot list or read private panes. See [the private bridge contract](private-sessions.md).

- **Move a Pi session by copying its history.** **New Session → Import** has one **Live / History** picker for owners and retained legacy guests explicitly allowed to continue local Pi sessions without project or session scope. **Live** lists local Herdr Pi instances. Select one, review the destination model and confirm **Move** to copy its last saved branch into a Durable Chat. Busy Pi is allowed and keeps running. Move never sends Escape, aborts work, stops or signals Pi, closes panes or writes its journal. Changed process/session fingerprints require refreshing the list; changed saved bytes require a fresh preview. **History** shows saved-session title, working directory, path and recency. Search by title or path and select a row to open the same model and Move confirmation, with short selected-branch excerpts folded below. Preview alone creates no conversation or work. **Advanced import** accepts manual file/branch entry only for the owner. Owners choose **Private / Shared** and an optional project in import confirmation; Private remains the default. A permitted guest must explicitly confirm sharing the copied conversation. The owner can later choose **Share imported Chat…** in the Chat menu or sidebar Options to share its complete current history and future messages without re-importing or needing the source file. Shared means existing authenticated project/invitation access, never anonymous access; unassigned imports need an exact-session invitation for project-only collaborators. No older import or private fork is automatically exposed. Every new copy is a Chat with an **Imported from Pi** origin label, not a separate thread type. The source archive stays owner-only. No unfinished request or tool is resumed here; unavailable tool results say the original tool may have run or may still run. A cut-off final JSONL record can be omitted from copied history while remaining intact in the archive; malformed complete records still fail. There is no separate stop-and-move or takeover recovery flow. See [the import contract](import-implementation.md).

- **Durable runs.** Every model request, tool call, queued message, and subagent is a durable task in one SQLite file. Kill the server mid-run and start it again: the run continues. A tool call that was cut off reruns if it is safe to; otherwise the model is told it was interrupted.
- **Settings.** The rightmost button at the foot of the session list opens one popup with **Appearance**, **Providers**, **Agents**, **PiP**, **Notifications**, **Extensions & safety**, **Account & access**, and **Usage & limits**. Settings uses nearly the full phone viewport and a larger centered workspace on iPad and desktop (up to 1200 × 960px). Categories sit in a sidebar on tablet and desktop and a scrolling tab row on phones. Controls stack or wrap to the content panel’s width, including iPad Split View. Panels load on their first visit, then keep their drafts, search and scroll position across tab changes without adding back steps. **People** and your name open Account & access; the launcher offers direct shortcuts to each category. The menu, home screen, folded sidebar and `/settings` open the same popup. `/login` goes straight to Providers; `/theme` without a name goes to Appearance. Provider sign-in, extensions, access changes and budgets keep their existing owner-only rules. Invites and provider sign-in prompts remain separate flows; back returns to the selected Settings category. Session-specific model, folder and instructions controls remain in the session UI.
- **Agent prompts.** Settings → **Agents** lists Chat, Researcher, Worker, Reviewer, Follow-up, Pull, Land and Publish with their matching thread-type icons and a read-only role-specific system prompt for each. A floating pencil icon opts into editing. Save, Restore default and Cancel then float directly over the prompt's top-right corner, without a reserved topbar or grouped toolbar background. Save returns to read mode; Cancel discards the draft and exits editing. Failed saves keep editing available. Desktop hover or keyboard focus reveals them; typing hides them until the pointer returns or focus leaves the field. Touch controls stay visible when not typing. Only the owner can view or edit these app-wide instructions. Save applies to the next model request in existing and new threads, including delegated helpers; changes persist across restarts. Restore default fills the editor and requires Save to apply. Switching categories keeps drafts, failed saves keep them too, and a stale tab cannot overwrite a newer prompt. Shared system guidance, repository/session instructions and hard execution permissions remain separate. Shared rules override saved legacy prompts that prohibit executing a clear human-requested handoff, make the tool status-only, ask agents to prepare/recommend handoffs or attest readiness. This does not configure private Herdr agents or create new agent types.
- **Themes.** A theme changes the app's look and layout without a change to its code: a folder of CSS, fonts, images, and optional colors (`docs/extensions/themes.md`). Appearance has a **Theme** row above **Colors**: **Pocket**, the app's own look; **Lantern**, a calm, warm dark theme that comes with the app, made for reading for hours (warm brown-grey with warm off-white text and a muted amber accent, one readable column of about 72 characters, tool calls as one quiet line until opened, and your messages set off by a quiet amber bar instead of cards); and each theme folder. A theme stays when the colors change; one with colors of its own brings them when you choose it. The owner can **Duplicate** the theme or the colors in use into a folder of their own (in the data folder's `themes/`), **Edit with Pi** (a session in the theme's folder, with a message ready that names the guide), and **Remove** one (its folder moves to `themes/.removed/`). Each save shows at once in every tab that uses the theme, without a reload, and a reload never flashes the app's own look. A theme loads only its own files; one that breaks a rule keeps its last good version, and the owner is told what and where. Each person chooses for each browser, guests too, and the owner can make the theme and colors in use the default for genuinely new browsers. Existing saved preferences remain personal and are not automatically rewritten. Layout, font and saved Dark/Light assignment edits keep a new browser following that default; explicitly choosing a mode, colors or a theme opts it out. The launcher's Themes and `/theme <name>` choose themes as well as colors. A theme can bring a pair of palettes, dark and light, that follows the system's setting using its own halves; explicitly choosing System from the mode selector instead uses your saved Dark/Light choices. Safe mode (`?noext=1`) loads no theme.
- **Standalone colors.** Bundled palettes, from Tokyo Night and Gruvbox to Rosé Pine and the light ones, kept independently of the server desktop, in soft tiles: rounded windows and controls on 1px hairlines, soft shadows only on what floats, bundled Geist and JetBrains Mono (`web/fonts/`, SIL Open Font License), with a separate UI font choice and monospace code, paths, and numbers; light themes too. Settings → **Appearance** (or the launcher, or `/theme gruvbox`) picks one under **Colors**, as well as a theme folder's `colors.toml` (any Omarchy theme folder dropped into `themes/` shows there); click a palette card to switch the live colors and their natural mode. The launcher's live previews remain temporary until committed, and leaving without choosing restores the saved colors. The new look grows as a circle from where you tapped. Themes are local to this browser; no server desktop-theme or wallpaper synchronization runs. Desktop is not a color source and cannot be duplicated; an obsolete server default falls back to Tokyo Night.
- **Color modes and fonts.** Appearance's **System / Dark / Light** selector activates separate saved Dark/Light palettes. Hover, keyboard focus or a long-press on a palette card reveals moon/sun buttons that save those slots without changing the current look or mode. Slots can also use a theme folder's palettes; they keep each palette's native colors rather than recoloring it. System follows later device changes and resolves the device's current preference when the app reopens. Clicking a palette card, committing a launcher palette or running `/theme <palette>` chooses the live palette and its natural mode without replacing the saved slots. The font picker offers bundled **JetBrains Mono**, **System sans**, **System mono** and **Serif**; its browser-local stack is cached for first paint while code and terminals remain monospace. Touch holds can be cancelled by movement or another gesture; a secondary touch cannot steal the primary hold. Assignment controls are keyboard reachable, and a hidden retained Appearance panel cannot consume Escape.
- **Sheets and controls.** Sheets have a 56px title bar on wide screens, a back chevron when opened from another sheet, grouped inset lists, round toggles, and segmented settings. On phones they keep their bottom-sheet grip and drag-to-close gesture. Text sheets have Cancel and the main action together at the bottom; all existing keyboard and back flows stay available. Buttons, fields, and search share the same rounded controls across the app.
- **Background connections.** Hiding the app or going offline closes the main event stream/long poll and pauses connection retries. Returning while online reconnects once and refreshes the current conversation, without clearing drafts or resubmitting messages. If web files changed while disconnected, returning also reloads the app to pick up those changes. This does not stop server-side agents or schedules. Browser frames, private Chat reads and editor language-server polling also pause while hidden/offline. Editor language support releases its lease and reconnects on return without replacing the unsaved buffer or cursor. Herdr terminal sockets also close while hidden/offline; returning reconnects only a mounted Terminal view with fresh state and no replayed input. Work Items eligibility reads and polling suspend too, aborting stale work and refreshing once on return. Only an open Handoff picker admits its recurring eligibility timer; controls otherwise refresh on relevant context changes, and opening, Refresh and routing hints request fresh options. The picker recovers after suspension without losing its draft. Live transcript and subagent elapsed clocks also stop while hidden, catching up from real time on return. Pagehide keeps these suspended until pageshow. Herdr snapshot reads retain their existing 4-second list / 2-second pane delay after completion, but no longer rerender unchanged content just to advance its capture timestamp. These changes do not establish a measured iPad battery improvement.
- **Tiled windows and motion.** Private Chat and Terminal use the same outer windows as shared sessions; their compact controls stay unchanged. On wide screens the sidebar and the session are Hyprland windows, softened: 8px gaps, rounded corners on a hairline, and a soft accent ring on the one under the mouse. Motion uses Omarchy's Hyprland curves: windows pop in at 87%, sheets and popovers rise a little as they fade in, and leave quickly, new messages slide in, and notices count down until they go. While Pi works, the conversation shows what it does; working sidebar rows use the same square-quadrant spinner as chat. Idle state squares stay neutral, even in the active row; unread results, people-chat messages or manual unread marks fill and pulse the square until read. Reduced motion holds the spinner still and keeps the unread accent without its pulse. Peek tiles keep quieter static working marks. Appearance can turn tiling off (no gaps, square corners, no ring), reduce motion (or follow the system's setting), change the conversation's text size (13 to 17), set the width (Comfortable, which grows with a wide window, Wide, or Full: how much of the window the conversation and the message box take, per browser; phones stay as they are; a reply's code block with long lines grows past the column, centered on it, where plain text and Markdown wrap in the column, and a wide table grows toward the window's edge), set the density (Comfortable, Compact, or Tight: less room between turns, inside message cards and activity groups, between the conversation's lines, in the session list's rows, around the message box and the status line, in sheets and their lists, and in the top bar, while font sizes stay and rows on a touch screen stay a thumb tall), show Pi's thinking while it works, and show the reply speed under the message box.
- **Projects and typed threads.** Collab opens **Projects** first, followed by **Recent** and **Archived**. A project has a name and default working directory, and contains threads and Work Items directly. Each project folds independently. A project's thread count leads its title, after the disclosure chevron. On desktop, project Add/Edit controls appear on hover or keyboard focus; hidden controls take no width, leaving room for header names and counts. Hover highlights the full header row without dimming its text, with corners supplied by the chosen theme. Right-click a header, use the Context Menu key / Shift+F10, or hold it on touch for its existing actions in Options, including New Session here and Edit project. Touch also has an explicit Options button. Their **+** actions open New Session prefilled there. New project threads default to Worker, with Researcher for investigations and Pull for upstream work. Blue agent icons identify **Worker** and green speech-bubble icons identify **Chat** at the left of sidebar rows without a background or border; **Researcher** uses a brain icon. Running state sits on the right and the conversation header keeps the labeled tag. Every standalone thread shows its path and current Git branch before any handoff groups it into a Work Item, including ordinary checkouts without a Coop-created worktree. A detached checkout shows its short commit instead; outside Git, the model remains the fallback context. Ordinary untyped Collab threads become Workers on upgrade, remain unassigned and appear as normal rows; untyped linked roots stay independent Chats. Explicit types are preserved. New one-time Chats can stand alone; type remains independent of project placement. Defaults never move an existing thread's folder and membership alone never grants access: owner-authored project grants define collaborator visibility. Agent tools for project/thread creation and cross-thread prompting remain future work. See [projects.md](projects.md).
- **The sidebar.** A rail and the session list beside it. The rail holds Pi (which goes to the home screen), Sessions (which folds the sidebar to numbered sessions and unfolds it again, as Ctrl/⌘+B does), the tools (Peek tiles, where the server has them, lit while they are on; Running now, with how many sessions work; the subagents board, with how many subagents work or wait, and a red mark when one waits for you or failed and nobody has dealt with it yet; People; Providers, for the owner; Theme), and you. On Projects-capable servers the list opens Projects first, then Recent and Archived, with sessions grouped by project or by day, in groups that fold; pinned sessions stay on top in Recent (per browser). Older servers retain the Folders view. Top-level session rows show a Worker/Chat icon, title and state mark, with the path and current branch beneath; Work Item member rows stay compact. Older servers keep the state mark at the start. The shared quadrant spinner means Pi or its subagents are working; two bars mean a call waits for you; a cross means its run failed. Waiting and failed marks keep the folder's color. A neutral hollow square means read or never run; an accent-filled pulsing square means a completed result, people-chat message or manual unread mark is unread. The title is semibold with a new result or chat, when marked unread, or when open, and the open row keeps its quiet active fill. The right side also shows a small pill with ⑂ and how many subagents work there (or failed with nobody dealing with it yet, in red), followed by the vertically centered loading/state indicator, who else is there, a "needs you" or "waiting" pill while a call waits, and how long ago; its folder and model are in its tooltip. Hover a row to archive, pin or mark it unread. Mobile rows omit the cog and keep the hold chooser. Right-click a thread or press the Context Menu key / Shift+F10 for its actions without opening that conversation. On touch, hold a row to reveal **Drag | Options**, then slide deliberately onto a half and dwell: that half expands across the row and briefly fills before starting the drag or opening Options. At tablet widths (700px and up), Options opens beside the contact, including on touch-only iPads; narrow touch layouts keep the bottom sheet. Mouse right-click and keyboard context requests open an in-place menu at every width, including narrow iPad Split View. A stationary hold never chooses; early release, leaving the row, another finger or cancellation does nothing. Switching halves restarts the dwell. Reduced motion keeps the same timing without expansion. Options keeps pinning, marking unread or read, archiving or restoring, and Select. On Projects-capable servers, drag threads onto projects, or onto the temporary **No project** target at the end of the list to clear placement without shifting existing rows. Collapsed destinations open on hover; hovering Projects switches from Recent and dragging at the list's edges scrolls it. Options → **Move to project…** opens the same placement picker for touch and keyboard users; selected threads can move together with **Move…** or a drag. Placement keeps history, type, archive state and working directory; it does not add manual row ordering. Marks are per browser, like pins (a session's square counts as read here when this browser opens it, or has it open in sight as its run ends; a failed run's cross stays until its next run starts, and a restart forgets it), and opening the session clears its mark; the session's menu marks the open one unread and goes back to the list. Completed-result read tracking stays active with peek tiles off, survives reloads and updates across tabs; people-chat read marks remain separate. A session that another one started (Agent Teams) shows under it, with a branch line to it, as deep as they go (up to three steps of indent, so a phone's list keeps its room), and the numbers (Alt+1…9, the folded rail) follow the tree; a pinned one stays among the pins, and in the older-server Folders view one in another folder stays in that folder's group. Someone who cannot see the session that started one sees it as a session of its own. A session moves up the list when it is renamed, gets a message, or Pi starts work there for any other reason (a scheduled message, a subagent's report, a message sent again after a restart), so the one that ran last is on top. Archiving says so in a notice that undoes it. Ctrl/⌘+click selects sessions, Ctrl/⌘+drag selects every row it passes (the list scrolls at its edges), and Shift+click selects a run; on a touch screen, after **Select**, taps select more rows or let them go. A bar under the list archives, unarchives, or pins them, and Esc (or back, after Select) lets go. Archiving does not move a session in the list, so one brought back returns to where it was. Drag its edge to resize the list (to 40% of the screen at most), or fold the sidebar to the rail with numbered sessions, like Waybar's workspaces. On phones the drawer and the list with no session open have the same rail. On wide screens with no session open, the home screen shows a fastfetch-style summary, buttons for a new session, the launcher, and Appearance, and the sessions to jump back into.
- **Peek tiles.** Off until you turn them on: the menu's **Peeks** tile, Alt+P, `/peek`, the launcher, or Appearance switches them on or off in one step, and so do the rail's **Peek tiles** button and the tiles button in the top bar, which shows wherever its pane is 480px wide or more (while off, it has a dot when another session waits for you). Then other sessions' live work shows beside the one you are in: one tile per session that is working, waiting for an approval, finished since this browser last had it open, or pinned, plus the one you just left. Each is a card with the session's folder square, title, and path, its last three lines (what was asked, what Pi said, its tool calls and how they went, each in two lines at most, with a mark for who or what said it), and a footer with its state in words; it changes at most once a second and keeps its working square still. Click a tile to open its session; the one you leave takes its place, so the tiles stay put. A watch can be narrowed to a label, to issues assigned to you, or to a branch's CI (mentions of @pi are not narrowed). CI is the branch's own runs: pushed to it, scheduled, started by hand or through the API, or started by another workflow, in the repository itself, never a pull request's or an issue's (a renamed repository keeps working). Only repositories `gh`'s account can push to can be watched or worked on, and issues and pull requests count only from the repository's owner, and organization members and collaborators whom GitHub says can write to it (and bots' pull requests), unless you turn on **From anyone** on the watch in Menu → Webhooks and watches (PiP cannot); @pi always only from them. PiP works in a checkout of a session you started, or in a clone it makes, which appears only once complete (a clone a restart cut off leaves a `~part-…` folder, removed at the next clone of that repository); a different folder already where the clone goes is reported, never overwritten. While Triggers is off, watches wait and ask GitHub nothing; while PiP is off, a watch to PiP holds what it found, and its note says so. What came from GitHub is fenced as data, each thing is told once, ten in a message and twelve messages an hour at most (the rest come next), and a look that fails is tried again, less often each time, with the reason shown. Menu → **Webhooks and watches** lists the watches, to remove one; or ask PiP ("what are you watching?", "stop watching acme/api"). PiP can also start a PR watch on a session ("see acme/api#12 through"), and Pi's own `watch_pr` takes a PR in another repository it can push to by its address or `owner/name#12`, telling Pi to work in a checkout of it. Part of the **Triggers** extension.
- **Webhooks.** Menu → **Webhooks and watches**: an address that other services (GitHub, a deploy, a monitor) post to, each post becoming a message to Pi in a session, or to PiP, as the work of whoever made the hook: their instructions first ("When a deploy fails, find out why and fix it"), then what was posted, trimmed of noise such as API addresses, and fenced as data. PiP gets them as folded cards and decides what to do: start a session, message one, or tell you. A GitHub hook is signed: GitHub gets the address and, separately, a secret (its Payload URL and Secret), and a post gets in only with GitHub's signature made with it, so whoever sees the address (the repository's admins do, in its settings) cannot post as the hook. Unless a GitHub hook is made **From anyone**, what people outside the repository wrote does not reach Pi (the repository's people are its owner, and the organization members and collaborators whom GitHub says can write to it, asked through `gh`, which must be signed in to the host and able to push there, or else only the owner counts; bots count on pull requests and what is said on them, never on issues): a post an outsider started (their issue, comment, pull request, review, or discussion) is dropped with a 202 that says so; in a post the repository's people started, the body of anything an outsider wrote in it (the issue under a member's comment, a review thread's comments) is left out, its title kept; a workflow run goes only when a branch of the repository itself started it (a push, a schedule, a manual or API dispatch, or another workflow), so one a pull request (a fork's too), an issue, or a comment started is dropped, and so is one whose head repository GitHub does not show; workflow jobs, check suites, and check runs do not say where their run came from, so they are dropped too, as are a commit status on no branch of the repository (a fork's commit) and a security advisory someone reported; and pushes, releases, and other posts that name no author go as they came. A hook for another service has the secret in its address instead: anyone who has the address can message Pi as the hook's person. **New secret** shuts out the old one, for an address or a secret that got out. Anything else gets 404. A post GitHub sends again goes to Pi once, GitHub's ping gets an answer and is nothing for Pi, a hook takes 30 posts an hour of up to 5 MB each (the server reads eight at a time, two to one hook, each within 15 seconds; past that, 503 with Retry-After), a hook to PiP answers 503 while PiP is turned off, and a post that cannot go now (someone else drives, a spend limit) gets a 409 that says no more. Services must be able to reach the server: through a tunnel, a public address works for GitHub. People who can steer make hooks for the sessions they can reach; each sees their own, the owner every one. The watch and webhooks are the **Triggers** extension: turned off, watches wait and hooks answer 503.

The status line shows a session's spend and limit; for a session with a limit that started linked sessions (Agent Teams), the spend it shows, here and in the sheet, is the team's, as its limit counts it. PiP's row shows its limit too, and PiP's notices (such as a stop at its limit) show in its panel. Spend per person counts from the first start of a version with this feature; what was spent before shows for its sessions only.

Models are grouped into collapsible provider sections with counts; the current provider opens first and its selected model is checked. - **Agent Teams.** Off until the owner turns it on in Settings → **Extensions & safety**. - **Background subagents.** The `subagent` tool spawns named subagents that work in their own conversations while you keep talking. Open one to watch it or talk to it. Its answer goes back to the main agent at its next pause (after a tool call; when it is idle, after a moment, so answers that finish together go together); answers that arrive meanwhile wait together and go as one message, shown as a card each, so many subagents cost the main agent one extra turn at most, and wait in its queue as one row: one that arrives while that row waits joins it. A subagent that fails says why. Explicit Stop sends no automatic report to the main agent. A message left queued when the child goes idle without taking it is withdrawn, and the main agent is told to send it again; that resend-needed report survives a restart and is not treated as an explicit Stop. The tool always offers an optional explicit model, thinking level (including `max`), and tool list. Omitting the model inherits the parent's. A level its model lacks becomes the nearest supported level, and Pi is told; levels above the parent's are allowed. Sending more work, queued or not, preserves the child's model and thinking rather than lowering them. An empty owner **Models for subagents** list leaves explicit model choices unrestricted. A nonempty list restricts extra choices to its entries, but the parent's model is always allowed. Availability and sign-in checks still apply; a refused explicit model is not silently replaced. Later work is refused for a child on another model excluded by a nonempty list, or whose provider cannot be used now. Clearing the list removes that model restriction, not availability checks. One whose model or provider failed (an expired sign-in, a model that is gone or refused, a quota or rate limit) says so with its model, on its card and in a notice, and the main agent is told to stop and tell you, never to start it again on another model.

- **Approvals need someone else.** An owner setting under Lancet Guard in Settings → **Extensions & safety**: a guest cannot allow a risky call that their own message led to. Someone else has to; the owner always can.
- **Docs for agents.** Pi's system prompt says where Pi Pocket's documentation is ([index.md](index.md)), to read when someone asks about Pi Pocket itself: changing how Pi works without code, writing extensions (with tested examples), and changing Pi Pocket's code while it runs, checked first on a throwaway copy (`node test/serve.ts`).
- **Drop-in extensions.** Put your own extension module (a `.ts` file that default-exports `(host, web) => Extension`, or a list, or nothing) in `~/.pi-durable-app/extensions/`. It shows in Settings → Extensions & safety, stays off until the owner turns it on, can import Coop's packages (Pi Durable, pi-ai, Pi's MCP client pi-mcp, and the rest) like the built-in modules, and reloads when edited. The MCP client is an importable dependency, not a built-in MCP connection manager. One that would take the name of a built-in extension or tool, or of another drop-in's, is not loaded, and the sheet says why: installing it would replace that one.
- **Extensions in the app.** A module can add to the app itself, without changes to Pi Pocket's code: routes on the server, commands for the message box, and a browser module with buttons on the rail, pages in the conversation's place (as the subagents board shows), sheets, rows in the menu, and launcher actions, which work without asking Pi. A dashboard of a provider's usage or the server's load, say: the route asks the service with a key that stays on the server, and the page shows what it says, live with the module's events. App-wide routes remain owner-only unless opened to unrestricted steering/viewing participants; session invitees cannot use them. A module may separately opt static browser assets into conversation access and register scoped routes that recheck current source visibility and role. Public inline controls and draft-only argument hints use the same guarded renderer; sending uses normal human input, never a second executor. Turning the module off takes away what it added, its pages included; an edit swaps the routes, and an edit to the browser module's files has tabs load it again. One that fails tells the owner why in a notice and in the Extensions sheet, and the rest of the app goes on; a tab opened with `?noext=1` loads none of their browser parts (safe mode), to turn off one that breaks the app. [docs/extensions.md](extensions/app.md) says how, with an example: a page with the server's load, memory, and uptime.
- **Extensions and safety.** Settings → **Extensions & safety** (or tap "guard" in the status line) lists Pi Pocket's extensions with their tools, the routes, commands, and browser module they add to the app, and any load error, in this browser too. The owner can turn Artifacts, Browser, Subagents, Scheduled messages, Done when, Plan mode, Codemode, Memory, Triggers, Extension gallery, Agent Teams, Lancet Guard, or a drop-in off and on, or reload one; the change applies to every session at once, stays after restarts (`disabledExtensions` and `enabledExtensions` in `~/.pi-durable-app/config.json`), and everyone in a session sees who changed what. Turning Lancet Guard off first shows a warning card with **Keep it on** and **Turn off**; only **Turn off** applies the change. This leaves Pi's own setting (`~/.pi/lancet-guard.json`) alone. PiP's pause, models and compaction controls belong to Settings → **PiP**. The system prompt cannot be turned off. Neither can the mandatory workflow core: transfer permissions/recovery, individually approved publication, constrained Pull reads and role-gated research remain installed independently of optional modules. Work Item execution belongs to **Agents**, not this list.
- **Extension gallery.** Settings → Extensions & safety → **Find extensions** (or **Find extensions** in the launcher) lists drop-ins other people wrote, from a reviewed index ([TannerMidd/pi-pocket-extensions](https://github.com/TannerMidd/pi-pocket-extensions) unless the owner picks another): search them by name, words, and tags; entries for a newer Pi Pocket are hidden. An entry shows who wrote it, where its code is (a GitHub repository at a pinned commit), its files, and what it declares: its tools (and which only read), hooks, prompt sections, wraps, routes, and browser module, and who can reach them. **Install** downloads its files over https from that commit, checks each against the SHA-256 the index pins (one that differs installs nothing), and puts them in the extensions folder, off, as every drop-in starts. Before turning it on, read its whole source in the gallery, or **Ask Pi to review**: a new session in the extensions folder, in plan mode, where Pi audits what the code reads (`config.json`, sign-ins, other secrets), the addresses it calls, the processes it starts, what its browser module does, and whether it does what it declares. Updates are never automatic: **update available** shows on it in the gallery and in Extensions, and the update shows what changes, as a diff of every file and of what it declares, before you apply it. When the index revokes the version you have, the gallery and Extensions say why and offer to turn it off, and a notice says so while it is on. **Uninstall** removes its files (where each came from is kept in `<name>.gallery.json` beside it). **Share…** on one of your own drop-ins in Extensions checks that it stands on its own (its files named after it, importing only Pi Pocket's packages and its own files), drafts its index entry (the description from its doc comment, each file's SHA-256, what it declares while it is on), asks where its files are on GitHub (the repository and commit you put them in, tags, your GitHub name), and, once the entry would pass the index's checks, opens GitHub's page for a pull request to the index with the entry filled in; Pi Pocket itself makes no GitHub calls. [docs/extensions.md](extensions/publishing.md) says how to publish. The owner's alone; turned off in Extensions, it reads nothing. It lists themes too, with a **Theme** tag and filter: **Install** checks a theme's pinned files and its CSS before it goes into `themes/`, and puts it in Appearance's list without applying it; **Update** shows a diff; **Remove** moves it to `themes/.removed/`; **Share…** in Appearance drafts an entry for one of your own themes ([themes.md](extensions/themes.md#themes-in-the-gallery)).
- **Refresh models.** The owner can tap **Refresh models** in the menu (under App) or Settings → **Providers** (above Models for subagents), or run **Refresh models** from the Ctrl/⌘+K launcher. The same controls work on phones. Refresh reloads `models.json` and Pi’s sign-ins, and asks configured providers for fresh catalogs. The menu's row says when it is refreshing, and a notice gives the added and removed model counts, without closing the menu; Settings → **Providers** also shows the errors for individual providers. All connected tabs receive the updated list. Healthy providers finish independently of slow ones; each provider has an eight-second limit. Running sessions keep their chosen models. A local model must be configured in `models.json` or registered by a Pocket-compatible extension: refresh does not load regular Pi CLI extensions or discover arbitrary local servers.
- **Uploads.** In normal chat and PiP, attach files with the picker, paste files or images, or drop them into the message box. Files are saved on the server for the conversation you send to and their paths are given to the agent; supported images also go straight to models that accept them.
- **Rich replies.** Code blocks in Pi's replies show their language and a Copy button, with syntax colors for the common languages (no dependencies, so it works offline), and a block of more than 40 lines folds until you ask for the rest. Some show more than code, with the code a tab away: an `html` block (or a reply that is a whole page) is previewed as a page, inline, with its scripts off and nothing loaded from anywhere; **▶ Run** runs its scripts in the artifacts' sandbox, where it can reach the internet but not the app; an `svg` block is drawn as an image (tap it for full screen); and a `diff` or `patch` block opens in the diff viewer. While Pi is still writing, they show as code. Write cards color the file they write, and the file viewer previews `.html` files the same way, with Run.
- **Images inline.** Attached images show as thumbnails (also in the composer before you send). When Pi writes `![description](path)` with a path on the server (absolute, `~/…`, or relative to the session's folder), the image shows in its reply. Images a tool returns and SVG artifacts show inline too. Tap any image to see it full screen. Only real image files are shown: the server checks a file's bytes, not just its name.
- **Launcher.** `npm start` asks how your devices should reach Pi Pocket: this device only, the local network, a Cloudflare Tunnel, or Tailscale over HTTP or opt-in native HTTPS. It then shows the address and a QR code to sign in your phone, and keeps running with keys to restart the server or change access.
