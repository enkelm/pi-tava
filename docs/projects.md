# Projects and typed threads

Collab's sidebar opens **Projects** first, followed by **Recent** and **Archived**. Projects group threads and Work Items directly. Herdr remains a separate owner-only view.

## Organization

A project has a name and a default working location and directory. Local means the machine running Coop, not the browser device; SSH identifies a configured host alias or user@host. Threads retain their existing durable conversation IDs, histories, permissions, model configuration and actual working directory. Their optional project ID organizes them independently of paths. Two projects can use the same folder; a worktree or directory override does not move a thread between projects.

Thread type is separate from placement:

- **Worker** has a blue agent tag. New project threads still default to Worker; research, optional planning and implementation can stay in the same thread.
- **Researcher** uses a brain icon and can start a new Work Item or investigate a pointed question mid-work. It produces cited findings and application guidance rather than implementing the feature; humans choose the next destination.
- **Chat** has a green speech-bubble tag. The one-time-chat flow starts an unassigned Chat.
- **Reviewer**, **Follow-up**, **Land** and **Publish** are successor types created through human-requested, agent-executed handoffs. Reviewer owns bounded independent review; Follow-up makes bounded review or Pull-intake repairs with a short delta self-review; Land performs authorized local integration and impact checks; Publish follows Land for individually approved external delivery. Entering Land is a human workflow choice, not a review/readiness/risk-acceptance gate or mutation permission.
- **Pull** reads upstream repository/PR/issue state and handles requested local rebases. It can start independently or be selected as a handoff at any stage.
- Moving a thread does not change its type. Threads grouped in a Work Item move together.

The first same-work handoff groups its source and successor in a **Work Item** named after the first thread. Later same-work successors join that item. Every active stage also offers Worker, Researcher and Pull as new-work starters, including the same starter type because it creates a distinct linked item. Same-work cannot repeat the current role consecutively. A human names a destination or describes the next task; the source agent infers a clear type or asks for clarification, then executes the handoff tool with its brief. Runtime state/history rules, not model readiness decisions, control which transitions can execute. Items can stand alone or belong directly to a project. Member threads cannot be archived independently. See [handoffs.md](handoffs.md) for the complete matrix and `/handoff` commands.

On upgrade, ordinary Collab catalogue entries without a type are durably marked Worker; untyped linked roots remain independent Chats. They stay unassigned and appear as ordinary rows, with no synthetic project or Unassigned section. Explicit types are not changed on later restarts. Private Herdr processes are not migrated.

A project's leading chevron folds its contents independently of navigation. Its single-line heading shows the configured default named agent's Blobatar/name and project name; there is no inline Edit action. Clicking the name opens `/projects/:id`, a project view with chats, Work Items, context and owner-only **Project settings**. The page starts with the project heading and its settings/New Session actions, not another Projects toolbar. Phones and narrow Split View retain an in-content Back to sessions control; roomy views use the persistent sidebar. Its **+** action opens Home creation prefilled for that project, without creating a conversation. Right-click, Context Menu / Shift+F10 and touch Options retain the existing project actions.

The owner's **Related PiPs** list also shows identities linked through their own `projectId`, including identities with no saved Chats. This link is separate from the project's **Default named agent**: the heading keeps the explicit default, while other linked identities remain visible below it and in the project view. Multiple links are listed, never resolved by arbitrarily selecting an agent. With no default, Home asks the owner to choose; clearing a default does not remove identity links, and linking an identity does not set a default.

Saved named Chats appear once by their actual project placement, and also remain discoverable in Recent and Archived. Owned Work Items nest under their exact named Chat, not its identity; accepted native ownership remains visible after Stop or completion without implying live control. Explicit project placement is authoritative: work in another project stays there without duplicating its parent Chat. Unknown or ambiguous ownership leaves work in its actual placement context rather than guessing a parent. New native handoffs inherit the actual originating Chat’s project, including no project, independently of their execution folder. Explicit research folders and pinned local/SSH destinations do not adopt the project’s machine or cwd; unsupported SSH repository checkout refuses rather than acquiring on the wrong host. Only Chats with real children have a disclosure, with their Blobatar above the chevron; leaves have the face alone. Thinking is the exact Chat’s Blobatar expression, including current orchestration waits, not a generic thread spinner. Work Item links open an accessible orchestrator when present, while individual thread links remain exact.

Standalone threads show their path and current Git branch before any handoff groups them into a Work Item, including ordinary checkouts without a Coop-created worktree. A detached checkout shows its short commit instead; outside Git, the model remains the fallback context. On the right, the subagent count precedes the loading/state indicator, which is vertically centered with the time and other controls.

## Moving threads

Only the owner can move threads between projects, including dragging a sidebar thread onto a project. Hovering a collapsed project opens it; hovering **Projects** while dragging from Recent switches tabs, and the list scrolls at its edges. The **No project** drop target appears only during a drag, after the existing list content so project headers and rows do not shift. It clears project membership. Dropping outside a destination or pressing Escape cancels. Rows are not manually reordered.

Threads keep hover Archive/Pin; Move is available through Options → **Move to project…** using the project picker. On touch, hold a thread row, then slide onto **Drag** or **Options** and dwell: the selected half expands across the row and briefly fills before activating. A stationary initial hold never chooses a half. Switching halves restarts the dwell; early release, leaving the row, a second finger or cancellation does nothing. Drag continues under the same finger, including across sidebar tab changes; Options opens as a bottom sheet. Mobile rows omit the cog and use the hold chooser; desktop actions retain hover and context-menu access. Reduced motion keeps the activation delay without the expanding motion.

Selected rows can be dragged together or moved using **Move…** in the selection bar. Multi-row moves use separate transactions per independent thread or whole Work Item, so a rejected target stays put and partial failure is reported; the picker retries only failed targets. Moving never archives/restores a thread or starts model work. It changes project membership only, never history, thread type or working directory.

## New threads

**New Session**, Alt+N and project **+** enter Home creation: a page on desktop and roomy iPad/tablet widths (768px and above), and the same flow in a native bottom sheet on phones or narrow Split View. Touch input does not force phone layout. Roomy Home keeps the in-content New Session heading, with no separate page toolbar or reserved header strip. When opened from another context, a native X at the content’s top-right and Escape return there; nested sheets keep first dismissal priority. Phones retain just the native bottom-sheet title and Close controls, with no second X in the content. Creation retains its state through orientation/Split View resizing; a phone-originated sheet uses a roomy centered dialog when widened, without replacing the source route. The mobile landing screen stays the full-width project/session list, with Back from a project or Chat returning there. Closing a child identity or import sheet returns to unfinished setup; dismissing creation returns to the unchanged underlying route. Host pills filter projects; **New Project** creates a real project, and owner-only **Add Machine** remembers an SSH destination in the current browser using the existing recent-destination preferences, without connecting. The primary owner path opens an unsent native named-agent Chat draft in the selected project. Choosing or viewing it starts no work; first Send uses the existing receipt/recovery path. Project-aware first Send requires the backend’s `agentDraftProjects: 1` capability. If the hot-reloaded UI is newer than the running backend, Send keeps the draft/files/project and explains the required update/restart instead of dropping the project or returning a generic unknown-setting error. **Other ways to start** expands native buttons for **New Work Item**, **Import from Pi** and the owner-only **One-time Chat**. Each choice reveals its existing native flow inline in the same creation surface; switching or collapsing retains its draft. Work Items require a selected project. Eligible import and one-time Chat paths remain available without one. One-time Chats stay unassigned; Import has its own optional project and privacy confirmation, never inherited silently from Home’s selection. Home reuses the native Live/History importer without opening the legacy import sheet.

Collaborators see only granted projects and create work at the saved machine and directory, without arbitrary location, folder or worktree overrides. Only the owner sees **New Project**, **Change**, directory browsing and the one-time path. Within disclosed work options, **Own Git worktree** remains visible below the compact working-directory row and its expanded controls. Changing a folder does not change membership.

Starter choices come from the application-owned WorkItems catalog and current namespaced extension profiles. The project default is the first starter other than core Chat; the declarative built-in order keeps Worker before Researcher. Pausing **Work Item execution** blocks non-Chat built-in starters without unloading profiles or controls. An earlier disabled setting stays paused after upgrade. Ordinary ungrouped Chat and Agent Teams remain independent; see [availability](handoffs.md#availability-and-execution-pause).

Confirming Start creates one thread directly in the selected project. Cancelling creates none. Creation retry receipts prevent duplicate conversations. Project selection performs no model request or naming work.

Projects may save an owner-private `defaultAgentId`, validated against the owner's named identities. It is a creation default, never a grant or an agent's access boundary. PiPs is the people-icon button beside New Session; its library creates identities globally without creating a Chat. Home and New Project can create an identity and return to their unfinished setup. A one-off Home selection does not rewrite the project's saved default. Agent settings can link, reassign or explicitly clear an identity's project using the current revision. Omitted links are preserved, and unrelated charter edits do not clear them. Charter Undo restores text only, keeping the current project link. Saving updates navigation metadata immediately; the owner-private catalogue carries the same identity link across events and reloads. None of these actions moves old Chats or grants access. The `projectAgentLinks: 1` server capability gates link/default editing; older hosts show the saved remit and an update/restart hint rather than falsely acknowledging an unsupported default change. The server must be restarted by the owner after installing these server changes.

A named draft pins its selected `projectId` into the first-send retry payload. The new Chat uses that project's destination defaults without retargeting sibling Chats or changing the identity's default context. Omitted first-send context retains the identity's existing project default; an explicit null clears it. Legacy explicit saved-Chat creation intents retain their existing behavior.

Project defaults affect new threads only. Moving an existing thread changes organization, never its directory. Ungrouped forks and resends retain source placement and thread type, actual directory/worktree and owner-only restrictions. Grouped handoff threads cannot fork or resend around Work Item ownership. Imports retain their source directory and default to unassigned Chats. The owner can select a project in import confirmation or when explicitly sharing an existing private imported Chat. Placement never changes the source directory or pinned machine; a private import remains owner-only inside a project. An unassigned shared import is still excluded from project-only grants, including All projects, and needs an exact-session invitation for those participants.

## SSH workspaces

Choose **Change → SSH…** in New Project or New Session, use a suggested SSH host or enter an alias, `user@host`, or `ssh://user@host:port`, and Browse to connect and select a remote folder. For the owner, the host picker reads concrete `Host` aliases from the Coop host’s `~/.ssh/config` and included files, plus saved host names from `~/.ssh/known_hosts`. Saved nonstandard ports are preserved as SSH URIs. Known-hosts entries do not record login usernames; edit the destination to add one when needed. Hashed names, wildcard/negated rules and marked/revoked entries are not suggested. Discovery does not probe machines, inspect other SSH sessions, or execute configuration commands; suggestions are not a connection-status check. Manual entry and recent folders remain available if discovery is empty or incomplete. Coop uses the host’s existing OpenSSH configuration, authentication and known-hosts files. Key/agent authentication stays noninteractive. For password authentication, the owner opens **Password login**, enters an **SSH password** and chooses **Log in with password** in the destination editor, a failed folder connection or an existing thread’s destination details. Use an HTTPS Coop address, or localhost on the Coop machine. Native **Tailscale (HTTPS)** provides this without Serve ([setup](../README.md#private-https-with-tailscale)); ordinary Tailscale HTTP is not a browser secure context. On an insecure page, the password controls remain visible but disabled with a short HTTPS hint. Opening the folder picker moves login controls there instead of repeating them. New or changed host keys must be handled on the Coop host first; password login never accepts them automatically. Nothing is installed on the remote beyond its existing SSH/SFTP service, bash and project toolchain.

Each thread has one destination. Projects store creation-time defaults; new threads pin their own location and directory, including overrides. Moving a thread or changing a project default never retargets existing threads. Helpers, linked sessions and forks inherit the source destination while all agent loops, model requests, history and provider settings remain on Coop.

Password login first verifies a real SFTP connection and password prompt. It keeps the credential only in server memory for that signed-in person/token and exact destination, not in project/thread metadata, history, browser storage, command arguments or environment values. It expires after 30 minutes without credential use or eight hours at most, and **Forget login**, app logout and server shutdown clear it. After a restart or expiry, log in again; failed commands are not resumed or replayed. Human Files and `!` commands use their actual requester’s login rather than borrowing the last agent requester’s password. An explicit project grant permits the service to use the owner's current exact-host password capability only for an actual visible thread's pinned workspace. The collaborator receives no password, handle or login status; requester grants and the captured owner's token are rechecked across awaited work. Forgetting, expiry and token rotation revoke old password authority without replaying work. Legacy implicit access and session-only invitations do not delegate passwords. Password login requires a POSIX Coop host with OpenSSH and `/usr/bin/mkfifo` (as on macOS/Linux). Ordinary password and password-only keyboard-interactive prompts work; key passphrases, OTP/MFA and password-change dialogs do not.

Remote projects share a monitor icon with a bottom-right status dot in the New Session picker, desktop sidebar, mobile drawer and home list. Gray means unknown, amber an explicit check is pending, green a recent successful filesystem or password-login probe, and red the last remote workspace attempt failed. Evidence is browser/user scoped and expires after two minutes; opening project lists does not probe hosts, and cached login status is not connection evidence. The header and Files root identify SSH destinations; Bash cards name the host. Connection errors offer retry for reads without switching to local paths. Closing or superseding Files, folder, diff and context reads cancels their work; HTTP disconnects reach the remote read transport and join its cleanup. Changes shares one foreground/online refresh lifecycle across the header, Files and review. Identical mention readers share an exact-caller pending traversal and briefly reuse names only after fresh root validation; no connection is retained between operations. Uncertain writes or commands are not automatically replayed. Stop and timeout request termination of the command’s remote process group, including TERM→STOP/KILL escalation, but a lost transport cannot confirm completion and programs can escape a group. Inspect remote state before retrying uncertain work.

SSH changes the workspace destination, not the thread type: managed workflows and handoffs keep the same roles, requester checks, approvals, spend controls and single-writer rules. Files, Git and project scripts use the pinned target; agents, provider calls, research and external acquisition remain on Coop. Managed commands require a supported **target-native** offline sandbox, currently macOS `sandbox-exec`. Missing or rejected confinement fails the particular operation; Coop never retries it as unrestricted SSH. Sandboxing the local SSH client is not a substitute.

Changes, branch switching, review diffs/comments and worktree operations use remote Git. Remote worktrees live in a private `0700` directory at `~/.pi-coop-worktrees`; an existing symlink or public directory is rejected without changing its permissions. Equal paths on different destinations do not share a worktree or checkout fingerprint. Inline `@` file mentions use remote bytes, never a local namesake.

Pull fetches and approved publication use host-owned staging and credentials. Git artifacts cross SSH as bounded bundles and explicit refs, with import/export confined offline on the target. Remote file/relative/absolute Git URLs are not reinterpreted as host files. Publication rejects unsupported executable configuration or active custom hooks before approval rather than silently ignoring them. SSH PR creation requires an explicit base; combined external/local cleanup flags such as `--delete-branch` are unsupported. Uncertain publication receipts still require reconciliation, never blind replay.

Complete UTF-8 files up to 512 KiB support Files quick edits when a compatible native Python 3 is already available on the target. Preview bytes and revisions come from one opened snapshot, without downloading the same eligible text over SFTP first. Saves stage privately, preserve metadata, reauthorize the original human after preparation, and recheck file identities before replacement. Missing native capabilities disable quick edits with a reason, never an SFTP overwrite fallback. Expanded hidden review context uses the same safe snapshot boundary.

Remote `.pi/skills`, repository-bounded ancestor `.agents/skills`, prompt templates and model defaults use explicit owner trust saved on Coop, keyed by the exact SSH filesystem and canonical folder. Trust can be revoked immediately; remote settings cannot grant it or import provider credentials. Remote skill expansion consumes remote bytes, never a same-path host file. Discovery is bounded and skips hidden entries and `node_modules`, but does not yet apply `.gitignore`, `.ignore` or `.fdignore` patterns.

**Remaining limits:** language services, filesystem watchers, PTYs and port forwarding are outside this SSH slice. Managed command confinement currently supports macOS targets with `sandbox-exec`; other platforms fail safely. Final replacement is best-effort against unrelated remote writers, not atomic compare-and-swap. Offline fixtures validate dispatch, scope, native file protocol and policy checks; real SSH authentication and actual target sandbox enforcement require separate authorized validation.

Remote project instructions load from the remote namespace. Host-global skills remain local and can be read with `host_skill`; their scripts are not implicitly copied or executable remotely. Uploads remain on Coop; `stage_upload(path)` explicitly copies one thread attachment (up to 25 MiB) to a private remote temporary directory and returns its remote path. It does not copy arbitrary host files, credentials or directories. Nonempty staging directories remain until explicitly removed. Remote generated images can be viewed through Files or inline paths; attaching them as new user-uploaded files is not provided.

## Archive

Archive and restore operate on an independent thread or an entire Work Item. They do not remove project membership, change the thread's directory or delete its history. Member conversations cannot be archived independently. Existing archived threads stay archived until explicitly restored.

The separate **Done when** `/until` completion-check feature is unchanged.

## Storage and access

`pocket.projects` is a session-scoped durable document beside the existing catalogue. `pocket.session-creates` stores creation retry receipts. The existing document kinds, versions, scope and fork settings are unchanged. Project membership and thread type remain catalogue metadata.

The owner grants project access when inviting a collaborator or editing them in **Account & access**. The picker has horizontally scrollable **All**, **Local** and per-SSH-machine filter pills, individual project rows, and quick grants for all projects, local projects or one machine's projects. Filters only change the visible rows; broad grants explicitly include future matching projects. A new collaborator invite defaults to no project grants. **All projects** does not expose unassigned conversations or owner-only imports.

`projectAccess` is additive user/invite metadata: `{ all?: true, local?: true, hosts?: string[], projectIds?: string[] }`. Rules combine by union and match exact configured SSH destination strings. Explicit IDs grant the named project, not every project sharing its path. Local/machine rules also check a thread's actual pinned namespace, so an old override on another machine does not leak through the project's current default. An absent field retains the legacy stored scope; no migration is run. An explicit single-thread invitation remains limited to its named thread and cannot create others.

Membership alone is not authority: current project grants, owner-only restrictions, steering/viewing roles, take-turns rules, workflow ownership and spend limits all apply. Project edits, placement, arbitrary destination preparation, SSH discovery/authentication/trust controls, directory browsing and cwd/worktree reconfiguration are owner-only. Collaborators may create threads only in granted existing projects at their saved destination; explicit matching defaults are accepted, overrides refused. Creation itself does not connect to a remote target or inspect remote model-default files. Granted viewers still cannot create or steer. Session-scoped participants see only projects associated with their visible threads, without default directories or unrelated empty projects. Whole-Work-Item edits that would touch a hidden thread reject as a whole.

Revocation filters catalogues and future events, evicts open unauthorized conversations/peeks, and invalidates captured requester environments and reads even without a token change. Project collaborators cannot browse/import host-local Pi history, including with an all-projects grant. Existing stored legacy Pi-history grants retain their separate restrictions.

These are application permissions, not an OS filesystem jail. Normal allowed agent commands and trusted project scripts retain the remote/local account's capabilities; see [Security](../SECURITY.md).

The server sends the filtered catalogue in `projects` events on connection, membership changes and catalogue updates. Current handoff/profile choices come through `app.workItems`, which owns the declarative first-party catalog and incorporates installed namespaced extension declarations. Its browser picker and hints use public conversation-scoped interfaces and the normal human-input journal. Core tasks recover already-accepted summary/delivery data only; they do not provide an alternate admission path.

## Interface

- `GET /api/projects`: filtered project catalogue.
- `POST /api/projects`: create a project with name, directory and retry ID.
- `POST /api/projects/:id`: rename a project or change its creation-time directory/default named agent.
- `GET /api/pip/agents`: owner-private identity catalogue, including optional identity `projectId` independently of each Chat's placement.
- `POST /api/pip/agents/:agentId`: revision-checked identity settings, including omitted/preserve, string/link and null/clear `projectId` semantics; no existing Chat placement changes.
- `POST /api/sessions`: existing thread creation, with optional project, type and retry ID.
- `POST /api/sessions/:id`: existing metadata editing, including project placement.

`app.projects` owns project validation, filtered projection and independent thread placement; HTTP is only an adapter. `app.workItems` owns whole-item organization, applies the project's placement validation and updates all members together. It retains membership and hidden-member checks rather than requiring Projects to expand groups. Agent-executed handoffs derive the authenticated requester from real human input in the current main run, enforce state-based transitions and commit successor creation, relationships, retry receipt, active-writer reservation and source retirement together. Summary delivery and guarded destination naming retain retry identity and exactly-once usage accounting. The tool supports status/start without readiness milestones. Autonomous project creation or arbitrary cross-thread prompting is not provided; adding project IDs alone does not grant that authority.
