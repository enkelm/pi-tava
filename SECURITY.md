# Security

## Reporting a problem

Please report security problems privately through GitHub: on this repository, open **Security → Report a vulnerability**. Do not open a public issue. Include what you found, how to reproduce it, and what an attacker gains.

## What pi-tava protects, and what it does not

pi-tava runs a coding agent that executes commands on the machine it runs on, as the user who started it.

- **Signing in.** The owner's sign-in link is the key to the server. Invites are one-time links that expire after 15 minutes, or an hour, a day, or a week when whoever makes one picks that; the longer one lasts, the longer a link that leaks can be used. Their codes are stored hashed. An owner invite, which only the owner can make, always lasts 15 minutes and gives the device that opens it the owner token itself, and with it full control; starting with `--rotate-token` signs out every device that has it and ends owner invites not yet used. Tokens are random, stored hashed, and kept in an `HttpOnly` cookie.
- **Viewers** can read, react, and chat. In sessions they can see, they can read live uncommitted changes within the session folder and comment on changes, files, or lines, even while Pi works. This review-only access does not unlock the Files browser, editor, ordinary Changes routes, tool approvals, or prompting Pi. Comments keep their original author, working folder and optional client-supplied line excerpt; anchors are advisory, not saved snapshots or proof of current file content. Review status follows each original author's unresolved threads, not assigned verdicts. The owner can resolve or reopen any chosen threads in one atomic action; other people can resolve or reopen only their own. Comment and resolution actions recheck current membership and scope, require durable retry IDs, and never drive Pi or Git. Explicit bot buttons send one reviewer's feedback or all feedback through the ordinary submission route, with steering/driver checks and durable retry IDs; viewers cannot use them. Live review diffs accept only listed changed files inside the session folder, excluding renames across its boundary. A review-only context endpoint supplies complete UTF-8 text up to 512 KiB for those changed files, with read-only, no-follow identity checks; it rejects symlink escapes, binary or incomplete reads and does not grant general file access. Forks start without review threads.
- **Project permissions.** Only the owner issues invitations and edits project grants. New collaborators default to no project access, with explicit all/local/exact-SSH-machine/project-ID grants available. Broad grants include future matching projects. Collaborators may create threads only in granted existing projects at the saved host and directory; project edits/moves, arbitrary directory browsing, SSH discovery/login/trust and destination/cwd/worktree reconfiguration stay owner-only. All-project access excludes unassigned and owner-only history. Viewers still cannot steer. Revocation rechecks live access on requests, events, cached environments and pending reads, even without rotating a token. Host Pi-history discovery/imports are unavailable to project-granted collaborators. Stored absent scopes retain legacy semantics without a migration. These are app/API permissions, not a filesystem jail for allowed agent commands or project scripts.
- **Anyone who can steer can do what you can.** Through Pi, they reach your files, pi-tava's settings and tokens, and its code. An invite to one session limits what someone sees in the app, not what Pi can reach. Neither do git worktrees or spend limits: a worktree keeps a session's files apart, and a run is stopped only after the request that crosses its limit.
- **Approvals.** Lancet Guard approvals can come from anyone who can steer, including the person who asked, unless the owner turns on "Approvals need someone else" (Menu → Extensions); then, when nobody is known to have asked, only the owner can allow. A notification offers Allow only for a call that fits on one short line; anything longer opens the app first. A "Done when" check command runs after every answer without asking, so with Lancet Guard on it must be one the guard allows outright.
- **The built-in browser**, outside managed workflows, reaches what this machine reaches: `localhost`, your network, and the internet. Anyone who can steer can use it from the Browser panel, and Pi from its `browser` tool; Lancet Guard does not check either, and pages can hold whatever they show. The addresses people open show in the session's chat. Its pages run in Chromium on the server and do not automatically share your app tab's cookies. Imported app-authentication cookies are stripped before opening shared pages; do not sign into pi-tava as the owner inside the shared browser. Only the owner opens files from the address bar or sees which servers run on the machine. If steering guests should not reach your network, turn Browser off in Menu → Extensions. The clean default uses isolated temporary sessions. Only the owner can import a local Chromium-family profile and select it as the app-wide default, with explicit confirmation: its copied cookies and site storage persist and are shared across conversations. Pi and people using the app browser can then access those signed-in accounts; imported profiles are not an owner-only browsing boundary. Import leaves the source unchanged and excludes password/autofill databases and extensions, but cookies and site storage are still credentials. Returning to clean sessions deselects the import, not an erasure of its app-owned copy.
- **File edits and language servers.** Quick saves require steering and the wheel while taking turns, reject stale file revisions and respect session-scoped paths. The route does not write Pi's settings or app state. Unsaved recovery drafts live in the browser tab's session storage until saved or explicitly discarded. Only the owner starts or talks to language servers: these are local processes with the daemon's filesystem and network access, not sandboxes. The bundled TypeScript 7 native server and fixed supported executables on PATH are allowed; browser/project-supplied launch commands and LSP command execution are not. Formatting changes the unsaved browser buffer only. Lancet Guard does not check editor saves or language-server activity.
- **Models** are a person's to choose. Background subagents inherit their parent's model unless another is selected explicitly; an empty owner list (Providers → Models for subagents) leaves explicit choices unrestricted, while a nonempty list limits extra choices. Agent Teams always treats that list as an extra-model allowlist, so empty means parent-only; PiP passes a model only when its person named it; compaction and PiP summaries use the session's own model. pi-tava's session-title and goal naming use the cheapest available text-capable small model from the same provider, falling back to the session's own; their usage counts toward the session's spend. Subagents on another model, and PiP, ask a model's sign-in afresh first and use none whose sign-in expired; a session's own run, a subagent on its model, titles, and summaries just try the model, and a run that fails on an expired sign-in marks it. This guards spending against Pi's choices, not against a person: anyone who can steer can pick a session's model, and Pi, which runs commands, can reach Pi's sign-ins and pi-tava's files like anything else on the machine.
- **Persistent private agents.** Stable owner/agent identity binds multiple owner-only chats, approved revisioned instructions, model choice, Blobatar, learned Memory and supervisory relationships. Server-derived `(ownerId, agentId)` Memory isolation applies to prompts, HTTP/tools, guessed IDs, writes, approvals, receipts and events; private learned facts are automatically maintained but never enter shared/global/project lessons. Instruction proposals stay inactive until an explicit owner save. Explicit project remit grants no cwd, membership, access, settings or activation. Named agents have real workspace tools, with delegation preferred over direct work. Exact native controller/execution contact automatically establishes its internal association; opening or discovery alone does not activate work. Accepted input, native generation/task ancestry, owner/token/identity/association/controller epochs and durable receipts fence stale calls and relevant descendants. Controllers remain independent Work Item roots. Direct correction of competing work requires native writer intervention: exclude competing effects, stop and join execution/helpers, then lend and return the existing writer. Native questions, access, model/sign-in, cumulative budgets and individual publication approvals still apply; shell refusals have no unrestricted fallback. Exact native controller, execution-thread, ordinary-Chat and literal-helper contacts retain service provenance and native queue/steer semantics. The source first commits a durable fingerprinted intent, then submits through its real invocation-bound native handle. There is no atomic cross-conversation source-admission callback: stale input may be durably accepted, but generation and effect fences deny its activation and withdraw/cancel it. Coding, helper and control bodies revalidate even when native safe replay skips tool hooks. Recovery persists these fences before abort APIs can resume other tasks. A missing selected safety extension refuses contact rather than adding tools or falling back to owner-account input. Unsupported legacy schedule/watch mutations, session archival, approval cancellation and extension effects still fail closed; passive inspection does not grant them. Stop/revoke and direct human takeover invalidate stale authority without undoing external effects. Passive reports are pinned to their originating task/chat, not an inbox or open browser tab. Send answers retain their accepted source, while independent exact follows fan out without tracking a Work Item’s changing active thread. Private-derived helper reports validate the registered native reporter and copied creator authority, and do not create activating parent couriers. Durable receipts deduplicate reports across retry/restart; unavailable origins hold delivery visibly at the exact target rather than rerouting. Old notebook definitions remain inert without migration/startup deletion. Generic PiP and shared replies never inherit private personalities or memory. These are application protections, not an OS filesystem jail.
- **Linked sessions** (Agent Teams, off until the owner turns it on) widen what prompt injection can reach. A session that read something hostile (a page, a file, an issue) can pass it on to the other sessions of its team in a message, and a message makes Pi work in the target for the person Pi worked for in the sender, with that person's access, in a session where other people may have written. Pi is told to take a linked session's message as a request, not as an order from a person, and to do nothing destructive or with credentials only because one asks; that is guidance to the model, not a boundary. A message is fenced, and a team stops after 20 messages without a person, at the starting session's spend limit, and at 10 sessions; a link gives no access to a session someone cannot already see.
- **Native Tailscale HTTPS.** Only explicit `tailscale-https` access can ask the trusted native Tailscale CLI for a certificate; existing HTTP modes stay HTTP. The owner must enable MagicDNS/HTTPS certificates in the tailnet, and issuance publicly records the device’s full `.ts.net` name in Certificate Transparency. Coop never changes tailnet administration, invokes sudo, installs software, enables Serve/Funnel or opens a second public listener. It validates the active profile and bind target before issuance, validates certificate identity/date/key and binds only the selected tailnet IPv4 address with TLS 1.2 or newer. Certificate/key output is bounded, kept in memory, not logged or written to app files; Tailscale owns its own cache. Renewal stays on the same identity, never downgrades to plaintext, and does not bypass normal sign-in, CSRF, origin or SSH-password gates. Tailnet ACLs still apply; the browser must use the full certificate hostname. See [setup](README.md#private-https-with-tailscale).
- **SSH workspaces.** File operations and project commands run as the selected remote account through the Coop host’s existing OpenSSH configuration/authentication/known-hosts policy; agents, models, history and provider credentials remain on Coop. Only the owner selects targets or browses arbitrary destination directories; project collaborators use the owner's configured project and pinned thread target. SSH configuration, including proxy directives and account bootstrap, is trusted owner input. Coop never bypasses host-key checks, forwards its agent/provider credentials or installs a remote service. One shared live policy preserves requester/token/access, role, single-writer, workflow and publication locks. Managed commands require a native offline/inspection sandbox on the target, currently macOS `sandbox-exec`; unsupported confinement fails the operation without raw SSH fallback. Local sandboxing of SSH is not remote confinement. Destination-bound Git, reviews, worktrees and fingerprints never read host-local namesakes. Remote worktree storage must be canonical and private. Pull/publication keep external activity and authentication on Coop, transferring bounded artifacts and rejecting unsupported hooks/configuration before approval. Canonical scope and optimistic agent edit checks cannot prevent every hostile concurrent remote path swap and do not provide atomic CAS. Files quick edits and hidden review context require native opened snapshots; saves preserve metadata, prepare a private adjacent replacement, reauthorize the original caller and recheck identities before rename. Missing native capabilities never trigger a weaker save. Final rename races remain best-effort. Remote project resources require explicit host-owned trust scoped to exact filesystem/canonical root, with immediate revocation and bounded content-aware skill expansion; remote settings cannot self-trust or supply provider credentials. LSP and watchers remain unsupported. Uploads stay local unless explicitly staged; host-global skill reads stay inside registered roots. Stop requests remote process-group termination, but transport loss cannot prove completion; mutations and publication are never automatically replayed. See [SSH limits](docs/projects.md#ssh-workspaces).
- **SSH password login.** Only the owner can submit or inspect password-login state, over HTTPS or localhost, with the usual sign-in and CSRF checks. The UI clears the field on submission and does not put the password in drafts, destinations or browser storage. Credentials remain in expiring server memory, scoped to the current person/token and exact SSH target; they are not stored in app data, argv or environment values. A private host-side FIFO delivers each password to OpenSSH askpass, bound to that SSH process’s PID so nested proxy/jump SSH processes cannot accidentally consume it. Password-mode connections disable multiplexing and require an actual accepted password prompt plus SFTP success before publishing a login. Host-key checks remain strict; confirmation, key-passphrase, OTP and password-change prompts are refused. Forget/logout/expiry/shutdown revoke the credential for new connections; they do not promise to stop already-authenticated remote jobs. Human Files and message-box shell actions select the actual requester’s authority, not another person’s agent attribution. For an actual visible project thread with an explicit current project grant, the service may use the owner's current exact-host password capability bound to that thread's pinned host/cwd/membership. Both the requester grant snapshot and captured owner/token are rechecked across awaits. Guests receive no password, credential handle or authentication status; arbitrary preparation/browsing, legacy implicit scope and session-only invitations cannot delegate passwords. Forget/expiry/token rotation revoke old authority without mutation replay or credential fallback after selection. This is API-level scoping, not protection from trusted extensions or code already running with the Coop OS user’s rights. No password is sent to model providers. See [password login and limits](docs/projects.md#ssh-workspaces).
- **Private failure diagnostics.** Only the current owner's global private PiP can read Collab status, grouped failures and metadata traces. The core reader checks actual invocation identity before enumeration and rechecks the current owner/token, enabled state and selected execution scope after awaited work, including nested codemode calls. Shared agents/mentions, helpers and scoped Work Item controllers cannot obtain global private visibility by selecting the tools. Diagnostic observations are bounded local metadata, not raw prompts, reasoning, tool arguments/results, exception messages, environment dumps or credentials; they are not room documents or shared events. The selected private model provider can receive this metadata when PiP uses the tools. Capture is best effort: unavailable storage or process loss can leave missing/unfinished records, and reads never probe, resume, repair or certify system health. No external telemetry exporter, raw database interface or automatic incident wake is added.
- **Managed handoff workflows.** Humans request handoffs through the header picker, in English or with `/handoff`; agents infer a clear intended type or ask for clarification, then execute the handoff tool with a brief. The runtime deterministically enforces type/history/diff transitions and live authorization, not agent recommendations, readiness claims or historical review/risk-acceptance records. Source-agent tool execution requires real human input in the active main run, excluding copied couriers, schedules and helper inputs. Explicit slash-command routing is pinned; ambiguity is an agent clarification responsibility, not a semantic natural-language authorization classifier. The owner may instead explicitly delegate one Work Item to a separate private PiP controller. Its live owner/token/epoch grant permits handoffs within that item without fresh source-thread human input or historical type/diff eligibility. Access, spending, driving, active-writer ownership, settled execution/helpers and individual publication approvals still apply. Pause, reclaim, human input and Stop fence stale controller actions; already dispatched work may continue. The controller's private conversation, goal and history are not automatically copied into execution context. A successful tool transaction creates the successor, pins its retry receipt, reserves its active-writer position and retires the source. The tool supports status/start, not legacy prepare/complete/record-review or recommendation controls. Earlier durable summary-first requests retain their summary-only and lookup-recovery restrictions. A predecessor loses local write capability permanently, including filesystem operations, shell execution and descendant agents. Verified read-only local inspection remains available; write authority never returns. The mandatory core gate is independent of Lancet Guard. Handoffs still require access, driving, idleness and single-writer ownership; Land admission does not require review/readiness/checkpoint/risk acceptance and grants no mutation authority. Managed shell commands run offline under macOS `sandbox-exec`; they cannot download dependencies, access network services or run HTTP/server tests. Shell execution fails closed on unsupported platforms rather than falling back to unrestricted execution. Artifact and unknown extension tools are blocked in managed agent workflows because they could bypass publication approval. Worker, Researcher and Follow-up have a bounded public-document reader and isolated public GitHub clones through `research`, not online shell access. Their browser actions are read-oriented: public HTTPS documents are fetched without cookies/auth, validated against private/reserved IPv4 destinations and DNS-pinned on every redirect, then reduced to static semantic content in a temporary isolated Chromium context with networking and scripts disabled. Managed pages never use imported accounts. Forms, live links, resources, scripts and interactive agent actions are unavailable; authenticated sites and local dev-server browser checks remain unsupported. Public servers are assumed to honor GET read semantics; this is not a guarantee that an arbitrary remote server never changes its own state. Cloning uses credential-free shallow GitHub-only HTTPS transport in app-created staging with no redirects/hooks/config/submodules/LFS, then bounded offline checkout. Sources remain untrusted. See the research limits and cleanup behavior in [handoffs](docs/handoffs.md). Existing artifacts and runnable reply previews are also denied in those conversations, including execution on a viewer’s device. An active Pull thread has a separate constrained `pull` adapter for configured Git remote fetches and explicit GitHub PR/issue reads. It is not an online shell: Git's network phase uses an app-created bare staging repository without checkout hooks/config or credential helpers, then imports only remote-tracking branches through the offline sandbox. File remotes stay offline. GitHub reads use allowlisted built-in commands against github.com; arbitrary API calls, aliases, templates, scripts and mutations are unsupported. External content remains untrusted. Publish follows Land and uses the separate `publication` tool for supported Git/GitHub CLI actions. Each action checks the actual current clean Publish checkout rather than an inherited readiness milestone, and needs individual human approval bound to the exact command, content checkpoint, destination and relevant executable inputs. Changed inputs need fresh approval; choosing Publish cannot approve an action. An interrupted or failed external operation remains uncertain until a human reconciles it; another handoff cannot erase that receipt. These restrictions control the normal agent execution path, not the administrator or trusted server extensions, which still execute with server rights. Unrelated Chats retain their existing execution behavior. See [handoffs](docs/handoffs.md).
- **Plan mode** keeps Pi to planning; it is not a boundary. Programs that people configured to run on their own, such as a git diff driver, run as they would for anyone.
- **Drop-in extensions** in `~/.pi-durable-app/extensions/` run inside the server with the owner's rights. They stay off until the owner turns them on. One with a browser module also runs code in the app's own page, with the rights of whoever's tab loads it: the owner's alone unless the module opens it to others (never to someone invited to one session). The page's content security policy keeps that code from loading scripts and styles from another site or fetching from one, but code in the page could still send data out in other ways (navigating the page elsewhere, for one): turn on only browser modules you trust, as with the server part. What a module's route throws with `web.error` reaches everyone who may use that route as it is; anything else it throws, only the owner reads. Every file of a web type (`.js`, `.mjs`, `.css`, `.json`, images, and `.woff2` fonts) in a browser module's folder can be read by everyone the module is for. A module's conversation command is offered to everyone who can steer that session, people invited to only that session included, and its handler runs with the owner's rights: treat its arguments as untrusted, and check who runs it. A global command is the owner's alone.
- **The extension gallery** (Menu → Extensions → Find extensions) installs drop-ins other people wrote, so what it installs has the owner's rights once turned on. It reads its index strictly, downloads only over https from each entry's pinned commit, refuses a file whose SHA-256 differs from the entry's, keeps file names inside the drop-in folder, and installs everything off; updates are never automatic. The index's checks and its maintainers' review lower the risk, but do not remove it: read the code (or ask Pi to review it) before you turn one on. Only the owner can use the gallery. A theme from the gallery is CSS, fonts, and images that the owner chooses to install. pi-tava checks it as every theme folder before it is in place, so it cannot load anything from other servers, nor the app's own addresses, and it runs no code. It can still hide or relabel parts of the app, approvals too: install only themes you trust.
- **Pi provider packages** are owner-selected trusted executable dependencies, not sandboxes. Discovery reads metadata only; adding/selecting/updating/enabling packages requires explicit trust confirmation. Coop installs exact releases with npm scripts disabled in separate retained trees and activates them only after restart, through isolated child workers. Isolation separates Pi settings and concurrent provider state, not filesystem/network rights or credential access; Lancet Guard does not inspect provider code. Package responses contain public settings, not keys or secret headers. Only supported API-key chat profiles are exposed; SSO, command credential helpers, MCP/skills and embedded tool loops are not implicitly enabled. A startup failure without a usable retained release holds all Durable progress while owner recovery controls remain available.
- **Replies are untrusted.** Anything Pi reads can steer what it writes, so the app page loads nothing from other sites, and replies cannot contain forms, scripts, or styling. Artifacts run in a sandbox with no access to the app. An HTML block in a reply is previewed in a frame of its own with its scripts off and a policy that loads nothing, not even from the app; tapping **Run** runs it as an artifact runs, with scripts and the network but no access to the app, so a page Pi was steered into writing could then send what it shows elsewhere. SVG blocks show as images, which run nothing. Managed handoff conversations disable executable artifacts and **Run**, and preview-frame requests must identify an accessible, unmanaged conversation or the owner-only private context.

Problems within these limits are bugs we want to hear about: for example, a viewer making Pi act, a session-scoped person seeing another session, or a reply reaching the app's cookies or API.
