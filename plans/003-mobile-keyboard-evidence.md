## Viewport distinctions

- **Layout viewport:** the CSS layout/initial-containing-block coordinate space. `innerHeight` and fixed overlays are layout-oriented measurements/placement; they are not an independent measure of space above an OS keyboard.
- **Visual viewport:** the area currently visible within the layout viewport. Its `height`, `width`, `offsetTop`, `offsetLeft` and `scale` may change for keyboard visibility, browser panning and pinch zoom. A smaller visual viewport is not itself proof of a keyboard.
- **Dynamic viewport units:** `dvh` accounts for dynamic browser interfaces, such as retractable browser chrome. It is not synonymous with `visualViewport.height`, nor a promise to shrink around the OS keyboard.
- **Pinch zoom:** changes visual-viewport scale/size without necessarily relaying out the page. Focus-induced input zoom is also distinct from keyboard occlusion. Device emulation's `deviceScaleFactor: 2` is pixel density, not a pinch-zoom or keyboard test.

### Primary platform evidence (retrieved successfully)

1. [Chrome's viewport resize behavior announcement](https://developer.chrome.com/blog/viewport-resize-behavior): describes Safari on iOS/iPadOS as shrinking the visual viewport while leaving the layout viewport untouched; introduces Chrome 108's `interactive-widget=resizes-content` opt-in to resize both. The article explicitly excluded iOS Chrome/WebKit support for the meta extension **at publication time**. It is historical platform evidence, not an exhaustive 2026 Safari support matrix.
2. [CSS Values 4, viewport sizes](https://drafts.csswg.org/css-values-4/#viewport-relative-lengths): overlay interfaces can have no effect on viewport-percentage lengths; “Typically on-screen keyboards will fit into this category.” Thus `dvh` alone cannot establish keyboard safety.
3. [CSSOM View, zoom/visual viewport](https://drafts.csswg.org/cssom-view/#visual-viewport): separates page zoom from visual-viewport scale, defines offsets relative to the layout viewport, and describes bringing an input into view after the virtual keyboard shrinks the visual viewport.
4. [WebKit Safari 15.4 announcement](https://webkit.org/blog/12445/new-webkit-features-in-safari-15-4/): documents `svh`, `lvh`, `dvh`, with `dvh` changing as the user scrolls; does not promise OS-keyboard accommodation.

The repository mobile-native skill's baseline sentence that compares Android's resize opt-in to iOS should not be read as platform verification. Its own hardware-verification requirement and the primary viewport definitions control this conclusion. No skill file was changed.

### Minimal measurement protocol (no content)

At initial scale 1, collect geometry **before focus, during opening, after settling, after close, after reopen, after rotation**. Remote inspector collection is a manual step for an authorized phone, not something this investigator performed.

Capture only:

- `innerWidth/innerHeight`, `document.documentElement.clientWidth/clientHeight`, `scrollX/scrollY`.
- `visualViewport.{width,height,offsetTop,offsetLeft,scale}` and `matchMedia('(display-mode: standalone)').matches`.
- Rectangles of `#app`, `.layout`, `.pane`, active composer/textarea/Send, open sheet/search/Close or launcher/menu, and terminal viewport/key toolbar. Record rectangle numbers, not text or arbitrary element IDs.
- Active element **tag, inputMode, readOnly and computed font size** only; no value/placeholder/aria-label.
- Event order/timestamps for window resize, visualViewport resize/**scroll**, focus/blur and orientation; selected field type only. For the static terminal fixture, also record numeric emitted cell geometry and whether unexpected mock input events occurred, without event text.

Compare DOM rectangles (layout CSS pixels) with visual bounds `[offsetTop, offsetTop + height]` and `[offsetLeft, offsetLeft + width]`. A textarea brought into view does not guarantee the adjacent Send/Close is visible. Browser DOM hit testing cannot prove absence of OS-keyboard overlay; pair measurements with direct physical observation using dummy content. If recording a screen, keep it fixture-only and redact machine/address/auth details.

## Evidence needed before implementing adaptation

A reviewer-approved repair requires a repeatable **user-visible** failure on a named phone/OS/display mode, not just the expected visualViewport shrink:

1. At `visualViewport.scale≈1`, opening the keyboard repeatedly leaves caret, Send, sheet Close or required search results covered/unreachable after settling, or the intended internal scroll cannot reveal them. Record which control and exact transition.
2. Geometry confirms layout/shell remains taller than the usable visual viewport, or that the value-only textarea cap stays wrong across resize without input. Distinguish browser auto-pan offsets and input font zoom from keyboard occlusion; record computed font and scale.
3. The same disposable setup is usable when the keyboard closes, and the failure survives the three-cycle, rotation and browser/PWA checks. A pinch-only issue is a separate zoom contract, not evidence for keyboard-height substitution.
4. Identify the smallest responsible owner: shell height, textarea cap, menu placement or dialog bounds. Do not replace every viewport unit or globally refocus/scroll as a workaround. Establish which coordinate space that owner's controls must occupy before selecting an API or strategy.
5. Agree a minimal repair and strongest boundary test with the reviewer. A controlled separate-layout/visual-viewport fixture may protect the chosen geometry/event-cleanup contract, but must be labelled synthetic; pair it with the phone checklist. Existing constrained terminal tests remain the primary touch-keyboard/resize/focus safeguard, not an OS-keyboard regression test.

Any future adaptation must preserve pinch zoom, intentional input and modal focus, draft/selection/read position, native-keyboard opt-in, IME and popup targeting, safe-area padding, existing terminal ResizeObserver/cell geometry, and no input replay. No strategy is approved or implemented here.
